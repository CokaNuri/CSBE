# 요구 페이징

> 요구 페이징 : 페이지를 미리 올리지 않고, 실제로 요청될 때(필요할 때) 메모리로 가져오는 방식

## 요구 페이징의 개요

**페이지를 언제 가져올까 — 두 가지 전략**

| 전략 | 내용 | 문제 |
|---|---|---|
| 미리 가져오기 (prefetch) | 앞으로 쓸 것 같은 페이지를 예측해 미리 적재 | 예측 실패 시 메모리·시간 낭비 |
| 요구 페이징 (demand paging) | **요청받은 페이지만** 그때그때 적재 | 첫 접근 때마다 적재 지연 |

- 현대 운영체제는 **요구 페이징이 기본** — 메모리를 효율적으로 쓰는 것이 우선
- 필요할 때까지 적재를 미룬다는 뜻에서 **게으른 스와퍼(lazy swapper)** 라고도 부름

---

## 페이지 테이블 엔트리의 구조

> 페이지 테이블의 한 행(엔트리)에는 프레임 번호 외에 상태를 나타내는 여러 비트가 있다

| 비트 | 다른 이름 | 내용 |
|---|---|---|
| 접근 비트 | 참조 비트 | 페이지에 읽기/실행 접근이 있었으면 1 |
| 변경 비트 | 더티 비트(dirty bit) | 페이지에 쓰기가 일어났으면 1 |
| 유효 비트 | 현재 비트 | 페이지가 물리 메모리에 **없으면** 1 (스왑 영역에 있음) |
| 읽기·쓰기·실행 비트 | 접근 권한 비트 | 허용된 접근 종류 표시, 위반 시 차단 |

- 유효 비트가 설정된 엔트리의 주소 필드는 프레임 번호가 아니라 **스왑 영역의 위치**를 가리킴
- 접근 비트·변경 비트는 **페이지 교체 알고리즘**(NUR 등)의 판단 재료

## 페이지 부재

> 페이지 부재(page fault) : 접근하려는 페이지가 물리 메모리에 없는 상황 — 인터럽트 발생

**페이지 부재 처리 과정**

1. 프로세스가 페이지에 접근 → 유효 비트 확인, 메모리에 없음 → **페이지 부재 인터럽트**
2. 메모리에 빈 프레임이 있으면 → 스왑 영역에서 페이지를 **스왑인**해 프레임에 적재
3. 빈 프레임이 없으면 → **희생될 페이지(victim page)** 를 골라 스왑 영역으로 **스왑아웃** 후 적재
4. 페이지 테이블 갱신 → 중단됐던 프로세스 재개

- 희생될 페이지를 고르는 기준이 **페이지 교체 알고리즘**
- 변경 비트가 0인 페이지는 디스크 내용과 같으므로 **쓰기 없이 버려도 됨** → 교체 비용 저렴

<details><summary>변경 비트(더티 비트)가 교체 비용을 좌우하는 이유는?</summary>

변경된(dirty) 페이지는 스왑 영역에 다시 써야 해서 디스크 쓰기 비용이 들지만, <br>
변경되지 않은 페이지는 디스크 원본과 같으므로 그냥 덮어써도 된다. <br>
그래서 교체 알고리즘은 가능하면 변경되지 않은 페이지를 희생양으로 고른다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 요구 페이징은 요청된 페이지만 그때그때 메모리에 올리는 방식으로, 페이지 테이블 엔트리의 접근·변경·유효·권한 비트로 상태를 관리하며, 페이지가 메모리에 없으면 페이지 부재 인터럽트가 발생해 스왑인(꽉 찼으면 희생 페이지 스왑아웃 후)으로 처리한다
