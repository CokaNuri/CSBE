# 스레싱과 프레임 할당

> 스레싱 : 페이지 교체(스왑)에 시간을 다 써서 정작 실제 작업은 못 하는 상태 — 프레임 할당으로 예방

## 스레싱

- 동시에 실행하는 프로세스 수(**멀티프로그래밍 정도**)를 늘리면 CPU 이용률이 올라가다가,
- 어느 순간을 넘기면 메모리가 부족해 **페이지 부재 → 스왑 → 또 페이지 부재**가 반복
- 하드디스크 입출력에 시간을 다 쓰고 CPU 이용률이 **급락**하는 지점 = **스레싱 발생 지점**

| 용어 | 내용 |
|---|---|
| 멀티프로그래밍 정도 | 동시에 메모리에 올라간 프로세스 수 |
| 스레싱 발생 지점 | 프로세스를 더 늘리면 CPU 이용률이 오히려 떨어지기 시작하는 지점 |

- 근본 해결 : 물리 메모리 증가, 또는 프로세스별 **적정 프레임 수 배분**

<details><summary>프로세스를 늘렸는데 CPU 이용률이 떨어지는 이유는?</summary>

각 프로세스가 가진 프레임이 너무 적어 페이지 부재가 폭증하기 때문이다. <br>
CPU가 일을 하려 해도 매번 페이지가 없어 디스크 스왑을 기다려야 하므로 <br>
실제 연산보다 입출력 대기에 시간을 다 쓰게 된다.
</details>

## 정적 할당

> 프로세스 시작 시점에 프레임 수를 미리 정해주는 방식

| 방식 | 내용 | 문제 |
|---|---|---|
| 균등 할당 | 모든 프로세스에 같은 수의 프레임 | 큰 프로세스는 부재 폭증, 작은 프로세스는 낭비 |
| 비례 할당 | 프로세스 **크기에 비례**해 프레임 배분 | 실행 중 필요량 변화를 반영 못 함 |

- 공통 한계 : 실행 중에 실제로 얼마나 쓰는지는 고려하지 않음

---

## 동적 할당

> 실행 중의 실제 접근 패턴을 보고 프레임 수를 조절하는 방식

**작업집합 모델 (working set model)**

- 최근 일정 시간(**작업집합 윈도우**) 동안 접근한 페이지 집합 = **작업집합**
- 작업집합에 든 페이지들을 메모리에 유지 → 지역성 활용
- 윈도우가 크면 유지 페이지 과다(낭비), 작으면 부재 증가 — 윈도우 크기가 성능 좌우

**페이지 부재 빈도 (PFF, Page Fault Frequency)**

- 페이지 부재 횟수를 관찰해 **상한선·하한선** 설정
- 부재 빈도 > 상한선 → 프레임 **추가 배정**
- 부재 빈도 < 하한선 → 프레임 **회수**

| 방식 | 판단 기준 |
|---|---|
| 작업집합 모델 | 어떤 페이지를 유지할까 (집합 내용) |
| PFF | 프레임을 몇 개 줄까 (부재 빈도) |

## 전역 교체와 지역 교체

> 페이지 부재 시 희생 페이지를 어느 범위에서 고를 것인가

| 방식 | 범위 | 특징 |
|---|---|---|
| 지역 교체 | **자기 프로세스**의 페이지 중에서 교체 | 다른 프로세스에 영향 없음, 자기 프레임 수 고정 |
| 전역 교체 | **전체 메모리**의 페이지 중에서 교체 | 효율적이지만 남의 프레임을 뺏어 다른 프로세스 부재 유발 가능 |

- 전역 교체는 한 프로세스의 스레싱이 **전체로 번질 수 있음** → 동적 할당과 함께 조절 필요

## 🔑 최종 정리

> 한 줄 요약: 스레싱은 프레임 부족으로 스왑만 반복하며 CPU 이용률이 급락하는 상태로, 예방하려면 프레임을 적절히 배분해야 하는데 정적 할당(균등·비례)은 실행 중 변화를 못 보므로 작업집합 모델·페이지 부재 빈도(PFF) 같은 동적 할당으로 조절하고, 교체 범위는 지역(자기 것만)과 전역(전체)으로 나뉜다
