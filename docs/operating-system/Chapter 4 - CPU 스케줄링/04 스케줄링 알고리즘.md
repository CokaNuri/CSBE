# 스케줄링 알고리즘

> 준비 큐의 프로세스 중 어떤 것에 CPU를 배정할지 정하는 구체적인 알고리즘들

## 스케줄링 알고리즘의 선택 기준

| 기준 | 내용 | 방향 |
|---|---|---|
| CPU 사용률 | 전체 시간 중 CPU가 일한 시간의 비율 | 높을수록 좋음 |
| 처리량 | 단위 시간당 완료된 작업 수 | 높을수록 좋음 |
| 대기 시간 | 준비 큐에서 기다린 시간의 합 | 짧을수록 좋음 |
| 응답 시간 | 요청 후 첫 응답이 오기까지의 시간 | 짧을수록 좋음 |
| 반환 시간 | 도착부터 종료까지 걸린 전체 시간 (대기 시간 + 실행 시간) | 짧을수록 좋음 |

---

## FCFS 스케줄링 (First Come First Served)

> 준비 큐에 도착한 순서대로 CPU를 배정 — **비선점형**

- 큐가 하나뿐이며 구현이 매우 단순 (공평해 보임)
- **콘보이 효과** : 실행 시간이 긴 프로세스가 앞에 있으면 뒤의 짧은 프로세스들이 모두 오래 기다림
- 현재 작업이 입출력을 하는 동안 CPU가 놀게 되어 효율 저하

**예** : P1(실행 30) → P2(실행 3) → P3(실행 6) 도착 시

| 프로세스 | 대기 시간 | 반환 시간 |
|---|---|---|
| P1 | 0 | 30 |
| P2 | 30 | 33 |
| P3 | 33 | 39 |
| 평균 | 21 | 34 |

---

## SJF 스케줄링 (Shortest Job First)

> 실행 시간이 가장 짧은 작업부터 CPU를 배정 — **비선점형** (최단 작업 우선)

**위 예를 SJF로** : P2(3) → P3(6) → P1(30) 순서로 실행

| 프로세스 | 대기 시간 | 반환 시간 |
|---|---|---|
| P2 | 0 | 3 |
| P3 | 3 | 9 |
| P1 | 9 | 39 |
| 평균 | 4 | 17 |

- 같은 작업을 FCFS보다 평균 대기 21 → 4 로 단축 (평균 대기 시간 **최소화** 이론상 최적)

**문제점**

| 문제 | 내용 |
|---|---|
| 실행 시간 예측 불가 | 프로세스의 종료 시간을 정확히 알기 어려움 (현실 적용의 최대 장벽) |
| 아사 | 긴 작업은 짧은 작업들에 계속 밀려 무한 연기될 수 있음 |

- 아사의 완화책 : **에이징** — 오래 기다릴수록 우선순위를 높여줌

---

## HRN 스케줄링 (Highest Response Ratio Next)

> SJF의 아사 문제를 완화한 비선점형 알고리즘 — 대기 시간을 고려하여 우선순위 계산

> **우선순위 = (대기 시간 + 실행 시간) ÷ 실행 시간**

- 값이 **클수록** 먼저 실행
- 실행 시간이 짧을수록 유리한 건 유지하면서, 오래 기다린 프로세스의 우선순위가 자연히 올라감 (에이징 내장)
- 그래도 공평성이 완전히 보장되지는 않아 널리 쓰이진 않음

---

## 라운드 로빈 스케줄링

> 각 프로세스에 타임 슬라이스만큼 CPU를 주고, 다 쓰면 준비 큐 맨 뒤로 보냄 — **선점형**

- 시분할 시스템의 대표 알고리즘, 오늘날 스케줄링의 기본 뼈대
- FCFS를 선점형으로 바꾼 것과 같음

**타임 슬라이스 크기의 트레이드오프**

| 타임 슬라이스 | 결과 |
|---|---|
| 너무 크면 | FCFS와 다를 게 없어짐 (응답성 저하) |
| 너무 작으면 | 문맥 교환이 잦아져 오버헤드가 실제 작업보다 커짐 |

- 적절한 크기 : 문맥 교환 비용을 감안하여 응답성을 해치지 않는 선 (유닉스 계열 약 10~100ms 수준)

---

## SRT 스케줄링 (Shortest Remaining Time)

> SJF의 선점형 버전 — **남은 시간**이 가장 짧은 프로세스에 CPU 배정

- 실행 도중 더 짧은 프로세스가 도착하면 CPU를 빼앗아 그쪽에 배정
- 평균 대기 시간은 더 줄지만, SJF의 문제(실행 시간 예측, 아사)에 문맥 교환 오버헤드까지 더해져 실제로는 잘 안 쓰임

---

## 우선순위 스케줄링

> 우선순위가 높은 프로세스에 먼저 CPU 배정 — 선점형·비선점형 모두 구현 가능

- SJF·HRN도 사실상 우선순위 스케줄링의 일종 (실행 시간·응답률이 곧 우선순위)
- 문제점 : 공평성 훼손, 낮은 우선순위 프로세스의 **아사** 발생 가능 → 에이징으로 완화

---

## 다단계 큐 스케줄링

> 우선순위별로 준비 큐를 여러 개 두고, 항상 높은 우선순위 큐부터 처리 — **선점형**

- 프로세스는 자신의 우선순위 큐에 고정 (큐 사이 이동 불가)
- 높은 큐가 비어야 낮은 큐가 실행됨
- 문제점 : 우선순위가 낮은 큐의 프로세스는 한없이 기다릴 수 있음 (아사)

---

## 다단계 피드백 큐 스케줄링

> 다단계 큐의 아사 문제를 개선 — CPU를 사용하고 나면 프로세스의 우선순위가 낮아져 **아래 큐로 이동**

- 우선순위가 낮은 큐일수록 **타임 슬라이스가 커짐** : 자주 실행되지 못하는 대신 한 번 잡으면 오래 씀
- 커널 프로세스 영역까지는 내려가지 않도록 경계 유지
- **오늘날 운영체제가 사용하는 표준적인 CPU 스케줄링 방식**

<details><summary>다단계 큐와 다단계 피드백 큐의 결정적 차이는?</summary>

큐 사이의 이동 가능 여부다. 다단계 큐는 프로세스가 처음 배정된 우선순위 큐에 고정되지만, <br>
다단계 피드백 큐는 CPU를 쓸 때마다 우선순위가 한 단계씩 낮아지며 큐를 이동한다. <br>
덕분에 낮은 우선순위 프로세스도 언젠가는 실행 기회를 얻어 아사가 완화된다.
</details>

## 알고리즘 총정리

| 알고리즘 | 선점 여부 | 핵심 아이디어 | 주요 문제 |
|---|---|---|---|
| FCFS | 비선점 | 도착 순서대로 | 콘보이 효과 |
| SJF | 비선점 | 실행 시간 짧은 것 먼저 | 실행 시간 예측 불가, 아사 |
| HRN | 비선점 | (대기+실행)/실행 비율 큰 것 먼저 | 공평성 불완전 |
| 라운드 로빈 | 선점 | 타임 슬라이스만큼 돌아가며 | 타임 슬라이스 크기 민감 |
| SRT | 선점 | 남은 시간 짧은 것 먼저 | SJF 문제 + 문맥 교환 부담 |
| 우선순위 | 둘 다 | 우선순위 높은 것 먼저 | 아사 |
| 다단계 큐 | 선점 | 우선순위별 고정 큐 | 하위 큐 아사 |
| 다단계 피드백 큐 | 선점 | 큐 이동 + 가변 타임 슬라이스 | (현대 OS 채택) |

---

## 🔑 최종 정리

> 한 줄 요약: 스케줄링 알고리즘은 FCFS에서 출발해 짧은 작업 우선(SJF·SRT), 에이징 반영(HRN), 시분할(라운드 로빈)을 거쳐, 우선순위 큐 이동과 가변 타임 슬라이스로 아사까지 완화한 다단계 피드백 큐로 발전했다
