# 다중 프로그래밍 환경의 메모리 할당

> 여러 프로세스를 동시에 메모리에 올리는 방식 — 가변 분할과 고정 분할, 그리고 각자의 단편화 문제

## 메모리 분할 방식

| 방식 | 내용 | 비유 |
|---|---|---|
| 가변 분할 방식 | 프로세스 **크기에 맞춰** 메모리를 나눔 | 칸막이 없는 원룸 |
| 고정 분할 방식 | 메모리를 **같은 크기로 미리** 나눠 배정 | 같은 크기의 방 여러 개 |

- 가변 분할 → 훗날 **세그먼테이션**, 고정 분할 → 훗날 **페이징**의 뿌리

---

## 가변 분할 방식의 메모리 관리

> 프로세스 크기대로 연속 배치 — 빈 공간이 조각나는 외부 단편화 발생

- 프로세스가 **연속된 공간**에 통째로 들어감 (메모리 관리 단순, 프로세스 입장 자연스러움)
- 프로세스가 종료되면 그 자리에 **빈 조각**이 남음 → 조각이 작아서 재사용 못 하는 **외부 단편화**

**배치 전략 (새 프로세스를 어느 빈 공간에 넣을까)**

| 전략 | 내용 | 특징 |
|---|---|---|
| 최초 배치 (first fit) | 처음 발견한 들어갈 수 있는 공간에 배치 | 검색 빠름 |
| 최적 배치 (best fit) | 크기가 가장 **비슷한** 공간에 배치 | 낭비 적지만 아주 작은 조각 양산 |
| 최악 배치 (worst fit) | 가장 **큰** 공간에 배치 | 남는 조각이 커서 재사용 가능 |

**외부 단편화 해결**

| 방법 | 내용 | 비용 |
|---|---|---|
| 조각 모음 (compaction) | 프로세스들을 한쪽으로 밀어 빈 공간을 합침 | 실행 중 프로세스 중단·이동·주소 재조정 — 부담 큼 |

---

## 고정 분할 방식의 메모리 관리

> 같은 크기 조각으로 잘라 배치 — 조각 안에 남는 공간, 내부 단편화 발생

- 프로세스가 조각 크기보다 크면 **여러 조각에 나뉘어** 들어감 (비연속 배치)
- 조각 크기보다 작은 부분이 조각 안에 남음 → **내부 단편화**
- 내부 단편화는 **조각 크기를 적절히 줄이면** 낭비 최소화 가능 (조각 모음 불필요)
- 관리가 단순하고 예측 가능 → 현대 운영체제 페이징의 기반

**가변 vs 고정 비교**

| 구분 | 가변 분할 | 고정 분할 |
|---|---|---|
| 배치 | 연속 | 비연속 (쪼개져 들어감) |
| 단편화 | 외부 단편화 | 내부 단편화 |
| 해결 | 조각 모음 (비쌈) | 조각 크기 조절 (저렴) |
| 관리 | 복잡 | 단순 |

<details><summary>현대 운영체제가 고정 분할(페이징) 쪽을 택한 이유는?</summary>

외부 단편화는 조각 모음이라는 비싼 작업 없이는 해결이 안 되지만, <br>
내부 단편화는 조각 크기를 조절하는 것만으로 낭비를 줄일 수 있기 때문이다. <br>
관리도 단순해서 고정 분할이 페이징으로 발전해 표준이 됐다.
</details>

## 버디 시스템

> 가변과 고정의 중간 — 메모리를 2의 거듭제곱 크기로 반씩 쪼개서 배정

- 프로세스 크기에 맞을 때까지 메모리를 **절반씩 분할**해 배정 (예: 1MB → 512KB → 256KB…)
- 나뉜 두 조각이 서로 **버디(buddy)** — 둘 다 비면 **자동으로 합쳐** 큰 조각 복원
- 비슷한 크기 조각이 모여 있어 **외부 단편화 완화**, 합치기도 간단 (조각 모음 불필요)
- 조각 안에 남는 공간은 있음 → 내부 단편화는 존재
- 리눅스 커널의 메모리 할당에 실제 사용

---

## 🔑 최종 정리

> 한 줄 요약: 다중 프로그래밍 메모리 할당은 크기대로 연속 배치하는 가변 분할(외부 단편화→조각 모음)과 같은 크기로 쪼개는 고정 분할(내부 단편화→조각 크기 조절)로 나뉘고, 버디 시스템은 2의 거듭제곱으로 반씩 쪼개고 비면 합치는 절충안이며, 현대 운영체제는 고정 분할 계열(페이징)을 택했다
