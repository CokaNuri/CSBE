# 분할 컴파일과 메모리 관리

> 소스코드를 여러 파일로 나눠 컴파일하는 분할 컴파일과, 변수가 실제 메모리에 놓이는 방식

## 분할 컴파일

> 소스코드를 여러 파일로 나눠 각각 컴파일한 뒤 링커로 합치는 방식

- 큰 프로그램을 파일 하나로 관리하면 수정할 때마다 **전체 재컴파일** 필요 → 낭비
- 분할 컴파일 : 파일별로 **목적 코드(오브젝트 파일)** 생성 → **수정된 파일만** 다시 컴파일
- 링커가 목적 코드들 + 라이브러리를 묶어 실행 파일 생성

| 장점 | 내용 |
|---|---|
| 빌드 시간 절약 | 바뀐 파일만 재컴파일 |
| 분업 가능 | 파일 단위로 나눠 개발 |
| 재사용 | 목적 코드·라이브러리 공유 |

<details><summary>분할 컴파일이 라이브러리 생태계의 기반인 이유는?</summary>

소스코드 없이 목적 코드만 있어도 링크해서 쓸 수 있기 때문이다. <br>
미리 컴파일된 목적 코드 묶음이 곧 라이브러리이고, <br>
링커가 내 코드와 라이브러리를 연결해 하나의 실행 파일로 만든다.
</details>

## 변수와 메모리 할당

> 변수의 종류에 따라 메모리에 놓이는 위치와 시점이 다르다

**프로세스의 메모리 구조와 변수**

| 영역 | 놓이는 것 | 할당 시점 |
|---|---|---|
| 코드 영역 | 실행할 명령어 | 로딩 시 |
| 데이터 영역 | **전역 변수, 정적(static) 변수** | 로딩 시 (프로세스 종료까지 유지) |
| 스택 영역 | **지역 변수, 매개변수** | 함수 호출 시 (함수 끝나면 자동 해제) |
| 힙 영역 | **동적 할당** 데이터 (malloc, new) | 실행 중 요청 시 (직접 해제 필요) |

- 지역 변수가 함수 종료와 함께 사라지는 이유 : 스택 프레임째로 **pop** 되기 때문
- 힙은 해제를 잊으면 **메모리 누수(memory leak)** — 가비지 컬렉터가 있는 언어는 자동 회수
- 스택과 힙은 서로를 향해 자라며, 만나면 메모리 부족

## 🔑 최종 정리

> 한 줄 요약: 분할 컴파일은 소스를 파일 단위로 나눠 목적 코드로 컴파일하고 링커로 합쳐 수정분만 재컴파일하게 하는 방식이며, 변수는 종류에 따라 전역·정적은 데이터 영역(로딩 시), 지역은 스택(함수 호출 시), 동적 할당은 힙(실행 중)에 놓인다
