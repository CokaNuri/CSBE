# 단일 프로그래밍 환경의 메모리 할당

> 한 번에 하나의 프로세스만 메모리에 올리던 초기 방식 — 메모리보다 큰 프로그램을 다루려 오버레이·스왑이 등장

## 단일 프로그래밍 환경

- 메모리에 운영체제 + **단 하나의 사용자 프로세스**만 올림
- 메모리를 **운영체제 영역**과 **사용자 영역**으로 나눔
- 사용자 프로세스가 운영체제 영역을 침범하지 못하도록 **경계 레지스터**로 보호
- 문제 : 프로그램이 메모리보다 크면 실행할 수 없음 → 이를 해결하려는 것이 오버레이

---

## 메모리 오버레이

> 프로그램을 여러 조각으로 나눠, 지금 필요한 부분만 메모리에 올려 실행하는 기법

- 프로그램 전체가 메모리보다 커도, **필요한 조각(모듈)** 만 번갈아 올려 실행
- 현재 필요 없는 조각은 메모리에서 내리고 그 자리에 다음 조각을 덮어씀(overlay)
- 어떤 조각을 언제 올릴지는 **프로그래머가 직접 설계**해야 했음 (초기 방식의 부담)
- 의의 : "프로그램 전체가 메모리에 다 있지 않아도 실행 가능하다"는 **가상 메모리의 기본 아이디어**를 제공

<details><summary>메모리 오버레이가 중요한 이유는?</summary>

프로그램 전체를 메모리에 올리지 않고도 실행할 수 있음을 처음 보여줬기 때문이다. <br>
"필요한 부분만 올린다"는 이 발상이 훗날 운영체제가 자동으로 처리하는 <br>
가상 메모리·페이징으로 발전했다.
</details>

## 스왑

> 메모리에서 쫓겨난 프로세스를 저장장치의 특별한 영역에 잠시 보관했다가 다시 불러오는 기법

| 용어 | 내용 |
|---|---|
| 스왑 영역 | 메모리에서 쫓겨난 프로세스를 임시 보관하는 **저장장치(디스크)의 공간** |
| 스왑 아웃 | 메모리의 프로세스를 스왑 영역으로 **내보내는** 것 |
| 스왑 인 | 스왑 영역의 프로세스를 메모리로 **불러오는** 것 |

- 스왑 영역 덕분에 **물리 메모리보다 많은 프로세스**를 돌릴 수 있음 (메모리가 커 보이는 효과)
- 스왑은 디스크 입출력이라 메모리 접근보다 훨씬 느림 → 스왑이 잦으면 성능 급락
- 스왑 영역은 저장장치에 있지만, 관리 주체는 파일 시스템이 아니라 **메모리 관리자**

---

## 🔑 최종 정리

> 한 줄 요약: 단일 프로그래밍 환경은 프로세스 하나만 메모리에 올리던 방식으로, 메모리보다 큰 프로그램은 필요한 조각만 번갈아 올리는 오버레이로, 부족한 메모리는 프로세스를 디스크 스왑 영역으로 내보냈다 불러오는 스왑으로 해결했으며 이는 가상 메모리의 토대가 됐다
