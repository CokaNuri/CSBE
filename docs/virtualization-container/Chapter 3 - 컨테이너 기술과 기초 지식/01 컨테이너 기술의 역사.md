# 컨테이너 기술의 역사

> 컨테이너는 도커와 함께 갑자기 등장한 기술이 아니라, 1979년 **chroot**에서 시작된 "프로세스 격리" 기술이 쌓여 만들어진 것

## 컨테이너 기술의 역사

| 연도 | 기술 | 내용 |
|---|---|---|
| 1979 | chroot | 유닉스에서 프로세스가 볼 수 있는 **루트 디렉터리를 변경** — 파일 시스템 격리의 시작 |
| 2000 | FreeBSD Jail | 파일 시스템 + 프로세스·네트워크까지 격리 |
| 2001 | Linux-VServer | 리눅스에서 OS 수준 가상화 구현 |
| 2004 | Solaris Containers (Zones) | 격리 + 자원 관리를 통합 — "컨테이너"라는 이름 사용 |
| 2005 | OpenVZ | 리눅스용 OS 수준 가상화 (커널 패치 방식) |
| 2006~2008 | cgroups | 구글이 개발, 리눅스 커널에 통합 — 프로세스 그룹의 **자원 사용량 제한** |
| 2008 | LXC | 네임스페이스 + cgroups를 조합한 리눅스 컨테이너 — 표준 커널만으로 동작 |
| 2013 | Docker | 이미지·레지스트리·간단한 명령으로 컨테이너를 **누구나 쓸 수 있게** 만듦 |
| 2014 | Kubernetes | 구글이 공개한 컨테이너 오케스트레이션 도구 |
| 2015 | OCI / CNCF | 컨테이너 이미지·런타임 표준화 단체, 클라우드 네이티브 재단 설립 |

**흐름**

```
파일 시스템 격리 (chroot)
   → 프로세스·네트워크 격리 (Jail, 네임스페이스)
   → 자원 제한 (cgroups)
   → 이를 조합한 컨테이너 (LXC)
   → 이미지와 배포 방식 (Docker)
   → 대규모 운용과 표준화 (Kubernetes, OCI)
```

**도커가 바꾼 것**

- 격리 기술 자체는 이미 있었음 → 도커는 **사용 방법**을 바꿈

| 요소 | 내용 |
|---|---|
| 이미지 | 애플리케이션 + 실행 환경을 하나로 묶어 배포 단위로 만듦 |
| Dockerfile | 환경 구축 절차를 코드로 기록 → 재현 가능 |
| 레지스트리 (Docker Hub) | 이미지를 공유·재사용 |
| 계층 구조 | 변경된 부분만 저장·전송 → 빠르고 가벼움 |

- 초기 도커는 LXC를 이용 → 이후 자체 런타임(libcontainer → runC)으로 교체

**표준화 (OCI, Open Container Initiative)**

| 표준 | 내용 |
|---|---|
| 이미지 사양 | 컨테이너 이미지의 형식 |
| 런타임 사양 | 컨테이너를 실행하는 방법 |
| 배포 사양 | 레지스트리와 이미지를 주고받는 방법 |

- 표준 덕분에 도커로 만든 이미지를 다른 컨테이너 런타임에서도 그대로 실행

<details><summary>chroot만으로는 왜 컨테이너라고 할 수 없을까?</summary>

chroot는 프로세스가 보는 파일 시스템의 루트만 바꿀 뿐이다. <br>
프로세스 목록·네트워크·사용자는 호스트와 그대로 공유되고, CPU·메모리 사용량도 제한할 수 없으며 root 권한이 있으면 빠져나올 수도 있다. <br>
네임스페이스(보이는 범위 분리)와 cgroups(자원 제한)가 더해져야 독립된 실행 환경이 된다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 컨테이너 기술은 1979년 chroot의 파일 시스템 격리에서 시작해 FreeBSD Jail·Solaris Containers를 거쳐 리눅스의 네임스페이스와 cgroups를 조합한 LXC로 발전했고, 2013년 도커가 이미지와 레지스트리로 사용성을 바꾸며 대중화되었으며 이후 쿠버네티스와 OCI 표준으로 대규모 운용과 호환성이 갖춰졌다
