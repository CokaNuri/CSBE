# 데브옵스와 컨테이너 기술

> 데브옵스 : 개발(Development)과 운영(Operations)이 **협력**해 소프트웨어를 빠르고 안정적으로 제공하려는 문화·방법 — 컨테이너가 이를 기술적으로 뒷받침

## 데브옵스란

**개발과 운영의 대립**

| 구분 | 개발 팀 | 운영 팀 |
|---|---|---|
| 목표 | 새 기능을 빨리 출시 | 서비스를 안정적으로 유지 |
| 변경에 대한 태도 | 변경을 원함 | 변경은 장애 위험 |

- 목표가 달라 서로 책임을 떠넘기고 배포가 느려짐 → 두 조직이 **같은 목표**를 향해 협력하자는 것이 데브옵스

**데브옵스의 요소**

| 요소 | 내용 |
|---|---|
| 문화 | 개발·운영의 공동 책임, 정보 공유, 실패를 비난하지 않고 개선 |
| 자동화 | 빌드·테스트·배포·인프라 구축을 자동화 |
| 측정 | 배포 빈도, 장애 복구 시간 등을 수치로 파악 |
| 공유 | 도구·지식·경험을 팀 간에 공유 |

**주요 프랙티스**

| 프랙티스 | 내용 |
|---|---|
| CI (지속적 통합) | 코드 변경을 자주 통합하고 자동으로 빌드·테스트 |
| CD (지속적 전달·배포) | 테스트를 통과한 결과물을 자동으로 배포 가능한 상태로 만들거나 실제 배포 |
| IaC (코드형 인프라) | 인프라 구성을 코드로 작성·버전 관리 |
| 모니터링 | 운영 상태를 관찰해 개발에 피드백 |

```
계획 → 코딩 → 빌드 → 테스트 → 릴리스 → 배포 → 운영 → 모니터링 → (계획으로)
```

## 데브옵스와 컨테이너 기술

> 컨테이너 이미지가 개발과 운영 사이의 **공통 전달 단위**가 됨

| 데브옵스의 과제 | 컨테이너의 해결 |
|---|---|
| 개발·운영 환경 차이로 인한 오류 | 이미지에 실행 환경까지 포함 → 어디서나 동일 |
| 환경 구축에 시간이 걸림 | 이미지에서 수 초 만에 기동 |
| 배포 절차가 복잡하고 수작업 | 이미지 교체로 배포 — 자동화 용이 |
| 문제 발생 시 복구가 느림 | 이전 버전 이미지로 즉시 롤백 |
| 인프라 구성이 문서·기억에 의존 | Dockerfile·매니페스트로 코드화 |

**컨테이너 기반 CI/CD 흐름**

```
코드 푸시 → 자동 빌드 → 자동 테스트 → 이미지 빌드 → 레지스트리 등록 → 운영 환경에 배포
```

1. 개발자가 코드를 저장소에 푸시
2. CI 도구가 빌드·테스트 후 **컨테이너 이미지** 생성
3. 이미지를 레지스트리에 등록 (버전 태그 부여)
4. 테스트 환경 → 운영 환경으로 **같은 이미지**를 배포

- 테스트를 통과한 이미지가 그대로 운영에 올라감 → "테스트한 것과 다른 것이 배포되는" 문제 제거

| 역할 분담 | 내용 |
|---|---|
| 개발 | 애플리케이션과 실행 환경을 이미지로 정의 |
| 운영 | 이미지를 실행할 기반(오케스트레이션, 감시, 확장) 제공 |

<details><summary>컨테이너를 도입하면 데브옵스가 완성되는 것일까?</summary>

아니다. 데브옵스의 본질은 개발과 운영이 협력하는 문화와 일하는 방식이고 컨테이너는 이를 쉽게 해 주는 도구다. <br>
컨테이너를 쓰더라도 조직이 여전히 분리되어 책임을 떠넘기거나 배포를 수작업으로 한다면 효과가 없다. <br>
반대로 컨테이너 없이도 자동화와 협력으로 데브옵스를 실천할 수 있다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 데브옵스는 빠른 출시를 원하는 개발과 안정을 원하는 운영이 협력해 CI/CD·IaC·모니터링으로 소프트웨어를 빠르고 안정적으로 제공하는 문화이며, 컨테이너는 실행 환경까지 담은 이미지를 공통 전달 단위로 삼아 환경 차이를 없애고 배포·롤백 자동화를 쉽게 해 데브옵스를 기술적으로 뒷받침한다
