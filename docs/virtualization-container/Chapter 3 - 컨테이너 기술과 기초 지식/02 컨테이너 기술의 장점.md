# 컨테이너 기술의 장점

> 컨테이너는 애플리케이션과 실행 환경을 이미지로 묶어 **가상 서버를 손쉽게 구축**하게 해 준다 — 단, 데이터는 컨테이너에 넣지 않는다

## 컨테이너 기술의 장점

| 장점 | 내용 |
|---|---|
| 가벼움 | 게스트 OS가 없어 이미지가 작고 CPU·메모리 소비가 적음 |
| 빠른 기동 | 프로세스를 시작하는 수준 — 초 단위 |
| 고밀도 | 같은 서버에 가상 머신보다 훨씬 많이 실행 |
| 이식성 | 이미지만 있으면 PC·서버·클라우드 어디서나 **같은 환경**으로 동작 |
| 재현성 | Dockerfile로 환경 구축 절차를 코드화 → 누가 만들어도 동일 |
| 환경 격리 | 컨테이너마다 라이브러리·버전이 달라도 충돌 없음 |
| 쉬운 확장 | 같은 이미지로 컨테이너를 여러 개 띄워 스케일 아웃 |
| 빠른 배포·롤백 | 이미지 교체만으로 배포, 이전 이미지로 되돌리기 쉬움 |

**"내 PC에서는 되는데요" 문제 해결**

- 기존 : 개발·테스트·운영 환경의 OS·라이브러리 버전이 달라 동작이 달라짐
- 컨테이너 : 애플리케이션과 의존성을 **이미지 하나로 묶어** 그대로 옮김 → 환경 차이 제거

**이미지의 계층 구조**

```
[ 컨테이너 계층 (쓰기 가능) ]   ← 컨테이너마다 따로, 삭제 시 사라짐
[ 애플리케이션 코드        ]   ┐
[ 라이브러리·런타임        ]   │ 이미지 계층 (읽기 전용, 공유)
[ 베이스 이미지 (OS 파일)  ]   ┘
```

- 같은 계층은 여러 이미지·컨테이너가 공유 → 저장 공간 절약, 변경된 계층만 전송

## 데이터를 컨테이너에 포함하지 않는다

> 컨테이너는 **언제든 버리고 새로 만들 수 있어야** 한다 — 컨테이너 안에 쓴 데이터는 컨테이너를 삭제하면 함께 사라짐

- 컨테이너의 쓰기 계층은 **임시** → 삭제·재생성하면 초기 상태로 돌아감
- 따라서 남겨야 할 데이터(DB 파일, 업로드 파일, 로그)는 컨테이너 **바깥**에 저장

| 방식 | 내용 | 용도 |
|---|---|---|
| 볼륨 | 컨테이너 엔진이 관리하는 호스트의 저장 영역을 컨테이너에 연결 | DB 데이터 등 영속 데이터 |
| 바인드 마운트 | 호스트의 특정 디렉터리를 컨테이너에 연결 | 개발 중 소스 코드 공유, 설정 파일 |
| 외부 스토리지·서비스 | 네트워크 스토리지, 관리형 DB, 오브젝트 스토리지 | 여러 호스트에서 공유해야 하는 데이터 |

| 구분 | 상태 비저장 (stateless) | 상태 저장 (stateful) |
|---|---|---|
| 내용 | 컨테이너가 데이터를 갖지 않음 | 컨테이너가 데이터를 보유 |
| 교체·확장 | 자유롭게 버리고 늘림 | 데이터 보존·동기화 필요 |
| 예 | 웹 서버, API 서버 | DB, 파일 저장소 |

- 컨테이너는 **불변 인프라** 사고방식 : 실행 중인 컨테이너를 고치지 않고, 새 이미지를 만들어 통째로 교체
- 설정 값(접속 정보 등)도 이미지에 넣지 않고 **환경 변수**로 외부에서 주입

<details><summary>컨테이너 안에 데이터를 저장하면 스케일 아웃할 때 어떤 문제가 생길까?</summary>

컨테이너를 여러 개로 늘리면 각 컨테이너가 서로 다른 데이터를 갖게 된다. <br>
사용자가 올린 파일이 1번 컨테이너에만 있으면 2번 컨테이너로 간 요청에서는 보이지 않고, <br>
부하가 줄어 컨테이너가 삭제되면 그 데이터도 사라진다. 데이터를 외부에 두어야 어느 컨테이너가 처리해도 결과가 같다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 컨테이너는 게스트 OS 없이 가볍고 빠르게 기동하며 이미지로 환경을 묶어 어디서나 동일하게 재현할 수 있어 구축·배포·확장이 쉽고, 언제든 버리고 새로 만들 수 있도록 영속 데이터는 볼륨이나 외부 스토리지에 두고 설정은 환경 변수로 주입해 상태 비저장으로 설계한다
