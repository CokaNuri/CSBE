# 마이크로서비스

> 마이크로서비스 : 하나의 애플리케이션을 **작고 독립적인 서비스들의 조합**으로 구성하는 설계 기법 — 컨테이너와 궁합이 좋다

## 마이크로서비스와 모놀리스

| 용어 | 내용 |
|---|---|
| 모놀리스 | 모든 기능을 **하나의 애플리케이션**으로 만들어 통째로 배포 |
| 마이크로서비스 | 기능별로 서비스를 나누고 각 서비스가 **API**(HTTP/REST, gRPC, 메시지 큐)로 통신 |

```
모놀리스                    마이크로서비스
┌──────────────┐           [회원] [상품] [주문] [결제]
│ 회원 상품     │             │      │      │      │
│ 주문 결제     │            (DB)   (DB)   (DB)   (DB)
└──────┬───────┘
      (DB)
```

| 구분 | 모놀리스 | 마이크로서비스 |
|---|---|---|
| 배포 단위 | 전체를 한 번에 | 서비스별로 독립 배포 |
| 변경 영향 | 작은 수정에도 전체 재배포 | 해당 서비스만 |
| 확장 | 전체를 통째로 복제 | 부하가 큰 서비스만 확장 |
| 장애 | 한 기능의 문제가 전체를 멈춤 | 해당 서비스로 국한 가능 |
| 기술 선택 | 하나의 언어·프레임워크 | 서비스마다 다른 기술 가능 |
| 데이터 | 하나의 DB 공유 | 서비스별 DB |
| 팀 | 큰 팀이 하나의 코드 공유 | 서비스별 작은 팀이 자율적으로 개발 |
| 초기 개발 | 단순하고 빠름 | 설계·기반 구축 부담 |

**마이크로서비스의 단점**

| 단점 | 내용 |
|---|---|
| 운용 복잡성 | 서비스 수만큼 배포·감시 대상 증가 |
| 통신 오버헤드 | 함수 호출이 네트워크 통신으로 바뀜 → 지연·실패 가능 |
| 데이터 일관성 | DB가 나뉘어 트랜잭션 처리가 어려움 |
| 장애 추적 | 요청이 여러 서비스를 거쳐 원인 파악이 어려움 → 분산 추적 필요 |
| 테스트 | 서비스 간 연동 테스트가 복잡 |

## 마이크로서비스와 컨테이너

> 서비스 하나 = 컨테이너 하나 — 컨테이너의 특성이 마이크로서비스의 요구와 맞아떨어짐

| 마이크로서비스의 요구 | 컨테이너의 특성 |
|---|---|
| 서비스마다 독립된 실행 환경 | 컨테이너별 격리 — 언어·라이브러리가 달라도 충돌 없음 |
| 서비스별 독립 배포 | 이미지 단위로 빌드·배포 |
| 서비스별 확장 | 필요한 컨테이너만 수를 늘림 |
| 많은 수의 서비스 실행 | 가볍고 고밀도 — 가상 머신보다 자원 효율적 |
| 빠른 교체·복구 | 초 단위 기동, 문제 시 버리고 재생성 |

**함께 필요한 기술**

| 기술 | 역할 |
|---|---|
| 컨테이너 오케스트레이션 | 다수 컨테이너의 배치·확장·복구 자동화 (Kubernetes) |
| 서비스 디스커버리 | 수시로 바뀌는 서비스의 위치(IP)를 찾아 줌 |
| API 게이트웨이 | 외부 요청의 단일 진입점 — 라우팅·인증 |
| 서비스 메시 | 서비스 간 통신의 제어·암호화·관측 (Istio 등) |
| 중앙 로그·분산 추적 | 흩어진 로그와 요청 흐름을 한곳에서 확인 |

<details><summary>모든 시스템을 마이크로서비스로 만드는 것이 좋을까?</summary>

아니다. 규모가 작거나 팀이 작으면 서비스 분할로 얻는 이점보다 운용 복잡성이 더 크다. <br>
처음에는 모놀리스로 빠르게 만들고, 규모와 조직이 커져 배포 충돌이나 확장 문제가 생길 때 <br>
경계가 분명한 부분부터 서비스로 떼어 내는 방식이 현실적이다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 마이크로서비스는 애플리케이션을 API로 통신하는 작은 독립 서비스들로 나누어 서비스별로 배포·확장·기술 선택을 할 수 있게 하는 설계 기법으로, 운용 복잡성과 통신·데이터 일관성 문제가 따르며, 서비스마다 격리되고 가볍게 실행·교체할 수 있는 컨테이너와 오케스트레이션이 이를 뒷받침한다
