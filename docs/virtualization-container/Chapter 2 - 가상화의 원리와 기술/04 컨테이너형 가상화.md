# 컨테이너형 가상화

> 호스트 OS의 커널을 공유하면서 **애플리케이션별로 독립된 실행 공간(컨테이너)**을 구축하는 방식 — 게스트 OS가 없다

## 컨테이너형 가상화란



- 컨테이너 : 애플리케이션과 그 실행에 필요한 라이브러리·설정을 묶어 **격리된 프로세스**로 실행한 것
- 하드웨어를 가상화하는 것이 아니라 **OS 수준**에서 프로세스의 실행 환경을 나눔

| 장점 | 단점 |
|---|---|
| 게스트 OS가 없어 가볍고 자원 소비가 적음 | 호스트와 **커널을 공유** → 다른 종류의 OS는 실행 불가 |
| 기동이 빠름 (초 단위) | 커널 취약점이 모든 컨테이너에 영향 — 격리 수준이 VM보다 낮음 |
| 한 서버에 더 많이 올릴 수 있음 (고밀도) | 컨테이너가 많아지면 관리가 복잡 → 오케스트레이션 필요 |
| 이미지로 묶여 어디서나 같은 환경 재현 (이식성) | 데이터 영속화·네트워크를 따로 설계해야 함 |

**가상 머신과 비교**

| 구분 | 가상 머신 | 컨테이너 |
|---|---|---|
| 가상화 대상 | 하드웨어 | OS (프로세스 실행 환경) |
| OS | VM마다 게스트 OS | 호스트 커널 공유 |
| 크기 | GB 단위 | MB 단위 |
| 기동 | 분 단위 | 초 단위 |
| 격리 | 강함 | 상대적으로 약함 |

**컨테이너를 만드는 리눅스 커널 기능**

| 기능 | 역할 |
|---|---|
| 네임스페이스 | 프로세스 ID, 네트워크, 파일 시스템 마운트, 호스트명 등을 컨테이너별로 **분리** → 서로 보이지 않음 |
| cgroups | 컨테이너가 쓸 CPU·메모리·디스크 I/O 양을 **제한** |
| 유니온 파일 시스템 | 여러 읽기 전용 계층을 겹쳐 하나의 파일 시스템으로 보이게 함 → 이미지 계층 공유 |

## 컨테이너형 가상화 소프트웨어의 대표: 도커

> Docker : 컨테이너를 만들고 배포하고 실행하는 플랫폼 — 2013년 공개 이후 컨테이너 기술의 사실상 표준

| 구성 요소 | 내용 |
|---|---|
| 이미지 | 컨테이너 실행에 필요한 파일·설정을 담은 **읽기 전용 템플릿** |
| 컨테이너 | 이미지를 실행한 **인스턴스** — 하나의 이미지로 여러 컨테이너 생성 |
| Dockerfile | 이미지를 만드는 절차를 적은 텍스트 파일 |
| 레지스트리 | 이미지를 저장·공유하는 저장소 (Docker Hub 등) |
| 도커 엔진 | 이미지 빌드와 컨테이너 실행을 담당하는 데몬 |

```
Dockerfile ──build──▶ 이미지 ──push/pull──▶ 레지스트리
                        │
                       run
                        ▼
                     컨테이너
```

<details><summary>macOS나 Windows에서도 도커로 리눅스 컨테이너가 실행되는 이유는?</summary>

컨테이너는 호스트 커널을 공유하므로 리눅스 컨테이너에는 리눅스 커널이 필요하다. <br>
Docker Desktop은 내부에 가벼운 리눅스 가상 머신을 띄우고 그 안에서 컨테이너를 실행한다. <br>
즉 사용자 눈에는 보이지 않지만 하이퍼바이저 위의 리눅스 VM이 호스트 역할을 한다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 컨테이너형 가상화는 호스트 OS의 커널을 공유하고 네임스페이스·cgroups로 애플리케이션 실행 환경만 격리하는 방식으로, 게스트 OS가 없어 가볍고 빠르며 이식성이 높지만 격리 수준은 VM보다 낮고, 이미지·컨테이너·Dockerfile·레지스트리로 구성된 도커가 대표적이다
