# 자동 빌드

> 소스 코드 변경을 계기로 **이미지 생성부터 배포까지의 절차를 자동화**하는 것

## 자동 빌드란

> 자동 빌드 : 소스 코드가 변경되면 컴파일·테스트·**컨테이너 이미지 생성**을 자동으로 수행하는 것

- **CI**(Continuous Integration, 지속적 통합)에 해당
- 코드를 저장소에 푸시(push)하는 것이 계기(트리거)

| 수동 빌드의 문제 | 자동 빌드의 효과 |
|---|---|
| 사람마다 절차·환경이 달라 결과가 다름 | 항상 같은 절차 → 결과가 일정 |
| 테스트를 빠뜨리기 쉬움 | 매번 테스트 실행 → 문제를 일찍 발견 |
| 반복 작업에 시간 소모 | 개발에 집중 |

---

## 자동 배포란

> 자동 배포 : 만들어진 이미지를 테스트·운영 환경에 자동으로 반영하는 것

- **CD**(Continuous Delivery / Deployment, 지속적 전달·배포)에 해당

| 구분 | 내용 |
|---|---|
| 지속적 전달 (Delivery) | 배포 가능한 상태까지 자동화 — 운영 반영은 사람이 **승인** |
| 지속적 배포 (Deployment) | 운영 환경 반영까지 **완전 자동** |

---

## 이미지 생성부터 배포까지의 절차

```
① 코드 수정·푸시 → ② 빌드·테스트 → ③ 이미지 생성 → ④ 레지스트리에 푸시
                         → ⑤ 매니페스트의 이미지 태그 변경 → ⑥ 클러스터에 적용
```

| 단계 | 내용 | 수동일 때의 명령 |
|---|---|---|
| 이미지 생성 | Dockerfile로 이미지 빌드 | `docker build -t web:1.1 .` |
| 이미지 등록 | 레지스트리에 업로드 | `docker push` |
| 매니페스트 변경 | 디플로이먼트의 이미지 태그를 새 버전으로 수정 | 파일 편집 |
| 적용 | 클러스터에 반영 | `kubectl apply -f` |

- 이미지 태그는 `latest`보다 **버전·커밋 해시** 사용 → 어떤 코드가 배포되었는지 추적 가능, 롤백 용이

## 새로운 파드로 변경하는 방법

| 방식 | 내용 | 특징 |
|---|---|---|
| 롤링 업데이트 | 기존 파드를 **조금씩** 새 파드로 교체 | 디플로이먼트의 기본값 — 무중단, 잠시 신·구 버전 공존 |
| 재생성 (Recreate) | 기존 파드를 **모두 정지**한 뒤 새 파드 기동 | 단순하지만 중단 발생 |
| 블루/그린 | 새 버전 환경을 통째로 준비한 뒤 **한 번에 전환** | 즉시 되돌리기 쉬움, 자원이 2배 필요 |
| 카나리 | **일부 요청만** 새 버전에 보내 검증 후 점차 확대 | 위험 최소화, 구성이 복잡 |

**롤링 업데이트의 조절 값**

| 설정 | 의미 |
|---|---|
| maxSurge | 교체 중 원하는 개수보다 **추가로** 만들 수 있는 파드 수 |
| maxUnavailable | 교체 중 **사용 불가**여도 되는 파드 수 |

- Readiness 프로브를 통과한 새 파드만 요청을 받음 → 준비 안 된 파드로 요청이 가지 않음

## 자동 빌드/배포를 지원하는 도구

| 도구 | 분류 | 특징 |
|---|---|---|
| Jenkins | CI/CD | 오래된 오픈 소스 — 플러그인이 풍부, 직접 서버 운영 |
| GitHub Actions | CI/CD | GitHub 저장소와 통합 — 워크플로를 YAML로 정의 |
| GitLab CI/CD | CI/CD | GitLab에 내장 |
| Skaffold | 개발 지원 | 구글 제공 — 코드 변경을 감지해 빌드·푸시·배포를 반복, 로컬 개발에 유용 |
| Argo CD | CD (GitOps) | Git 저장소의 매니페스트와 클러스터 상태를 **자동 동기화** |
| Flux | CD (GitOps) | Argo CD와 같은 GitOps 방식 |
| Tekton | CI/CD | 쿠버네티스 위에서 파이프라인을 객체로 정의 |

> GitOps : Git 저장소를 **유일한 정답**으로 삼아, 저장소의 매니페스트대로 클러스터가 맞춰지게 하는 운영 방식

<details><summary>GitOps에서는 왜 CI 도구가 kubectl apply를 직접 실행하지 않을까?</summary>

CI 도구가 직접 적용하면 클러스터 접속 권한을 외부 도구에 주어야 하고, 누군가 수동으로 바꾼 내용은 Git에 남지 않는다. <br>
GitOps에서는 CI가 Git의 매니페스트만 고치고, 클러스터 안의 Argo CD가 Git을 보고 스스로 끌어와 적용한다. <br>
변경 이력이 모두 Git에 남고, 되돌릴 때도 Git 커밋을 되돌리면 된다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 자동 빌드(CI)는 코드 변경 시 테스트와 이미지 생성을, 자동 배포(CD)는 레지스트리 등록 후 매니페스트 변경과 클러스터 적용을 자동화하며, 새 파드로의 교체는 롤링 업데이트·재생성·블루/그린·카나리 방식이 있고 Jenkins·GitHub Actions·Skaffold·Argo CD 등이 이를 지원한다
