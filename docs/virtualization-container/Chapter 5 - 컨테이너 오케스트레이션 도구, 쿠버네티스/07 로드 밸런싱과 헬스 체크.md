# 로드 밸런싱과 헬스 체크

> 요청을 나누고 이상을 감지해 교체함으로써 **시스템의 가용성을 향상**시키는 방법

## 로드 밸런싱과 헬스 체크란

| 구분 | 내용 |
|---|---|
| 로드 밸런싱 | 요청을 여러 파드에 **분산** → 부하 집중 방지 |
| 헬스 체크 | 파드가 정상인지 **주기적으로 확인** → 비정상이면 제외·재기동 |

- 둘은 함께 동작 : 헬스 체크로 정상 파드를 가려내고, 로드 밸런싱은 정상 파드에만 요청 전달

```
요청 ──▶ 로드 밸런서 ──▶ 파드 A (정상)
                   ├──▶ 파드 B (정상)
                   └──✕  파드 C (이상 → 제외 후 재기동)
```

---

## 가용성이란

> 가용성 : 시스템이 멈추지 않고 계속 서비스를 제공할 수 있는 정도

- 가동률 = 가동 시간 ÷ 전체 시간

| 가동률 | 연간 정지 허용 시간 |
|---|---|
| 99% | 약 3.65일 |
| 99.9% | 약 8.8시간 |
| 99.99% | 약 53분 |

- 가용성을 높이는 기본 : **다중화**(같은 것을 여러 개 준비) + **장애 감지 후 자동 전환**
- **단일 장애 지점**(SPOF) — 그것 하나가 멈추면 전체가 멈추는 부분 — 을 없애는 것이 목표

## 쿠버네티스의 로드 밸런싱

| 수단 | 계층 | 내용 |
|---|---|---|
| 서비스 (ClusterIP) | L4 | 클러스터 **내부** 통신을 파드들에 분산 |
| 서비스 (LoadBalancer) | L4 | 클라우드의 로드 밸런서로 **외부** 요청을 받아 분산 |
| 인그레스 (Ingress) | L7 | HTTP(S)의 **호스트명·URL 경로**에 따라 서비스로 분배, TLS 처리 |

- kube-proxy가 각 노드에서 서비스 IP → 파드 IP 전달 규칙(iptables/IPVS)을 관리
- 인그레스는 규칙일 뿐이며, 실제 처리는 **인그레스 컨트롤러**(NGINX 등)가 수행

```
/api  ──▶ api 서비스 ──▶ api 파드들
/     ──▶ web 서비스 ──▶ web 파드들      (인그레스 하나로 경로별 분배)
```

## 쿠버네티스의 헬스 체크

> 각 노드의 **kubelet**이 컨테이너를 **프로브**(probe)로 검사

| 프로브 | 확인하는 것 | 실패 시 조치 |
|---|---|---|
| Liveness Probe | 컨테이너가 **살아 있는가** (멈춤·교착 상태 여부) | 컨테이너 **재기동** |
| Readiness Probe | 요청을 **받을 준비가 되었는가** | 서비스의 엔드포인트에서 **제외** (재기동은 안 함) |
| Startup Probe | **기동이 끝났는가** | 성공할 때까지 다른 프로브 보류 — 기동이 느린 앱 보호 |

| 검사 방식 | 내용 |
|---|---|
| HTTP GET | 지정한 경로로 요청해 200~399 응답이면 정상 |
| TCP 소켓 | 지정한 포트에 연결되면 정상 |
| 명령 실행 (exec) | 컨테이너 안에서 명령을 실행해 종료 코드 0이면 정상 |

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10   # 기동 후 첫 검사까지 대기
  periodSeconds: 5          # 검사 간격
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
```

- 노드 자체가 멈춘 경우 : 마스터가 노드의 응답 없음을 감지 → 그 노드의 파드를 다른 노드에 다시 생성

<details><summary>Liveness와 Readiness를 왜 나눌까?</summary>

살아는 있지만 잠시 요청을 받을 수 없는 상태가 있기 때문이다. 기동 직후 데이터를 불러오는 중이거나 의존하는 DB에 일시적으로 연결되지 않는 경우다. <br>
이때 재기동하면 오히려 준비 시간이 길어지므로, Readiness 실패는 요청만 잠시 끊고 기다린다. <br>
반대로 교착 상태처럼 스스로 회복할 수 없는 경우는 Liveness가 감지해 재기동한다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 가용성은 시스템이 멈추지 않고 서비스를 제공하는 정도로 다중화와 장애 감지·자동 전환으로 높이며, 쿠버네티스는 서비스(L4)와 인그레스(L7)로 요청을 분산하고 kubelet의 Liveness·Readiness·Startup 프로브로 컨테이너를 검사해 재기동하거나 요청 대상에서 제외한다
