# 컨테이너 오케스트레이션

> 다수의 컨테이너를 자동으로 관리하고 운영하는 것 


---

## 로드 밸런싱

> 들어오는 요청을 여러 컨테이너에 할당해 부하를 분산하는 것

- 같은 역할의 컨테이너를 여러 개 띄우고 요청을 나누어 전달
- 한 컨테이너에 부하가 몰리는 것을 방지 → 응답 속도 유지
- 일부 컨테이너가 멈춰도 나머지가 처리 → 서비스 지속

---

## 헬스 체크

> 헬스 체크 : 컨테이너가 정상 동작 중인지 확인하는 것

- 컨테이너에 요청을 보내고 정상적으로 응답을 반환하는지 확인
- 이상이 발견된 컨테이너는 로드 밸런서가 요청 대상에서 제외

---

## 스케일링

> 스케일링 : 부하에 맞춰 컨테이너의 수나 성능을 조절하는 것

- 요청이 많은 시간에는 늘리고, 한가한 시간에는 줄여 리소스 소비 최적화
- 리소스 부족 때문에 시스템 다운되는 상황 방지

---

## 오케스트레이션의 중요성

- 관리 및 운영하는 컨테이너 수가 늘어날수록 대응하기가 어려워짐
- 장애 대응·확장·배포를 자동화해 가용성과 운영 효율을 모두 확보


<details><summary>현대 애플리케이션은 어느 정도 규모의 컨테이너로 운영되고 있을까? 도커만으로는 부족하고 쿠버네티스로 컨테이너를 관리할 정도가 되려면 규모가 어느 정도가 되어야 할까?</summary>

규모는 서비스마다 크게 다르다. 작은 서비스는 컨테이너 몇 개~수십 개로 충분하고, 마이크로서비스로 나눈 대형 서비스는 수천~수만 개를 운영한다. 구글은 주당 수십억 개의 컨테이너를 실행한다고 밝힌 바 있고, 쿠버네티스는 공식적으로 클러스터 하나에 노드 5,000대·파드 150,000개까지 지원한다. <br>
쿠버네티스가 필요해지는 기준은 컨테이너 개수보다 **서버(호스트)가 여러 대가 되는지**와 **사람 손으로 감당할 수 있는지**다. <br>
서버 한 대에 컨테이너 몇 개~십여 개라면 도커와 도커 컴포즈로 충분하다. 쿠버네티스 자체를 운영하는 부담이 오히려 더 크다. <br>
반대로 서버가 여러 대로 늘어 어느 서버에 무엇을 띄울지 정해야 하고, 장애 시 자동 복구, 트래픽에 따른 자동 스케일링, 무중단 배포가 필요해지면 수작업으로는 한계가 온다. 보통 서버 수 대 이상·컨테이너 수십 개 이상에 서비스 종류와 배포 횟수가 많아지는 시점이다. <br>
즉 "몇 개부터"라는 정해진 숫자는 없고, 수작업 운영 비용이 쿠버네티스 학습·운영 비용보다 커지는 때가 도입 시점이다. 그 중간 단계에서는 클라우드의 관리형 서비스(ECS, Cloud Run 등)를 쓰기도 한다.
