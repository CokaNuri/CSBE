# 컨테이너 오케스트레이션

> 여러 서버에 흩어진 다수의 컨테이너를 **자동으로 배치·감시·조정**하는 작업 — 컨테이너를 관리하기 위한 작업

## 오케스트레이션이란

> 오케스트레이션 : 여러 서버(노드)에서 동작하는 컨테이너의 배포·연결·확장·복구를 **자동화**하는 것

- 컨테이너가 몇 개뿐이면 도커 명령으로 직접 관리 가능
- 서버가 여러 대, 컨테이너가 수십~수천 개가 되면 사람이 관리하기 어려움 → 오케스트레이션 도구 필요

| 사람이 직접 할 때의 문제 | 오케스트레이션 도구가 하는 일 |
|---|---|
| 어느 서버에 컨테이너를 올릴지 일일이 판단 | 자원 여유를 보고 자동 배치 (스케줄링) |
| 컨테이너가 죽었는지 계속 감시 | 헬스 체크 후 자동 재기동 |
| 요청이 늘면 수동으로 컨테이너 추가 | 스케일링 |
| 컨테이너 주소가 바뀔 때마다 설정 변경 | 로드 밸런싱·서비스 디스커버리 |

**오케스트레이션의 주요 기능**

- 로드 밸런싱, 헬스 체크, 스케일링 — 이 세 가지가 핵심

---

## 로드 밸런싱

> 로드 밸런싱 : 들어오는 요청을 여러 컨테이너에 **분산**하는 것

- 같은 역할의 컨테이너를 여러 개 띄우고 요청을 나누어 전달
- 한 컨테이너에 부하가 몰리는 것을 방지 → 응답 속도 유지
- 일부 컨테이너가 멈춰도 나머지가 처리 → 서비스 지속

```
            ┌──▶ 컨테이너 A
요청 ──▶ 로드 밸런서 ──▶ 컨테이너 B
            └──▶ 컨테이너 C
```

---

## 헬스 체크

> 헬스 체크 : 컨테이너가 **정상 동작 중인지** 주기적으로 확인하는 것

- 이상이 발견된 컨테이너는 요청 대상에서 제외하고 새 컨테이너로 교체
- 사람이 개입하지 않아도 정해 둔 개수가 유지됨 → **자동 복구(셀프 힐링)**

| 단계 | 내용 |
|---|---|
| 감시 | 정해진 간격으로 컨테이너 상태 확인 |
| 판정 | 응답이 없거나 오류가 반복되면 비정상으로 판단 |
| 조치 | 비정상 컨테이너 정지 → 새 컨테이너 기동 |

---

## 스케일링

> 스케일링 : 부하에 맞춰 컨테이너(또는 서버)의 **수나 성능을 조절**하는 것

| 구분 | 내용 |
|---|---|
| 스케일 아웃 | 컨테이너 수를 늘림 |
| 스케일 인 | 컨테이너 수를 줄임 |
| 스케일 업 / 다운 | 컨테이너 하나에 할당하는 CPU·메모리를 늘림 / 줄임 |

- 요청이 많은 시간에는 늘리고, 한가한 시간에는 줄여 **성능과 비용**을 함께 관리
- 컨테이너는 기동이 빨라 스케일 아웃과 궁합이 좋음

---

## 오케스트레이션의 중요성

- 마이크로서비스처럼 서비스가 잘게 나뉠수록 컨테이너 수가 급증 → 수동 운영은 한계
- 장애 대응·확장·배포를 자동화해야 **가용성**과 **운영 효율**을 모두 확보

| 대표 도구 | 특징 |
|---|---|
| 쿠버네티스 | 사실상 표준 — 기능이 풍부하고 생태계가 큼 |
| 도커 스웜 | 도커에 내장 — 단순하고 배우기 쉬움 |
| Amazon ECS | AWS 고유의 오케스트레이션 서비스 |

<details><summary>도커만으로는 왜 부족할까?</summary>

도커는 한 대의 서버에서 컨테이너를 만들고 실행하는 데 초점이 맞춰져 있다. <br>
여러 서버에 걸쳐 어디에 배치할지, 죽은 컨테이너를 어떻게 되살릴지, 요청을 어떻게 나눌지는 도커 엔진만으로는 해결되지 않는다. <br>
그래서 도커(컨테이너 실행) 위에 오케스트레이션 도구(컨테이너 운영 자동화)를 함께 쓰는 구성이 일반적이다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 컨테이너 오케스트레이션은 여러 서버에 걸친 다수 컨테이너의 배치·연결·복구·확장을 자동화하는 작업으로, 요청을 분산하는 로드 밸런싱, 이상을 감지해 교체하는 헬스 체크, 부하에 맞춰 수와 성능을 조절하는 스케일링이 핵심 기능이며 컨테이너 수가 늘어날수록 필수가 된다
