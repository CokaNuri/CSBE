# 네임스페이스

> 작업 공간을 분리하는 방법 — 네임스페이스로 "보이는 범위"를 나누고, 컨트롤 그룹으로 "쓸 수 있는 양"을 제한

## 네임스페이스란

> 네임스페이스(namespace) : 프로세스가 볼 수 있는 시스템 자원의 범위를 나누어, 프로세스마다 **독립된 공간**을 가진 것처럼 보이게 하는 리눅스 커널 기능

- 같은 네임스페이스에 속한 프로세스끼리만 서로의 자원이 보임
- 다른 네임스페이스의 프로세스·네트워크·파일은 **존재하지 않는 것처럼** 보임
- 하드웨어를 가상화하지 않고도 격리된 환경을 만들 수 있는 이유

---

## 네임스페이스와 컨테이너

- 컨테이너 = 네임스페이스로 격리된 프로세스 (+ 컨트롤 그룹으로 자원 제한)
- 도커는 컨테이너를 만들 때마다 그 컨테이너 전용 네임스페이스 묶음을 생성

```
호스트 (커널 1개)
 ├─ 컨테이너 A : [PID NS] [NET NS] [MNT NS] [UTS NS] ...  → PID 1 = nginx
 └─ 컨테이너 B : [PID NS] [NET NS] [MNT NS] [UTS NS] ...  → PID 1 = mysqld
```

- 컨테이너 A 안에서 `ps`를 실행하면 A의 프로세스만 보이고 PID도 1부터 시작
- 호스트에서 보면 A와 B의 프로세스 모두 일반 프로세스로 보임 (다른 PID)

---

## 네임스페이스에 의해 격리된 리소스

| 네임스페이스 | 격리 대상 | 효과 |
|---|---|---|
| PID | 프로세스 ID | 컨테이너별로 독립된 프로세스 번호 체계 |
| Network (NET) | 네트워크 인터페이스, IP 주소, 포트, 라우팅 테이블 | 컨테이너마다 독자 IP, 같은 포트 번호 사용 가능 |
| Mount (MNT) | 파일 시스템의 마운트 지점 | 컨테이너별로 독립된 디렉터리 구조 |
| UTS | 호스트명, 도메인명 | 컨테이너별 호스트명 |
| IPC | 프로세스 간 통신 자원 (공유 메모리, 세마포어, 메시지 큐) | 다른 컨테이너의 IPC에 접근 불가 |
| User | 사용자 ID, 그룹 ID | 컨테이너 안의 root를 호스트의 일반 사용자로 대응 |
| Cgroup | 컨트롤 그룹의 계층 정보 | 컨테이너에서 호스트의 cgroup 구조가 보이지 않음 |

---

## 컨트롤 그룹이란

> 컨트롤 그룹(cgroups, control groups) : 프로세스를 그룹으로 묶어 그 그룹이 사용할 수 있는 **자원의 양을 제한·감시**하는 리눅스 커널 기능

| 구분 | 네임스페이스 | 컨트롤 그룹 |
|---|---|---|
| 역할 | 무엇이 **보이는지** 격리 | 얼마나 **쓸 수 있는지** 제한 |
| 없으면 | 다른 컨테이너의 프로세스·파일이 보임 | 한 컨테이너가 호스트의 자원을 독점 |

| 제어 대상 | 내용 |
|---|---|
| CPU | 사용 시간의 비율·상한 |
| 메모리 | 사용량 상한 — 넘으면 프로세스 강제 종료(OOM Kill) |
| 블록 I/O | 디스크 읽기·쓰기 속도 |
| PID 수 | 생성할 수 있는 프로세스 수 |
| 장치 | 접근 가능한 장치 |

```bash
docker run -d --cpus=1.5 --memory=512m nginx    # CPU 1.5개, 메모리 512MB로 제한
```

---

## 컨트롤 그룹의 계층 구조

- 컨트롤 그룹은 **트리(계층) 구조**로 구성, 가상 파일 시스템(`/sys/fs/cgroup`)을 통해 조작
- 하위 그룹은 상위 그룹의 제한을 **상속**하며, 상위 그룹의 한도를 넘을 수 없음

```
/sys/fs/cgroup            (루트 — 시스템 전체)
 ├─ system.slice          (시스템 서비스)
 │   └─ docker-<컨테이너 A ID>.scope   메모리 512MB
 │   └─ docker-<컨테이너 B ID>.scope   메모리 1GB
 └─ user.slice            (사용자 세션)
```

| 구분 | cgroup v1 | cgroup v2 |
|---|---|---|
| 구조 | 자원 종류(CPU, 메모리 등)별로 계층이 따로 존재 | **단일 계층**으로 통합 |
| 관리 | 복잡 | 단순하고 일관됨 |
| 채택 | 과거 기본값 | 최근 리눅스 배포판의 기본값 |

<details><summary>네임스페이스만 있고 컨트롤 그룹이 없다면 어떤 문제가 생길까?</summary>

네임스페이스는 보이는 범위만 나눌 뿐 사용량은 제한하지 않는다. <br>
한 컨테이너에서 메모리 누수나 무한 루프가 발생하면 호스트의 CPU·메모리를 모두 차지해 같은 호스트의 다른 컨테이너까지 느려지거나 멈춘다. <br>
컨트롤 그룹으로 컨테이너별 상한을 정해 두면 문제의 영향을 그 컨테이너 안으로 한정할 수 있다.
</details>

## 🔑 최종 정리

> 한 줄 요약: 네임스페이스는 PID·네트워크·마운트·UTS·IPC·사용자 등 프로세스가 볼 수 있는 범위를 컨테이너별로 분리하는 커널 기능이고, 컨트롤 그룹은 계층 구조로 프로세스 그룹의 CPU·메모리·I/O 사용량을 제한하는 커널 기능으로, 이 둘이 결합되어 컨테이너의 격리된 실행 환경을 만든다
