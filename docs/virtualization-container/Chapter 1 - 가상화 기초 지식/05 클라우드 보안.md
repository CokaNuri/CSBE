# 클라우드 보안

> 클라우드는 사업자가 높은 수준의 보안을 제공해 안전성이 높지만, **자원 공유**와 **설정 실수**라는 클라우드만의 리스크가 있다

## 클라우드 보안

- 사업자는 전문 인력·물리 보안·인증(ISO 27001 등)을 갖춤 → 개별 기업이 직접 운영하는 것보다 안전한 경우가 많음
- 그러나 보안 책임이 모두 사업자에게 있는 것은 아님 → **책임 공유 모델**

| 서비스 모델 | 사업자 책임 | 이용자 책임 |
|---|---|---|
| IaaS | 시설, 하드웨어, 가상화 계층 | OS, 미들웨어, 애플리케이션, 데이터, 접근 권한 |
| PaaS | + OS, 실행 환경 | 애플리케이션, 데이터, 접근 권한 |
| SaaS | + 애플리케이션 | 데이터, 계정·접근 권한 |

**클라우드만의 리스크**

| 리스크 | 내용 |
|---|---|
| 멀티 테넌트 | 다른 이용자와 물리 자원 공유 — 격리가 깨지면 영향 |
| 설정 실수 | 스토리지 공개 설정, 과도한 권한, 열린 포트 → 정보 유출 |
| 계정 탈취 | 관리 콘솔·API 키가 유출되면 전체 자원이 노출 |
| 사업자 의존 | 사업자 장애·정책 변경의 영향, 데이터 저장 위치(국가) 문제 |

## 실제로 발생한 취약성의 예

| 사례 | 내용 |
|---|---|
| VENOM (2015) | 가상 플로피 드라이브 코드의 결함으로 게스트 OS에서 **호스트로 탈출** 가능 (VM 이스케이프) |
| Meltdown / Spectre (2018) | CPU의 예측 실행을 악용해 다른 프로세스·가상 서버의 **메모리를 훔쳐봄** — 하드웨어 수준 취약점 |
| runC 취약점 (2019) | 컨테이너 안에서 호스트의 런타임 실행 파일을 덮어써 **호스트 권한 획득** (컨테이너 탈출) |
| 스토리지 공개 설정 실수 | 클라우드 스토리지를 외부 공개로 두어 대량의 개인 정보 유출 — 가장 흔한 사고 유형 |

- 앞의 세 가지는 가상화의 전제인 **격리**가 깨지는 유형, 마지막은 이용자 측 **설정 실수** 유형

<details><summary>Meltdown·Spectre가 클라우드에서 특히 심각했던 이유는?</summary>

클라우드에서는 서로 모르는 이용자의 가상 서버가 같은 물리 CPU를 공유한다. <br>
CPU 자체의 결함이라 가상화 소프트웨어가 아무리 격리해도 다른 가상 서버의 메모리를 읽을 가능성이 생겼고, <br>
사업자는 전 서버에 패치를 적용해야 했으며 그 과정에서 성능 저하도 발생했다.
</details>

## 편의성과 보안 문제의 절충

- 보안을 강화할수록 절차가 늘어 불편해지고, 편의성만 추구하면 위험이 커짐 → **지킬 대상의 중요도에 맞춰** 균형

| 대책 | 내용 |
|---|---|
| 최소 권한 원칙 | 사용자·서비스에 필요한 권한만 부여 (IAM) |
| 다요소 인증 (MFA) | 비밀번호 유출만으로는 로그인 불가 |
| 암호화 | 저장 데이터·통신 구간 모두 암호화 |
| 네트워크 분리 | 공개 영역과 내부 영역 분리, 필요한 포트만 허용 |
| 로그·감시 | 조작 이력 기록, 이상 징후 탐지 |
| 설정 점검 자동화 | 공개 설정·과도한 권한을 도구로 상시 검사 |
| 제로 트러스트 | 내부 네트워크도 신뢰하지 않고 매 접근마다 검증 |

## 🔑 최종 정리

> 한 줄 요약: 클라우드는 사업자의 전문적인 보안으로 안전성이 높지만 책임 공유 모델에 따라 OS·데이터·권한 설정은 이용자 책임이며, VM·컨테이너 탈출이나 CPU 취약점처럼 격리가 깨지는 위험과 설정 실수로 인한 유출이 클라우드 특유의 리스크이므로, 최소 권한·MFA·암호화·감시로 편의성과 보안의 균형을 잡아야 한다
