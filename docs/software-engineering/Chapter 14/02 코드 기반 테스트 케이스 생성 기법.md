# 코드 기반 테스트 케이스 생성 기법

> 소스 코드의 내부 구조를 보고 테스트 케이스를 만드는 방법

> 화이트박스 테스트에 해당

## 제어 흐름 그래프

> 소스 코드를 입력하여 코드 실행 시작부터 종료까지의 흐름을 플로우차트로 표현한 것

- 노드 : 하나의 문장 또는 연속 실행되는 문장 블록
- 간선 : 실행이 이동하는 방향
- 분기문은 노드에서 두 개의 간선이 뻗어 나감

### 예시 코드

```java
public int discount(int amount, boolean isMember, int point) {
1:    int rate = 0;
2:    if (isMember || point >= 1000) {
3:        rate = 10;
      }
4:    if (amount >= 50000) {
5:        rate = rate + 5;
      }
6:    return amount * rate / 100;
}
```

### 제어 흐름 그래프

```
        (1) rate = 0
             |
        (2) isMember || point >= 1000 ?
           /                    \
      참  /                      \  거짓
    (3) rate = 10                 |
           \                     /
            \                   /
        (4) amount >= 50000 ?
           /                    \
      참  /                      \  거짓
    (5) rate = rate + 5            |
           \                     /
            \                   /
        (6) return amount * rate / 100
```

| 경로 | 거치는 노드 | 조건 |
|---|---|---|
| 경로 1 | 1 → 2 → 3 → 4 → 5 → 6 | 회원이거나 포인트 충족 + 5만원 이상 |
| 경로 2 | 1 → 2 → 3 → 4 → 6 | 회원이거나 포인트 충족 + 5만원 미만 |
| 경로 3 | 1 → 2 → 4 → 5 → 6 | 비회원 + 5만원 이상 |
| 경로 4 | 1 → 2 → 4 → 6 | 비회원 + 5만원 미만 |

<details><summary>모든 경로를 다 테스트하면 안 되는가?</summary>

분기가 늘어날수록 경로 수가 지수적으로 증가함 <br>
분기 10개면 최대 1024개 경로가 되고, 반복문이 섞이면 경로가 무한해짐 <br>
그래서 전체 경로 대신 문장, 분기, 조건 같은 기준으로 커버리지를 정해 일부 경로만 선택함
</details>

## 경로 기반 테스트 케이스 생성

> 테스트 커버리지 : 테스트 케이스가 전체 코드를 어느 정도 커버하는가

> 문장과 제어 흐름을 모두 거쳐 가는가

> 제어 흐름 그래프의 경로를 기반으로 테스트 케이스 생성

### 문장 커버리지

> 코드를 구성하는 모든 문장을 최소한 한 번씩 거쳐 가도록 경로 선택

| 테스트 케이스 | 입력 | 거치는 경로 |
|---|---|---|
| TC1 | amount=50000, isMember=true, point=0 | 1 → 2 → 3 → 4 → 5 → 6 |

- 한 개의 테스트 케이스로 모든 문장 실행 가능

<details><summary>문장 커버리지만으로 충분하지 않은 이유는?</summary>

모든 문장을 실행해도 조건이 거짓인 경로는 한 번도 지나가지 않을 수 있음 <br>
위 예시에서 TC1 하나로 모든 문장을 실행했지만, 비회원이거나 5만원 미만인 경우는 검증되지 않음 <br>
if만 있고 else가 없는 코드에서 특히 취약함 <br>
커버리지 기준 중 가장 약한 기준임
</details>

### 분기 커버리지

> 모든 분기를 적어도 한 번씩은 거쳐 가도록 경로 선택

| 테스트 케이스 | 입력 | 2번 분기 | 4번 분기 |
|---|---|---|---|
| TC1 | amount=50000, isMember=true, point=0 | 참 | 참 |
| TC2 | amount=10000, isMember=false, point=0 | 거짓 | 거짓 |

- 문장 커버리지를 항상 포함함
- 결정 커버리지라고도 부름

<details><summary>분기 커버리지와 문장 커버리지의 관계는?</summary>

분기 커버리지를 만족하면 문장 커버리지는 자동으로 만족됨 <br>
모든 분기를 거치려면 그 안의 문장도 반드시 실행되기 때문임 <br>
반대는 성립하지 않으므로 분기 커버리지가 더 강한 기준임
</details>

### 조건 커버리지

> 조건문에 대하여 모든 가능한 결과가 적어도 한 번씩은 나타날 수 있도록 테스트 케이스를 준비하는 방법

- 결정문 전체가 아니라 그 안의 개별 조건식 각각을 참·거짓으로 만듦

| 테스트 케이스 | isMember | point >= 1000 | 결정 결과 |
|---|---|---|---|
| TC1 | 참 | 거짓 | 참 |
| TC2 | 거짓 | 참 | 참 |

- 개별 조건은 모두 참·거짓을 가졌지만 결정 결과는 둘 다 참
- → 분기 커버리지는 만족하지 못함

<details><summary>조건 커버리지가 분기 커버리지를 보장하지 못하는 이유는?</summary>

개별 조건의 참·거짓만 챙기고 결정문 전체의 결과는 따지지 않기 때문임 <br>
or 조건에서 한쪽만 참이면 결정은 항상 참이 되어 거짓 분기를 한 번도 타지 않을 수 있음 <br>
그래서 조건 커버리지와 분기 커버리지는 포함 관계가 아니라 서로 다른 기준임
</details>

<details><summary>or 연산 뒤쪽 조건은 왜 주의해야 하는가?</summary>

자바를 비롯한 대부분의 언어는 단축 평가를 사용함 <br>
`isMember || point >= 1000`에서 isMember가 참이면 뒤쪽 조건은 아예 평가되지 않음 <br>
따라서 뒤쪽 조건을 참·거짓으로 만들려면 앞쪽 조건을 반드시 거짓으로 두어야 함 <br>
and 연산은 반대로 앞쪽 조건이 거짓이면 뒤쪽이 평가되지 않음
</details>

### 다수 조건 커버리지

> 조건 커버리지와 분기 커버리지를 동시에 만족하는 테스트 케이스를 생성하기 위한 방법

> 조건 커버리지에서 고려하는 테스트 케이스 조합의 수를 줄이면서 개별 조건식에 대한 테스트를 수행할 수 있도록 고안된 기법

| 테스트 케이스 | isMember | point >= 1000 | 결정 결과 |
|---|---|---|---|
| TC1 | 참 | 참 | 참 |
| TC2 | 거짓 | 거짓 | 거짓 |

- 개별 조건이 각각 참·거짓을 모두 가짐 → 조건 커버리지 만족
- 결정 결과도 참·거짓을 모두 가짐 → 분기 커버리지 만족

<details><summary>조합을 줄인다는 말의 의미는?</summary>

조건이 n개면 가능한 조합은 2의 n제곱 개가 됨 <br>
조건 3개면 8개, 4개면 16개로 급격히 늘어나 현실적으로 전부 시도하기 어려움 <br>
그래서 결정 결과에 실제로 영향을 주는 조합만 골라 케이스 수를 조건 개수에 비례하는 수준으로 줄임 <br>
항공·의료처럼 안전이 중요한 분야에서 요구되는 기준임
</details>

### 데이터 흐름 커버리지

> 변수 선언과 변수 사용에 의존하여 테스트 데이터를 선정하는 방법

- 정의 : 변수에 값이 할당되는 지점
- 사용 : 변수의 값을 읽는 지점
- 정의된 값이 사용되는 지점까지의 경로를 커버하도록 테스트 케이스 선정

| 변수 | 정의 지점 | 사용 지점 |
|---|---|---|
| rate | 1, 3, 5 | 5, 6 |

- 1에서 정의된 rate가 3을 거치지 않고 6에서 사용되는 경로도 검증해야 함

<details><summary>데이터 흐름 커버리지가 잡아내는 결함은?</summary>

값을 할당하지 않고 사용하는 미초기화 변수 결함 <br>
할당했지만 한 번도 쓰이지 않는 불필요한 코드 <br>
이전 값이 사용되기 전에 덮어써지는 논리 오류 <br>
제어 흐름만 보는 기준으로는 놓치기 쉬운 변수 관련 결함을 찾음
</details>

## 커버리지 기준 비교

| 커버리지 | 기준 | 강도 | 예시 케이스 수 |
|---|---|---|---|
| 문장 | 모든 문장을 한 번 이상 실행 | 약함 | 1 |
| 분기 | 모든 분기의 참·거짓을 한 번 이상 | 중간 | 2 |
| 조건 | 개별 조건식의 참·거짓을 한 번 이상 | 중간 | 2 |
| 다수 조건 | 조건 + 분기를 동시에 만족 | 강함 | 2 |
| 데이터 흐름 | 변수의 정의-사용 경로를 커버 | 강함 | 경로에 따라 다름 |

<details><summary>커버리지 100퍼센트면 결함이 없다고 볼 수 있는가?</summary>

아님 <br>
커버리지는 작성한 코드를 얼마나 실행했는지를 재는 것이지 정확성을 재는 것이 아님 <br>
아예 빠뜨린 요구사항이나 누락된 예외 처리는 실행할 코드 자체가 없으므로 커버리지에 잡히지 않음 <br>
커버리지는 테스트가 부족한 곳을 찾는 도구이지 품질의 보증서가 아님
</details>

## 🔑 최종 정리

코드 기반 테스트는 소스 코드의 내부 구조를 보고 테스트 케이스를 만드는 **화이트박스** 접근이다.
→ 먼저 코드를 **제어 흐름 그래프**로 바꿔 실행 흐름을 노드와 간선으로 표현한다.
→ 이때 모든 경로를 다 검사하는 것은 분기 수에 따라 경로가 지수적으로 늘어나 불가능하므로, **커버리지**라는 기준을 세워 일부 경로만 고른다.
→ 가장 약한 기준은 **문장 커버리지**로, 모든 문장을 실행하지만 거짓 분기를 건너뛸 수 있다.
→ **분기 커버리지**는 각 분기의 참·거짓을 모두 거치므로 문장 커버리지를 포함하지만, 결정문 안의 개별 조건까지는 보지 않는다.
→ **조건 커버리지**는 개별 조건식을 참·거짓으로 만들지만, or 조건 때문에 결정 결과가 한쪽으로만 나올 수 있어 분기 커버리지를 보장하지 못한다.
→ 그래서 둘을 동시에 만족시키되 조합 수는 줄인 **다수 조건 커버리지**가 필요하다.
→ 제어 흐름과 별개로, 변수의 정의와 사용 관계를 따라가는 **데이터 흐름 커버리지**는 미초기화나 불필요한 할당 같은 변수 결함을 잡는다.
→ 다만 커버리지가 100퍼센트여도 누락된 요구사항은 드러나지 않으므로, 커버리지는 품질의 보증이 아니라 테스트가 부족한 지점을 찾는 지표로 써야 한다.

> 한 줄 요약: 코드 기반 테스트는 제어 흐름 그래프 위에서 어떤 커버리지 기준을 택하느냐로 테스트 케이스를 정하며, 기준이 강해질수록 잡아내는 결함은 늘지만 케이스 수와 비용도 함께 늘어난다.
