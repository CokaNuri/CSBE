# 오류 기반 테스트

> 개발자의 실수가 잠재적으로 내재되었는지를 평가하기 위한 목적

> 코드에 결함을 일부러 심어 놓고, 테스트 케이스가 그 결함을 잡아내는지를 확인

## 뮤턴트 커버리지

> 실수하기 쉬운 부분에 결함을 주입하여 뮤턴트 코드를 생성하는 것

- 원본 코드에 작은 변형을 가한 복사본이 뮤턴트
- 변형을 만드는 규칙을 뮤턴트 연산자라 함

### 뮤턴트 연산자

| 연산자 | 변형 방식 | 원본 → 뮤턴트 |
|---|---|---|
| 논리 연산자 대체 | and, or 등을 서로 바꿈 | `isMember \|\| hasCoupon` → `isMember && hasCoupon` |
| 관계 연산자 대체 | 비교 연산자를 서로 바꿈 | `amount >= 50000` → `amount > 50000` |
| 산술 연산자 대체 | 사칙 연산자를 서로 바꿈 | `total = price + fee` → `total = price - fee` |
| 단항 연산자 삽입 | 부호나 부정 연산자를 끼워 넣음 | `if (isValid)` → `if (!isValid)` |
| 배열 참조 대체 | 인덱스나 배열 참조를 바꿈 | `items[i]` → `items[i + 1]` |
| 문장 삭제 | 한 문장을 통째로 제거 | `rate = 10;` → (삭제) |

### 뮤턴트 테스트 절차

1. 원본 코드에 뮤턴트 연산자를 적용해 여러 뮤턴트 코드 생성
2. 기존 테스트 케이스로 원본과 뮤턴트를 각각 실행
3. 실행 결과를 비교
4. 결과가 다르면 뮤턴트가 죽은 것 → 테스트 케이스가 결함을 잡아냄
5. 결과가 같으면 뮤턴트가 살아남은 것 → 테스트 케이스가 그 결함을 놓침
6. 살아남은 뮤턴트를 죽일 수 있도록 테스트 케이스를 보강

```java
// 원본
if (amount >= 50000) {
    rate = 10;
}

// 뮤턴트 (관계 연산자 대체)
if (amount > 50000) {
    rate = 10;
}
```

- amount=50000인 테스트 케이스가 있으면 두 코드의 결과가 달라져 뮤턴트가 죽음
- 경계값 케이스가 없으면 뮤턴트가 살아남아 테스트 케이스의 허점이 드러남

<details><summary>뮤턴트가 살아남으면 무엇을 알 수 있는가?</summary>

원본 코드에 결함이 있다는 뜻이 아니라 테스트 케이스가 불충분하다는 뜻임 <br>
그 결함이 심어져도 테스트가 통과했으므로, 같은 종류의 진짜 결함도 못 잡는다는 의미임 <br>
따라서 살아남은 뮤턴트를 죽일 수 있는 입력을 찾아 테스트 케이스로 추가해야 함 <br>
즉 오류 기반 테스트는 코드가 아니라 테스트의 품질을 평가하는 기법임
</details>

<details><summary>뮤턴트 점수는 어떻게 계산하는가?</summary>

죽인 뮤턴트 수를 전체 뮤턴트 수로 나눈 비율 <br>
동치 뮤턴트는 죽일 수 없으므로 분모에서 제외함 <br>
점수가 높을수록 테스트 케이스가 결함을 잘 잡아낸다는 의미임 <br>
커버리지가 코드를 얼마나 실행했는지를 잰다면, 뮤턴트 점수는 실행한 결과를 얼마나 제대로 검증했는지를 잼
</details>

<details><summary>동치 뮤턴트란?</summary>

코드는 변형되었지만 동작이 원본과 완전히 같은 뮤턴트 <br>
예를 들어 절대 도달하지 않는 코드나 결과에 영향을 주지 않는 변수를 바꾼 경우임 <br>
어떤 입력을 넣어도 결과가 같으므로 원리적으로 죽일 수 없음 <br>
동치 여부를 자동으로 판정하는 것이 불가능해 뮤턴트 테스트의 대표적 난점으로 꼽힘
</details>

<details><summary>뮤턴트 테스트의 비용 문제는?</summary>

뮤턴트 하나마다 프로그램을 다시 실행해야 하므로 실행 횟수가 뮤턴트 수만큼 늘어남 <br>
코드가 크면 뮤턴트가 수천 개 생성되어 시간이 크게 소요됨 <br>
그래서 변경된 부분만 대상으로 삼거나 일부 뮤턴트만 표본으로 뽑아 실행하는 방식을 씀
</details>

<details><summary>커버리지 기반 테스트와 무엇이 다른가?</summary>

커버리지는 코드를 얼마나 실행했는지만 보므로 결과를 검증하지 않아도 수치가 올라감 <br>
단언문 없이 메서드만 호출해도 커버리지 100퍼센트가 나올 수 있음 <br>
뮤턴트 테스트는 결과가 달라졌을 때 테스트가 실패하는지를 보므로 검증의 실질을 확인함 <br>
커버리지의 빈틈을 메우는 보완적 기법임
</details>
