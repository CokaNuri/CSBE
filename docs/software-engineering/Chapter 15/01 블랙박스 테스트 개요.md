# 블랙박스 테스트 개요

> 소스 코드 정보 없이 요구사항 명세만 이용하여 테스트 케이스를 생성하는 기법

> 기능적 테스트라고도 부름

- 내부 구조를 보지 않고 입력과 출력의 관계만으로 판단
- 요구사항 명세가 유일한 기준이 되므로 명세의 품질이 테스트 품질을 좌우

| 구분 | 블랙박스 테스트 | 화이트박스 테스트 |
|---|---|---|
| 기준 | 요구사항 명세 | 소스 코드 구조 |
| 관점 | 무엇을 하는가 | 어떻게 동작하는가 |
| 찾는 결함 | 기능 누락, 잘못된 기능 | 논리 오류, 미실행 코드 |
| 수행 시점 | 주로 통합·시스템·인수 테스트 | 주로 단위 테스트 |

<details><summary>블랙박스 테스트만으로 충분하지 않은 이유는?</summary>

명세에 적히지 않은 내부 분기나 예외 처리 경로는 아예 대상이 되지 않음 <br>
같은 출력을 내더라도 내부에서 잘못된 경로를 타는 경우를 잡을 수 없음 <br>
반대로 화이트박스 테스트는 명세에 있으나 구현되지 않은 기능을 찾지 못함 <br>
두 기법은 서로 다른 결함을 잡으므로 함께 사용해야 함
</details>

## 테스트 케이스 선정 휴리스틱

> 전수 테스트가 불가능하므로 대표성 있는 입력을 고르는 경험적 기준이 필요

### 동치 분할

> 같은 결과가 나올 것으로 기대되는 입력들을 하나의 그룹으로 묶고, 각 그룹에서 대표값 하나만 테스트

- 유효 동치 클래스와 무효 동치 클래스로 나눔
- 한 그룹의 값이 통과하면 그 그룹의 다른 값도 통과할 것으로 가정

**예시 : 회원 가입 나이 입력 (14세 이상 100세 이하 허용)**

| 동치 클래스 | 범위 | 대표값 | 기대 결과 |
|---|---|---|---|
| 무효 (미달) | 14 미만 | 10 | 가입 거부 |
| 유효 | 14 ~ 100 | 30 | 가입 승인 |
| 무효 (초과) | 100 초과 | 120 | 가입 거부 |
| 무효 (형식) | 숫자 아님 | "abc" | 입력 오류 |

<details><summary>동치 분할의 가정이 위험한 경우는?</summary>

같은 그룹 안에서도 내부적으로 다르게 처리되는 값이 있으면 대표값 하나로는 놓침 <br>
예를 들어 유효 범위 안이지만 특정 값에서만 별도 로직이 도는 경우임 <br>
그래서 동치 분할은 단독으로 쓰기보다 경계치 분석과 함께 사용함
</details>

### 경계치 커버리지 분석

> 동치 클래스의 경계와 그 주변 값을 테스트 케이스로 선정

- 결함은 범위의 한가운데가 아니라 경계에서 발생하는 경우가 많음
- 경계값, 경계값 −1, 경계값 +1을 함께 확인

**예시 : 나이 14세 이상 100세 이하**

| 값 | 위치 | 기대 결과 |
|---|---|---|
| 13 | 하한 경계 −1 | 거부 |
| 14 | 하한 경계 | 승인 |
| 15 | 하한 경계 +1 | 승인 |
| 99 | 상한 경계 −1 | 승인 |
| 100 | 상한 경계 | 승인 |
| 101 | 상한 경계 +1 | 거부 |

<details><summary>경계에서 결함이 자주 나는 이유는?</summary>

이상과 초과, 이하와 미만을 혼동해 비교 연산자를 잘못 쓰는 실수가 잦음 <br>
반복문의 종료 조건에서 한 번 더 돌거나 덜 도는 오류도 경계에서 나타남 <br>
배열 인덱스의 시작이 0인지 1인지 착각하는 것도 같은 유형임 <br>
코드를 보지 않아도 이런 실수를 겨냥할 수 있어 효율이 높은 기법임
</details>

### 특수치 커버리지 분석

> 결함을 유발하기 쉬운 특별한 값을 테스트 케이스로 선정

| 유형 | 예시 값 |
|---|---|
| 빈 값 | null, 빈 문자열, 빈 리스트 |
| 0과 부호 | 0, 음수 |
| 극단값 | 자료형 최대값, 최소값 |
| 형식 위반 | 공백만 있는 문자열, 특수문자, 매우 긴 문자열 |

**예시 : 장바구니 주문 금액 계산**

- 상품이 0개일 때
- 수량이 음수로 들어올 때
- 금액 합이 int 최대값을 넘을 때

<details><summary>특수치 분석이 경계치 분석과 다른 점은?</summary>

경계치는 명세에 정의된 범위의 끝을 다룸 <br>
특수치는 명세에 명시되지 않았더라도 프로그램이 취약한 값을 다룸 <br>
null이나 빈 문자열처럼 명세에는 언급이 없지만 실제로 자주 터지는 입력이 대상임 <br>
테스터의 경험에 크게 의존하는 기법임
</details>

### 원인/효과 커버리지

> 입력 조건을 원인, 출력 결과를 효과로 두고 그 조합을 의사결정 테이블로 정리하여 테스트 케이스 도출

- 여러 조건이 조합되어 결과가 결정되는 기능에 적합
- 조합을 표로 만들어 누락된 경우를 눈으로 확인 가능

**예시 : 주문 배송비 정책**

- 원인 1 : 회원인가
- 원인 2 : 주문 금액이 3만원 이상인가
- 효과 : 배송비 무료 여부

| 케이스 | 회원 여부 | 3만원 이상 | 배송비 |
|---|---|---|---|
| TC1 | 예 | 예 | 무료 |
| TC2 | 예 | 아니오 | 무료 |
| TC3 | 아니오 | 예 | 무료 |
| TC4 | 아니오 | 아니오 | 3000원 |

<details><summary>의사결정 테이블의 장점은?</summary>

조건 조합을 빠짐없이 나열하므로 명세에서 빠진 경우를 발견하기 좋음 <br>
표의 한 행이 그대로 하나의 테스트 케이스가 되어 설계가 기계적으로 이루어짐 <br>
개발자와 기획자가 같은 표를 보며 정책을 확인할 수 있어 의사소통 도구로도 쓰임 <br>
다만 조건이 늘어나면 행이 2의 n제곱으로 증가해 조합을 줄이는 작업이 필요함
</details>

## 테스트 수행 절차

| 단계 | 활동 | 산출물 |
|---|---|---|
| 1. 명세 분석 | 요구사항에서 입력 조건과 기대 출력을 식별 | 테스트 대상 기능 목록 |
| 2. 테스트 케이스 설계 | 동치 분할, 경계치, 특수치, 의사결정 테이블 적용 | 테스트 케이스 명세서 |
| 3. 테스트 데이터 준비 | 입력값과 예상 결과를 구체적인 값으로 확정 | 테스트 데이터 |
| 4. 테스트 실행 | 준비한 입력으로 소프트웨어 실행 | 실행 결과 |
| 5. 결과 비교 | 실제 결과와 예상 결과를 대조 | 결함 목록 |
| 6. 결함 보고·수정 | 결함을 등록하고 수정 후 회귀 테스트 | 결함 보고서 |

<details><summary>예상 결과를 미리 정해 두어야 하는 이유는?</summary>

실행 후에 결과를 보고 판단하면 나온 값에 끌려가 맞다고 착각하기 쉬움 <br>
테스트 케이스를 설계할 때 예상 결과까지 함께 확정해야 객관적인 판정이 가능함 <br>
예상 결과가 곧 테스트 오라클 역할을 함
</details>

## 🔑 최종 정리

블랙박스 테스트는 소스 코드를 보지 않고 **요구사항 명세만으로** 입력과 출력의 관계를 검증하는 기능적 테스트다.
→ 그런데 가능한 입력을 전부 넣어 볼 수는 없으므로, 대표성 있는 값을 고르는 **휴리스틱**이 필요하다.
→ 먼저 **동치 분할**로 같은 결과가 기대되는 입력들을 묶어 그룹당 하나씩만 고른다.
→ 그룹의 한가운데보다 끝에서 결함이 자주 나므로 **경계치 분석**으로 경계와 그 앞뒤 값을 추가한다.
→ 명세에 없더라도 null이나 0, 극단값처럼 프로그램이 취약한 값은 **특수치 분석**으로 보완한다.
→ 조건이 여럿 얽혀 결과가 정해지는 기능은 **원인/효과 분석**으로 의사결정 테이블을 만들어 조합의 누락을 막는다.
→ 이렇게 설계한 케이스를 가지고 **명세 분석 → 케이스 설계 → 데이터 준비 → 실행 → 결과 비교 → 결함 보고**의 절차로 테스트를 수행한다.
→ 단, 명세에 없는 내부 경로는 검증되지 않으므로 화이트박스 테스트와 함께 써야 한다.

> 한 줄 요약: 블랙박스 테스트는 요구사항 명세를 기준으로 입력 공간을 나누고 결함이 잘 숨는 지점을 골라내는 기법이며, 동치 분할로 나누고 경계치·특수치·원인효과 분석으로 촘촘하게 메운다.
