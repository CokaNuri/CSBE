# 기능 기반 테스트 케이스 생성 기법

## 동치 분할 기법

> 모집단 구간을 동등한 처리를 수행하는 그룹으로 분할하는 것

> 모듈의 인터페이스와 기능을 중심으로 수행

- 입력 데이터 영역은 동등한 연산에 의해 처리되는 데이터들의 부분집합으로 분할된다
- 이러한 부분집합을 **동치 클래스**라고 부른다
- 같은 클래스에 속하는 모든 입력 데이터는 동등한 연산 과정을 통해 처리된다
- 따라서 각 클래스에서 대표값 하나씩만 테스트하면 된다

### 동치 클래스 도출 기준

| 입력 조건의 형태 | 도출 방법 | 예시 |
|---|---|---|
| 일정 값의 영역을 갖는 경우 | 유효 1개, 무효 2개 (미만·초과) | 수량 1~20 → 0 이하 / 1~20 / 21 이상 |
| 데이터 타입으로 정의된 경우 | 유효 1개, 무효 1개 | 정수형 → 정수 / 정수가 아닌 값 |
| 제약 조건을 갖는 데이터 타입인 경우 | 제약 만족 1개, 위반 1개 | 8자리 코드 → 8자리 / 8자리 아님 |
| 동치 클래스 내에서 제약 조건을 갖는 경우 | 처리가 달라지는 지점에서 추가 분할 | 금액 유효 범위를 5만원 기준으로 다시 분할 |

<details><summary>유효 클래스를 다시 나눠야 하는 경우는?</summary>

같은 유효 범위 안이라도 프로그램이 다르게 처리하면 동등한 클래스가 아님 <br>
주문 금액이 유효 범위 안이더라도 5만원을 기준으로 배송비가 갈리면 두 클래스로 나눠야 함 <br>
동치 클래스의 기준은 입력의 형태가 아니라 처리 방식의 동일성임
</details>

<details><summary>무효 클래스는 왜 한 케이스에 하나씩만 넣는가?</summary>

여러 무효 값을 한 케이스에 동시에 넣으면 어떤 값 때문에 오류가 났는지 알 수 없음 <br>
앞의 입력에서 검증이 걸려 뒤의 입력은 검사조차 되지 않는 마스킹이 발생함 <br>
반대로 유효 클래스는 여러 개를 한 케이스에 묶어도 되므로 케이스 수를 줄일 수 있음
</details>

## 경계치 커버리지 분석

> 동치 분할에 의해 분리된 동치 클래스의 경계에 해당하는 값을 테스트 데이터로 선정하는 방법

> 입력 변수에 정의된 값의 특정 영역에 대한 경곗값을 선정

- 경계값, 경계값 −1, 경계값 +1을 함께 선정
- 결함은 영역의 중앙이 아니라 끝에서 발생하는 경우가 많음

**간단한 예시 : 주문 수량이 1 이상 20 이하인 경우**

| 값 | 위치 | 기대 결과 |
|---|---|---|
| 0 | 하한 −1 | 오류 |
| 1 | 하한 | 정상 |
| 2 | 하한 +1 | 정상 |
| 19 | 상한 −1 | 정상 |
| 20 | 상한 | 정상 |
| 21 | 상한 +1 | 오류 |

<details><summary>경계치 분석이 동치 분할을 보완하는 이유는?</summary>

동치 분할은 클래스에서 아무 값이나 하나 고르므로 보통 중앙값을 뽑게 됨 <br>
그런데 이상과 초과, 이하와 미만을 혼동하는 실수는 경계에서만 드러남 <br>
경계치 분석은 그 취약 지점을 겨냥해 클래스마다 값을 몇 개 더 추가하는 방식임 <br>
두 기법은 함께 쓰는 것이 전제임
</details>

## 특수치 커버리지 분석

> 모듈의 인터페이스가 아닌 모듈의 기능을 중심으로 테스트 케이스를 선정하는 방법

> 알고리즘에 대한 특징을 반영하거나, 내부적으로 특수한 함수를 사용하는 경우, 오류 발생이 빈번하다고 알려진 특정 변수를 사용하는 경우

| 유형 | 선정 근거 | 예시 |
|---|---|---|
| 알고리즘 특성 | 계산식이 특정 값에서 무너짐 | 나눗셈의 분모가 0, 정렬 대상이 빈 배열 |
| 특수 함수 사용 | 함수 자체가 취약한 입력을 가짐 | 제곱근의 음수, 로그의 0 |
| 오류 빈발 변수 | 경험적으로 결함이 잦은 값 | null, 빈 문자열, 자료형 최대·최소값 |

<details><summary>특수치 분석이 인터페이스가 아니라 기능 중심인 이유는?</summary>

동치 분할과 경계치 분석은 입력 명세만 보고 기계적으로 도출할 수 있음 <br>
반면 특수치는 내부에서 어떤 연산과 함수를 쓰는지 알아야 짚어낼 수 있음 <br>
명세에 적힌 범위 밖의 값이라도 프로그램이 취약하면 대상이 됨 <br>
그래서 테스터의 경험과 도메인 지식에 크게 의존함
</details>

## 원인 결과 커버리지 분석

> 입력 조건을 원인, 출력 결과를 결과로 두고 그 조합을 정리하여 테스트 케이스를 도출

**표현 방법**

- 의사결정 테이블
- 원인 - 결과 그래프

### 예시 명세

- 원인 C1 : VIP 회원이다
- 원인 C2 : 주문 금액이 5만원 이상이다
- 결과 E1 : 배송비 무료
- 결과 E2 : 배송비 3000원 부과

### 의사결정 테이블

| 구분 | 항목 | 규칙1 | 규칙2 | 규칙3 | 규칙4 |
|---|---|---|---|---|---|
| 원인 | C1 : VIP 회원 | Y | Y | N | N |
| 원인 | C2 : 5만원 이상 | Y | N | Y | N |
| 결과 | E1 : 배송비 무료 | O | O | O | |
| 결과 | E2 : 3000원 부과 | | | | O |

- 규칙 하나가 곧 테스트 케이스 하나가 됨

### 원인 - 결과 그래프

```
   C1 (VIP 회원) ──┐
                   ├── OR ──→ E1 (배송비 무료)
   C2 (5만원 이상) ─┘                │
                                    NOT
                                     ↓
                              E2 (3000원 부과)
```

- 노드 : 원인과 결과
- 간선 : 인과 관계
- 게이트 : AND, OR, NOT 등의 논리 관계

<details><summary>의사결정 테이블과 원인-결과 그래프의 차이는?</summary>

원인-결과 그래프는 조건 사이의 논리 관계를 그림으로 드러내는 데 강함 <br>
의사결정 테이블은 조합을 빠짐없이 나열해 테스트 케이스로 바로 옮기기 좋음 <br>
실무에서는 그래프로 관계를 정리한 뒤 테이블로 변환해 케이스를 뽑는 순서를 씀
</details>

<details><summary>조건이 많아지면 어떻게 하는가?</summary>

조건이 n개면 규칙이 2의 n제곱 개로 늘어나 표가 감당하기 어려워짐 <br>
결과가 같은 규칙끼리 묶어 무관 표시로 축약하는 방법을 씀 <br>
현실적으로 발생하지 않는 조합은 제외해 규칙 수를 줄임
</details>

## 블랙박스 테스트 케이스 생성 예제

### 예제 명세

온라인 주문 시스템의 배송비 계산 기능

| 입력 | 조건 |
|---|---|
| quantity (주문 수량) | 1 이상 20 이하의 정수 |
| amount (주문 금액) | 10,000원 이상 500,000원 이하의 정수 |
| grade (회원 등급) | GENERAL 또는 VIP |

**처리 규칙**

- 입력이 조건을 벗어나면 오류 메시지 출력
- grade가 VIP이거나 amount가 50,000원 이상이면 배송비 0원
- 그 외에는 배송비 3,000원

### 1단계 : 동치 분할

| 입력 | 클래스 ID | 조건 | 구분 |
|---|---|---|---|
| quantity | EC1 | 1 미만 | 무효 |
| quantity | EC2 | 1 ~ 20 | 유효 |
| quantity | EC3 | 20 초과 | 무효 |
| amount | EC4 | 10,000 미만 | 무효 |
| amount | EC5 | 10,000 ~ 49,999 | 유효 |
| amount | EC6 | 50,000 ~ 500,000 | 유효 |
| amount | EC7 | 500,000 초과 | 무효 |
| grade | EC8 | GENERAL | 유효 |
| grade | EC9 | VIP | 유효 |
| grade | EC10 | 그 외 값 | 무효 |

- amount의 유효 범위는 5만원을 기준으로 처리가 달라지므로 EC5와 EC6로 다시 분할

### 2단계 : 커버리지 매트릭스

| 클래스 | TC1 | TC2 | TC3 | TC4 | TC5 | TC6 | TC7 | TC8 |
|---|---|---|---|---|---|---|---|---|
| EC1 | | | O | | | | | |
| EC2 | O | O | | | O | O | O | O |
| EC3 | | | | O | | | | |
| EC4 | | | | | O | | | |
| EC5 | O | | | | | | | O |
| EC6 | | O | | | | O | | |
| EC7 | | | | | | | O | |
| EC8 | O | | | | | | | |
| EC9 | | O | | | | | | |
| EC10 | | | | | | | | O |

- 유효 클래스는 한 케이스에 묶어서 커버
- 무효 클래스는 케이스마다 하나씩만 포함
- 매트릭스로 빠진 클래스가 없는지 확인 가능

### 3단계 : 경계치 분석

| 입력 | 경계 | 선정값 |
|---|---|---|
| quantity | 하한 1 | 0, 1, 2 |
| quantity | 상한 20 | 19, 20, 21 |
| amount | 하한 10,000 | 9,999, 10,000, 10,001 |
| amount | 처리 분기 50,000 | 49,999, 50,000, 50,001 |
| amount | 상한 500,000 | 499,999, 500,000, 500,001 |

### 4단계 : 테스트 케이스 작성

| ID | 테스트 항목 | quantity | amount | grade | 예상 결과 |
|---|---|---|---|---|---|
| TC1 | 일반 회원 소액 주문 | 5 | 30,000 | GENERAL | 배송비 3,000원 |
| TC2 | VIP 회원 주문 | 5 | 100,000 | VIP | 배송비 0원 |
| TC3 | 수량 하한 미달 | 0 | 30,000 | GENERAL | 오류 메시지 |
| TC4 | 수량 상한 초과 | 21 | 30,000 | GENERAL | 오류 메시지 |
| TC5 | 금액 하한 미달 | 5 | 9,999 | GENERAL | 오류 메시지 |
| TC6 | 금액 무료 기준 충족 | 5 | 50,000 | GENERAL | 배송비 0원 |
| TC7 | 금액 상한 초과 | 5 | 500,001 | GENERAL | 오류 메시지 |
| TC8 | 등급 값 오류 | 5 | 30,000 | SILVER | 오류 메시지 |
| TC9 | 수량 하한 경계 | 1 | 30,000 | GENERAL | 배송비 3,000원 |
| TC10 | 수량 상한 경계 | 20 | 30,000 | GENERAL | 배송비 3,000원 |
| TC11 | 금액 무료 기준 직전 | 5 | 49,999 | GENERAL | 배송비 3,000원 |
| TC12 | 금액 상한 경계 | 5 | 500,000 | GENERAL | 배송비 0원 |

<details><summary>TC6과 TC11을 반드시 함께 넣어야 하는 이유는?</summary>

배송비가 갈리는 기준이 5만원 이상인지 초과인지를 확인하는 짝임 <br>
개발자가 부등호를 잘못 써 초과로 구현했다면 TC6만 실패하고 TC11은 통과함 <br>
경계값 하나만 넣으면 이 실수를 놓치므로 경계의 양쪽을 함께 확인해야 함
</details>
