# 시나리오 기반 테스트

> 사용자가 시스템을 실제로 사용하는 흐름을 따라가며 테스트하는 기법

> 개별 기능이 아니라 기능들이 이어진 사용 흐름 전체를 검증

## 테스트 시나리오 생성 방법

| 방법 | 기준 | 특징 |
|---|---|---|
| 아웃라인 방법 | 관련된 기능의 연계성 고려 | 화면과 화면 전환을 따라 흐름을 구성 |
| 유스 케이스 방법 | 시스템의 액터를 중심으로 시나리오 생성 | 액터의 목적 단위로 흐름을 구성 |

**선택 기준**

- 테스터의 경험과 선호도에 따라 선택
- 요구사항에 주어진 형식에 따라 선택
- 테스트 시나리오를 개발하기 위한 도구의 가용성에 따라 결정

<details><summary>시나리오 기반 테스트가 필요한 이유는?</summary>

개별 기능이 각각 정상이어도 이어 붙였을 때 문제가 생기는 경우가 많음 <br>
장바구니 담기와 결제가 따로는 잘 되지만 로그인 세션이 끊기면 흐름이 깨지는 식임 <br>
사용자는 기능을 하나씩 쓰는 것이 아니라 목적을 이루기 위해 연속으로 사용함 <br>
그래서 시스템 테스트와 인수 테스트 단계에서 주로 활용됨
</details>

<details><summary>두 방법은 어떻게 다른가?</summary>

아웃라인 방법은 화면 전환처럼 시스템이 보여 주는 구조를 따라감 <br>
유스 케이스 방법은 액터가 이루려는 목적을 따라가므로 화면과 무관하게 흐름이 정해짐 <br>
UI가 명확한 시스템은 아웃라인이, 요구사항이 유스 케이스로 정리된 시스템은 유스 케이스 방법이 유리함
</details>

## 테스트 시나리오 생성 예제

**대상 시스템 : 온라인 쇼핑몰**

| 시나리오 ID | 시나리오 | 관련 기능 |
|---|---|---|
| SC1 | 회원이 로그인하여 상품을 주문하고 결제를 완료한다 | 로그인, 상품 조회, 장바구니, 결제 |
| SC2 | 비회원이 상품을 조회하다 로그인 요구를 받는다 | 상품 조회, 로그인 |
| SC3 | 회원이 주문 내역에서 주문을 취소한다 | 로그인, 주문 조회, 주문 취소 |
| SC4 | 결제 도중 잔액 부족으로 결제가 실패한다 | 장바구니, 결제, 예외 처리 |

- 정상 흐름뿐 아니라 실패 흐름도 시나리오로 포함해야 함

## 아웃라인 방법에 의한 테스트 케이스 생성

### 화면 흐름 아웃라인

```
1. 로그인 화면
   1.1 아이디/비밀번호 입력 → 성공 → 2. 상품 목록 화면
   1.2 아이디/비밀번호 입력 → 실패 → 1. 로그인 화면 (오류 메시지)

2. 상품 목록 화면
   2.1 상품 선택 → 3. 상품 상세 화면
   2.2 로그아웃 → 1. 로그인 화면

3. 상품 상세 화면
   3.1 장바구니 담기 → 4. 장바구니 화면
   3.2 뒤로 가기 → 2. 상품 목록 화면

4. 장바구니 화면
   4.1 주문하기 (상품 있음) → 5. 결제 화면
   4.2 주문하기 (상품 없음) → 4. 장바구니 화면 (오류 메시지)

5. 결제 화면
   5.1 결제 (잔액 충분) → 6. 주문 완료 화면
   5.2 결제 (잔액 부족) → 5. 결제 화면 (오류 메시지)
```

### 테스트 케이스 생성 방법

- 각 화면 단위의 사용자 입력에 대해 테스트 케이스 생성
- 테스트의 결과는 화면 전환이 이루어지도록 구성
- 요구사항 스펙에 따라 입력에 대한 결과를 예상 결과로 정의
- 각 화면에서 다음 화면으로 분기 가능한 모든 입력에 대해 예상 결과 생성
- 예상 결과대로 구현한 시스템이 동작하는지를 점검하고 Pass 또는 Fail을 실제 결과에 기록

### 테스트 케이스

| ID | 현재 화면 | 입력 | 예상 결과 (화면 전환) | 실제 결과 |
|---|---|---|---|---|
| TC1 | 로그인 | 올바른 아이디·비밀번호 | 상품 목록 화면으로 이동 | |
| TC2 | 로그인 | 잘못된 비밀번호 | 로그인 화면 유지, 오류 메시지 표시 | |
| TC3 | 상품 목록 | 상품 선택 | 상품 상세 화면으로 이동 | |
| TC4 | 상품 목록 | 로그아웃 | 로그인 화면으로 이동 | |
| TC5 | 상품 상세 | 장바구니 담기 | 장바구니 화면으로 이동, 상품 1건 표시 | |
| TC6 | 장바구니 | 주문하기 (상품 있음) | 결제 화면으로 이동 | |
| TC7 | 장바구니 | 주문하기 (상품 없음) | 장바구니 화면 유지, 오류 메시지 표시 | |
| TC8 | 결제 | 결제 (잔액 충분) | 주문 완료 화면으로 이동 | |
| TC9 | 결제 | 결제 (잔액 부족) | 결제 화면 유지, 오류 메시지 표시 | |

<details><summary>예상 결과를 화면 전환으로 정의하는 이유는?</summary>

아웃라인 방법은 화면 사이의 연결이 올바른지를 확인하는 것이 목적임 <br>
값의 계산이 맞는지보다 다음에 어떤 화면으로 가는지가 검증 대상임 <br>
전환이 명확한 관찰 지점이므로 Pass와 Fail 판정이 쉬움 <br>
화면에 머무는 경우도 오류 메시지 표시까지 예상 결과에 적어야 함
</details>

## 유스 케이스 방법에 의한 테스트 케이스 생성

### 유스 케이스 명세

| 항목 | 내용 |
|---|---|
| 유스 케이스 명 | 상품 주문하기 |
| 액터 | 회원 |
| 사전 조건 | 회원이 로그인되어 있고 장바구니에 상품이 있다 |
| 사후 조건 | 주문이 생성되고 결제가 완료된다 |

**기본 흐름**

1. 회원이 장바구니에서 주문하기를 선택한다
2. 시스템이 주문 정보와 결제 금액을 표시한다
3. 회원이 배송지와 결제 수단을 입력한다
4. 시스템이 결제를 요청한다
5. 결제가 승인되면 시스템이 주문을 생성하고 완료 화면을 표시한다

**대체 흐름**

- 3a. 회원이 기존 배송지를 선택하면 입력을 건너뛴다
- 4a. 회원이 포인트를 사용하면 결제 금액을 차감한 후 결제를 요청한다

**예외 흐름**

- 4b. 결제가 거절되면 오류 메시지를 표시하고 결제 단계로 돌아간다
- 5b. 재고가 부족하면 주문 생성을 중단하고 안내 메시지를 표시한다

### 테스트 케이스

| ID | 대상 흐름 | 조건 | 예상 결과 |
|---|---|---|---|
| TC1 | 기본 흐름 | 배송지·결제 수단 정상 입력, 잔액 충분 | 주문 생성, 완료 화면 표시 |
| TC2 | 대체 흐름 3a | 기존 배송지 선택 | 배송지 입력 없이 결제 단계로 진행 |
| TC3 | 대체 흐름 4a | 포인트 5,000원 사용 | 결제 금액에서 5,000원 차감 후 승인 |
| TC4 | 예외 흐름 4b | 카드 한도 초과 | 오류 메시지 표시, 결제 단계 유지, 주문 미생성 |
| TC5 | 예외 흐름 5b | 결제 직전 재고 소진 | 주문 생성 중단, 안내 메시지 표시, 결제 취소 |
| TC6 | 사전 조건 위반 | 장바구니가 비어 있음 | 주문하기 불가, 오류 메시지 표시 |

### 유의 사항

- 모든 유스 케이스에 대해 테스트 케이스를 작성해야 함
- 비정상적인 동작에 대해서도 테스트를 수행해야 하므로 예외 처리 부분에 대한 테스트를 수행해야 함

<details><summary>왜 예외 흐름 테스트가 특히 중요한가?</summary>

기본 흐름은 개발 과정에서 반복 확인되지만 예외 흐름은 손이 덜 감 <br>
결제 실패나 재고 부족처럼 드물게 발생하는 경로에 결함이 몰리는 이유임 <br>
특히 예외 발생 시 이미 진행된 작업을 되돌리는 처리가 빠지면 데이터 정합성이 깨짐 <br>
TC5처럼 결제는 됐는데 주문이 생성되지 않는 상황을 반드시 확인해야 함
</details>

<details><summary>사전 조건도 테스트 대상인가?</summary>

사전 조건이 만족되지 않은 상태에서 유스 케이스를 시도하는 경우도 케이스로 만들어야 함 <br>
로그인하지 않은 사용자가 주문 화면에 직접 접근하는 상황이 대표적임 <br>
정상 흐름만 검증하면 이런 우회 접근이 그대로 통과할 수 있음
</details>

## 🔑 최종 정리

개별 기능이 각각 정상이어도 이어 붙였을 때 문제가 생기므로, 사용자의 **실제 사용 흐름**을 따라 검증하는 시나리오 기반 테스트가 필요하다.
→ 시나리오를 만드는 방법은 두 가지다. 화면과 기능의 연계를 따라가는 **아웃라인 방법**, 액터의 목적을 따라가는 **유스 케이스 방법**이며, 테스터의 경험·요구사항 형식·도구 가용성에 따라 고른다.
→ **아웃라인 방법**은 화면 흐름을 계층으로 정리한 뒤, 각 화면의 입력마다 테스트 케이스를 만들고 **예상 결과를 화면 전환으로 정의**한다. 분기 가능한 모든 입력을 빠짐없이 다뤄야 한다.
→ **유스 케이스 방법**은 액터·사전 조건·기본 흐름·대체 흐름·예외 흐름으로 정리된 명세에서 각 흐름을 하나씩 케이스로 옮긴다.
→ 이때 **모든 유스 케이스**를 대상으로 하되, 결함이 몰리는 **예외 흐름과 사전 조건 위반**까지 반드시 포함해야 한다.
→ 실행 후에는 예상 결과와 대조해 Pass 또는 Fail을 기록한다.

> 한 줄 요약: 시나리오 기반 테스트는 기능을 하나씩이 아니라 사용 흐름 단위로 검증하는 기법이며, 화면 전환을 따라가는 아웃라인 방법과 액터의 목적을 따라가는 유스 케이스 방법으로 시나리오를 만든다.
