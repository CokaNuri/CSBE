# 좋은 코딩 기법

## 좋은 소프트웨어 코드의 6가지 공통점

| 공통점 | 설명 |
| --- | --- |
| 쉽게 읽을 수 있다 | 코드는 **작성하는 시간보다 읽는 시간이 훨씬 길다** |
| 주석이 잘 작성되어 있다 | 코드만으로는 드러나지 않는 의도·배경·제약을 설명 |
| 코드 구조가 간결하다 | 가독성이 올라가고, 복잡도가 낮아 버그가 줄어든다 |
| 쉽게 변경할 수 있다 | 요구사항 변화에 드는 유지보수 비용을 낮춘다 |
| 활용을 위해 관리할 수 있다 | 하드코딩 지양, 설정 분리, 변경 이력 추적(버전 관리) |
| 제 기능을 한다 | 아무리 깔끔해도 요구사항을 만족하지 못하면 의미가 없다 |



## 좋은 코드 작성을 위한 규칙

| 규칙 | 핵심 내용 |
| --- | --- |
| 최적화보다 가독성 우선 | 성능 튜닝은 병목이 측정된 뒤에 한다 |
| 아키텍처 우선 개발 | 모듈화된 구조를 먼저 잡아야 테스트·디버깅이 쉬워진다 |
| 테스트 커버리지 고려 | 테스트하기 쉬운 구조로 설계한다 |
| 간단하고 단순하게 | 불필요한 일반화·과설계를 피한다 |
| 주석은 보조적으로 | 코드 자체가 설명이 되게 하고, 주석은 보조적 설명 |
| 강한 응집, 느슨한 결합 | 모듈 내부는 뭉치고, 모듈 사이는 느슨하게 |
| 코드 리뷰가 항상 좋은 것은 아니다 | 리뷰 의존보다 각자 맡은 부분에 대한 완전한 이해·책임이 먼저 |
| "나중에 리팩토링" 은 작동하지 않는다 | 처음부터 구조화된 코드를 작성한다 |
| 한 번에 완성하지 말고 반복 개발 | 작게 만들고 검증하며 키운다 |
| 자동화 도구를 사용 | 빌드·테스트·정적 분석·포매팅을 사람 손에서 뗀다 |



<details>
<summary>리뷰를 안 하면 자기 부분만 알게 되어 전체 이해가 떨어지지 않는가?</summary>

- 리뷰의 대표적 효익 중 하나가 지식 전파와 버스 팩터(특정 인원 이탈 시 프로젝트가 멈추는 위험) 완화다
- 리뷰를 없애면 지식 공유 공백은 메워지지 않는다

</details>

<details>
<summary>"리팩토링은 작동하지 않는다"가 어떤 의미인가?</summary>

리팩토링 기법이 쓸모없다는 뜻이 아니라, "일단 대충 짜고 나중에 정리하자"는 계획이 지켜지지 않는다는 뜻 <br>
- 나중에는 오지 않는다
- 방치된 나쁜 구조 위에 코드가 계속 쌓이면 정리 비용이 기하급수로 커진다
- 처음부터 구조를 잡고, 리팩토링은 상시로 조금씩 한다

</details>
