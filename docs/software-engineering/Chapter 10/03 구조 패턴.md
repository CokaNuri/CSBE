# 구조 패턴 Structural Patterns

> 클래스와 객체를 조합해 더 큰 구조를 만드는 패턴 묶음<br>
> 대부분 "무언가를 감싼다"는 공통 기법을 쓰지만 감싸는 목적이 서로 다름<br>
> 코드 모양이 비슷하므로 **구조가 아니라 목적으로 구분**해야 함

---

## 한눈에 보기

| 패턴 | 인터페이스 | 감싸는 개수 | 목적 |
|---|---|---|---|
| 어댑터 | **바뀜** | 1개 | 안 맞는 것을 맞춤 |
| 브릿지 | 그대로 | 1개 | 두 축을 독립적으로 확장 |
| 컴포지트 | 그대로 | **여러 개** | 트리로 묶어 동일하게 취급 |
| 데코레이터 | 그대로 | 1개 | 기능을 더함 |
| 파사드 | **새로 만듦** | 여러 개 | 복잡한 것을 단순하게 보여줌 |
| 플라이웨이트 | 그대로 | — | 중복 객체를 공유해 메모리 절약 |
| 프록시 | 그대로 | 1개 | 접근을 제어함 |

### 감싸기 계열 판별법

| 질문 | 어댑터 | 데코레이터 | 프록시 |
|---|---|---|---|
| 받는 타입과 자기 타입이 같은가 | 아니오 | 예 | 예 |
| 자기 자신을 겹칠 수 있는가 | 아니오 | 예 | 대개 한 겹 |
| 원본을 반드시 호출하는가 | 예 | 예 | **아니오** |

## 1. 어댑터 Adapter

> 클래스의 인터페이스를 클라이언트가 기대하는 다른 인터페이스로 변환하여<br>
> 호환되지 않던 것들이 함께 동작할 수 있게 하는 패턴

### 문제 및 동기

우리 시스템은 `PaymentGateway` 인터페이스에 맞춰 짜여 있는데<br>
새로 계약한 PG 사가 준 SDK 는 메서드 이름도 파라미터도 반환 타입도 전부 다름

고칠 수 있으면 고치면 되지만 남의 라이브러리라 못 고침<br>
우리 인터페이스를 SDK 에 맞춰 바꾸면 기존 PG 사 코드와 이를 쓰는 서비스가 전부 무너짐

이때 흔히 저지르는 실수는 도메인 코드에 외부 SDK 타입을 직접 끌어들이는 것<br>
주문 로직 안에 특정 PG 사의 요청 · 응답 타입과 응답 코드 규칙이 들어와 버림

### 해결 아이디어

해외여행에서 쓰는 **콘센트 변환기**와 같음<br>
기기를 개조하지도 벽을 뜯지도 않고 사이에 어댑터를 하나 끼움

```java
public class TossPaymentAdapter implements PaymentGateway {   // 우리 규격을 따름

    private final TossSdk sdk;                                 // 남의 물건을 감쌈

    @Override
    public PaymentResult pay(String orderId, long amount) {
        TossRequest req = new TossRequest();      // 우리 형식 → 저쪽 형식
        req.setOrderNo(orderId);
        req.setAmt(amount);

        TossResponse res = sdk.requestPayment(req);

        return new PaymentResult(                 // 저쪽 형식 → 우리 형식
                "0000".equals(res.getCode()), res.getTid());
    }
}
```

어댑터가 하는 일은 딱 세 가지 — **입력 변환 → 호출 → 출력 변환**<br>
여기에 예외 변환이나 단위 변환이 붙기도 함

### 적용 대상

- 기존 인터페이스와 맞지 않는 클래스를 사용해야 할 때
- 수정할 수 없는 외부 라이브러리나 레거시를 붙여야 할 때
- 여러 외부 벤더를 하나의 규격으로 통일하고 싶을 때

### 구조

| 역할 | 예시 | 책임 |
|---|---|---|
| Target | `PaymentGateway` | 클라이언트가 기대하는 규격 |
| Adaptee | `TossSdk` | 기능은 있는데 규격이 안 맞는 것 |
| Adapter | `TossPaymentAdapter` | 둘 사이의 번역기 |
| Client | `OrderService` | Target 만 알고 있음 |

핵심은 어댑터가 **양쪽을 동시에 바라본다**는 것<br>
위로는 우리 인터페이스를 구현하고 옆으로는 외부 객체를 필드로 들고 있음

### 객체 어댑터와 클래스 어댑터

| 구분 | 객체 어댑터 | 클래스 어댑터 |
|---|---|---|
| 방식 | Adaptee 를 필드로 보유 | Adaptee 를 상속 |
| 자바에서 | 사실상 표준 | 다중 상속 불가로 제약이 큼 |
| 문제점 | 없음 | Adaptee 의 public 메서드가 전부 노출 |

실무에서는 사실상 객체 어댑터만 씀 — 스프링 DI 와도 자연스럽게 맞음

### 실무 위치

**Spring MVC 의 `HandlerAdapter`** — 이름부터 어댑터<br>
`DispatcherServlet` 은 `@Controller` · `HttpRequestHandler` 등 생김새가 제각각인 핸들러를<br>
각각의 어댑터를 통해 `handle` 이라는 단일 규격으로 다룸<br>
그래서 `DispatcherServlet` 코드에 컨트롤러 종류별 분기가 없음

**`InputStreamReader`** — 바이트 스트림을 문자 스트림으로 변환<br>
**SLF4J** — 서로 다른 로깅 구현체를 하나의 인터페이스로 감쌈

**헥사고날 아키텍처** — "포트 앤 어댑터"라는 별명 그대로 이 패턴이 뼈대<br>
도메인이 포트를 정의하고 외부 세계와의 연결은 전부 어댑터가 담당하므로<br>
도메인 코드에 외부 라이브러리 타입이 하나도 들어가지 않음

## 2. 브릿지 Bridge

> 추상부와 구현부를 분리하여 두 계층이 각각 독립적으로 확장될 수 있게 하는 패턴

### 문제 및 동기

알림에는 종류가 있고 채널도 있음<br>
일반 · 긴급 · 예약 세 종류에 SMS · 이메일 · 슬랙 세 채널이면 상속으로는 **3 × 3 = 9개** 클래스

`UrgentSmsNotification` · `NormalSmsNotification` 처럼 이름에 두 개념이 붙기 시작하고<br>
SMS 발송 코드가 세 클래스에 중복되어 SMS 업체를 바꾸면 세 군데를 고쳐야 함

문제의 정체는 **변하는 축이 두 개인데 상속이라는 축 하나에 다 밀어 넣은 것**

| 축 | 내용 | 서로의 관계 |
|---|---|---|
| 축 1 | 알림을 어떻게 처리할지 | 긴급이라고 SMS 전송 방식이 달라지지 않음 |
| 축 2 | 알림을 무엇으로 보낼지 | SMS 라고 긴급 처리 로직이 달라지지 않음 |

무관한 두 축을 상속으로 엮으니 클래스가 **곱셈**으로 늘어남

### 해결 아이디어

축 하나를 별도 인터페이스로 뽑고 남은 축은 그것을 참조로만 들고 있음

```java
public interface MessageSender {                        // 축 2
    void send(String to, String title, String body);
}

public abstract class Notification {                    // 축 1
    protected final MessageSender sender;               // 이 참조가 다리

    @Override
    public void notify(User user, String msg) { ... }
}

public class UrgentNotification extends Notification {
    public void notify(User user, String msg) {
        for (int i = 0; i < 3; i++) {                   // 긴급은 3회 반복
            sender.send(user.getContact(), "[긴급]", msg);
        }
    }
}
```

```java
new UrgentNotification(new SlackSender()).notify(user, "서버 다운");
```

클래스가 **3 + 3 = 6개**로 줄고 조합은 런타임에 만듦

> **브릿지는 곱셈을 덧셈으로 바꾸는 패턴**

### 적용 대상

- 변하는 축이 두 개이고 각각 독립적으로 자랄 것으로 예상될 때
- 클래스 이름에 두 개념이 `AB` 형태로 붙기 시작할 때
- 구현 세부사항이 상위 로직에 오염되면 안 될 때

### 구조

| 역할 | 의미 | 비유 |
|---|---|---|
| Abstraction 추상부 | 상위 수준 제어 로직 — 무엇을 할지 | 코스 순서를 정하는 매니저 |
| RefinedAbstraction | 추상부의 변형들 | 긴급 알림 · 예약 알림 |
| Implementor 구현부 | 하위 수준 실제 동작 — 어떻게 할지 | 실제로 요리하는 주방 |
| ConcreteImplementor | 구현부의 변형들 | SMS · 이메일 · 슬랙 |

**용어 주의**<br>
여기서 말하는 "구현"은 `abstract class` 나 `implements` 얘기가 전혀 아님<br>
구현부 쪽도 인터페이스와 그 구현체들로 되어 있음

### 어댑터와의 차이

| | 어댑터 | 브릿지 |
|---|---|---|
| 언제 | 이미 만들어진 뒤 사후에 붙임 | 설계 단계에서 처음부터 분리 |
| 왜 | 규격이 안 맞아서 | 두 축이 각각 자랄 것 같아서 |
| 대상 | 보통 남의 코드 | 보통 내 코드 |

### 실무 위치

JDBC — 자바가 정한 API 가 추상부이고 각 벤더 드라이버가 구현부<br>
SLF4J — 로깅 API 와 Logback · Log4j2 바인딩

직접 짜게 되는 상황<br>
저장 정책 × 저장소 · 결제 유형 × PG 사 · 집계 방식 × 출력 대상

전략 패턴과 코드가 거의 같아 구분이 어려운데<br>
전략은 한쪽만 갈아끼우고 브릿지는 양쪽이 다 자란다는 것이 차이<br>
실무에서는 **"변하는 축이 두 개인가"** 만 확인하면 충분

## 3. 컴포지트 Composite

> 부분과 전체의 계층을 트리 구조로 표현하여<br>
> 개별 객체와 복합 객체를 클라이언트가 동일하게 다룰 수 있게 하는 패턴

### 문제 및 동기

조직도에서 본부 전체 인건비를 구해야 함<br>
사원 리스트와 부서 리스트를 따로 두면 클라이언트가 매번 "사원이냐 부서냐"를 구분해 이중 순회를 함

이 구분이 한 군데서 끝나지 않는 것이 진짜 문제<br>
인원수 계산 · 조직도 출력 · 등급별 조회 등 **모든 기능마다 같은 구조의 분기가 복제**됨<br>
새 타입이 생기면 모든 메서드에 세 번째 순회를 추가해야 함

### 해결 아이디어

"인건비를 갖고 있다"는 점에서 사원과 부서는 같으므로 같은 타입으로 취급

```java
public interface OrgUnit {
    long getTotalSalary();
}

public class Employee implements OrgUnit {          // Leaf
    public long getTotalSalary() { return salary; }  // 재귀 없음
}

public class Department implements OrgUnit {        // Composite
    private final List<OrgUnit> children = new ArrayList<>();   // 타입이 하나

    public long getTotalSalary() {
        return children.stream()
                       .mapToLong(OrgUnit::getTotalSalary)      // 자식이 뭐든 상관없음
                       .sum();
    }
}
```

```java
long cost = unit.getTotalSalary();   // 사원이든 본부든 똑같이 호출
```

분기가 사라진 이유는 **재귀가 클라이언트 코드에서 객체 구조 안으로 옮겨갔기 때문**

### 성립 조건 — 이게 중요함

컴포지트가 되려면 세 조건이 모두 필요함

| 조건 | 내용 |
|---|---|
| 1 | 말단과 묶음이 서로 **다른 타입**일 것 |
| 2 | 클라이언트가 둘을 구분하지 않고 **같은 연산**을 호출할 것 |
| 3 | 묶음에서 그 연산이 **자식들의 결과를 모아 합치는** 형태일 것 |

댓글과 대댓글은 조건 1부터 실패함 — 둘 다 `Comment` 라 다형성이 필요 없음<br>
카테고리 트리도 마찬가지로 그냥 자기 참조 자료구조일 뿐

> **같은 타입끼리 중첩되면 그냥 트리 · 다른 타입을 같게 취급해야 하면 컴포지트**

### 진짜 컴포지트가 필요한 예 — 조건 조합

쿠폰 적용 조건을 관리자가 화면에서 조립하는 기능

```java
public interface Condition { boolean matches(Order order); }

public class MinAmount implements Condition {          // Leaf
    public boolean matches(Order o) { return o.getTotal() >= amount; }
}

public class And implements Condition {                // Composite
    private final List<Condition> children;
    public boolean matches(Order o) {
        return children.stream().allMatch(c -> c.matches(o));
    }
}
```

```java
Condition rule = new And(
        new MinAmount(50_000),
        new Or(new NewMember(), new MemberGrade(GOLD)));
```

진짜 이득은 **이 트리를 JSON 으로 저장하고 런타임에 읽어 조립할 수 있다는 것**<br>
마케팅팀이 관리자 화면에서 조건을 조립하면 배포 없이 적용됨 — `if` 로는 불가능한 일

### 적용 대상

- 중첩 가능한 규칙 · 사용자가 조립하는 조건
- 재귀적으로 값을 합산해야 하는 구조
- 권한 정책 엔진 · 검증기 조합 · 번들 상품 가격 계산

### 구조

| 역할 | 책임 |
|---|---|
| Component | 말단과 묶음이 공유하는 인터페이스 |
| Leaf | 자식이 없는 말단 · 자기 값만 반환 |
| Composite | 자식 목록을 보유하고 결과를 합산 · **Component 를 다시 담음** |

`Composite` 가 자기 조상 타입을 다시 담는 **자기 참조 고리**가 트리를 만듦

### 설계 선택 — 투명성과 안전성

| 방식 | `add` `remove` 위치 | 장점 | 단점 |
|---|---|---|---|
| 투명성 우선 | Component 에 선언 | 완전히 동일하게 취급 | Leaf 에 말이 안 되는 메서드가 생김 |
| 안전성 우선 | Composite 에만 선언 | 컴파일 타임에 잘못된 호출 차단 | 타입 캐스팅이 등장할 수 있음 |

GoF 는 투명성을 선호하지만 대부분의 실무 코드는 안전성 쪽을 택함

### 주의할 점

- 타입 제약이 느슨해짐 — "이 부서에는 사원만"같은 규칙을 컴파일러가 못 잡음
- 순환 참조 시 무한 재귀로 `StackOverflowError` 발생 — 조립 시점에 검증할 것
- **DB 에서 쓸 때 N+1 이 기다림** — 지연 로딩 트리를 재귀 순회하면 노드마다 쿼리가 나감<br>
  트리 전체를 한 번에 읽어 메모리에서 조립하는 방식으로 대응

### 실무 위치

상품 카테고리 · 조직도 · 메뉴 권한 트리 · QueryDSL `BooleanBuilder` · JPA `Specification`<br>
스프링의 `CompositeCacheManager` · `CompositeHealthContributor` · `CompositeItemProcessor`

빈도 자체는 낮지만 **필요한 순간에는 대체재가 없음**<br>
쓸 곳을 찾아다니는 패턴이 아니라 만났을 때 알아보는 패턴

## 4. 데코레이터 Decorator

> 객체에 동적으로 새로운 책임을 추가하며<br>
> 기능 확장이 필요할 때 서브클래싱 대신 사용할 수 있는 유연한 대안

### 문제 및 동기

외부 API 클라이언트에 로깅 · 캐싱 · 재시도를 붙여야 함<br>
상속으로 풀면 조합마다 클래스가 필요해 기능 3개에 **2³ − 1 = 7개**가 생김<br>
4개면 15개 · 5개면 31개로 **2ⁿ** 으로 늘어남

게다가 상속은 컴파일 타임에 고정되어 운영에서는 캐싱을 켜고 개발에서는 끄는 것도 불가능

### 해결 아이디어

**부가 기능을 가진 클래스도 같은 인터페이스를 구현하되 안에 또 다른 같은 타입을 품음**

```java
public class LoggingProductClient implements ProductClient {

    private final ProductClient delegate;      // 같은 타입을 품음

    @Override
    public Product findById(Long id) {
        long start = System.currentTimeMillis();
        Product product = delegate.findById(id);          // 원본에 위임
        log.info("조회 {}ms", System.currentTimeMillis() - start);
        return product;
    }
}
```

```java
ProductClient client =
        new LoggingProductClient(
            new CachingProductClient(
                new RetryProductClient(
                    new HttpProductClient())));
```

클래스는 4개인데 조합은 무한<br>
필요 없는 껍질은 그 줄만 지우면 되고 설정에 따라 런타임 조립도 가능

### 순서가 곧 동작

```java
new LoggingClient(new CachingClient(http));   // 캐시에 맞아도 로그가 남음
new CachingClient(new LoggingClient(http));   // 캐시에 맞으면 로그가 안 남음
```

**바깥 껍질일수록 먼저 실행되고 나중에 끝남** — 실무에서 자주 하는 실수 지점

### 적용 대상

- 여러 부가 기능을 자유롭게 조합해야 할 때
- 런타임에 기능을 붙이거나 뗄 수 있어야 할 때
- 상속으로 풀면 조합 폭발이 일어날 때

### 구조

| 역할 | 책임 |
|---|---|
| Component | 원본과 데코레이터가 공유하는 인터페이스 |
| ConcreteComponent | 실제 일을 하는 원본 |
| Decorator | Component 를 필드로 보유하며 같은 인터페이스를 구현 |
| ConcreteDecorator | 위임 전후에 부가 기능을 추가 |

### 실무 위치

**`java.io` 가 통째로 데코레이터**

```java
new BufferedReader(new InputStreamReader(new FileInputStream(file)));
```

이 한 줄에 두 패턴이 같이 있음<br>
`InputStreamReader` 는 `InputStream` 을 받아 `Reader` 가 되므로 타입이 바뀌는 **어댑터**<br>
`BufferedReader` 는 `Reader` 를 받아 `Reader` 가 되므로 타입이 유지되는 **데코레이터**

**`Collections.unmodifiableList`** — 기능을 더하는 게 아니라 빼는 데코레이터<br>
**서블릿 필터와 `HttpServletRequestWrapper`**<br>
**스프링 AOP** — `@Transactional` · `@Cacheable` 이 붙으면 프록시가 원본 빈을 감쌈<br>
우리가 손으로 하던 조립을 스프링이 대신 해주는 것

### 주의할 점

- 스택 트레이스가 껍질 수만큼 깊어져 디버깅이 괴로움
- 감싼 객체와 원본은 다른 객체라 `==` 비교나 `instanceof` 검사가 실패함
- 껍질이 여러 겹이면 조립 코드가 지저분해짐

## 5. 프록시 Proxy

> 다른 객체에 대한 접근을 제어하기 위해<br>
> 그 객체의 대리자 또는 자리표시자를 제공하는 패턴

### 문제 및 동기

주문을 조회할 때 회원 정보가 필요할 수도 없을 수도 있음<br>
항상 회원까지 조회하면 안 쓰는 경우에도 쿼리가 낭비되고<br>
클라이언트가 직접 관리하면 "필요하면 그때 불러온다"는 로직이 호출부마다 반복됨

### 해결 아이디어

**원본과 똑같이 생겼지만 실제로는 비어 있는 대역**을 세움

```java
public class MemberProxy extends Member {

    private final Long id;
    private Member target;                       // 아직 비어 있음

    @Override
    public String getName() {
        if (target == null) {
            target = repository.findById(id);    // 이 순간 처음 쿼리
        }
        return target.getName();
    }
}
```

클라이언트 코드는 전혀 바뀌지 않고 `getName` 호출 전까지는 DB 를 치지 않음<br>
**언제 진짜 객체를 만들 것인가라는 결정이 클라이언트에서 프록시 안으로 옮겨감**

JPA 지연 로딩의 정체가 정확히 이것 — 하이버네이트가 런타임에 같은 형태의 프록시를 만들어 넣음

### 네 가지 용도

| 종류 | 목적 | 실무 예 |
|---|---|---|
| 가상 프록시 | 생성 비용이 큰 객체를 미룸 | JPA 지연 로딩 |
| 보호 프록시 | 접근 권한을 검사 | Spring Security `@PreAuthorize` |
| 원격 프록시 | 다른 서버 객체를 로컬처럼 사용 | Feign Client · RMI |
| 스마트 참조 | 접근 시 부가 작업 수행 | `@Cacheable` |

### 적용 대상

- 객체 생성을 지연시켜야 할 때
- 접근 권한을 통제해야 할 때
- 원격 자원을 로컬 객체처럼 다루고 싶을 때

### 구조

| 역할 | 책임 |
|---|---|
| Subject | 원본과 프록시가 공유하는 인터페이스 |
| RealSubject | 실제 일을 하는 원본 |
| Proxy | 같은 타입으로 행세하며 원본을 스스로 관리 |

데코레이터와 구조가 거의 같지만 **프록시는 대상을 스스로 만들고 관리**함<br>
클라이언트는 진짜 객체가 있는지조차 모름

### 스프링 AOP 와의 관계

`@Transactional` · `@Cacheable` · `@Async` · `@PreAuthorize` 가 전부 프록시로 동작함<br>
스프링은 빈을 등록할 때 원본 대신 프록시 객체를 컨테이너에 넣음

| 방식 | 조건 |
|---|---|
| JDK 동적 프록시 | 인터페이스가 있을 때 |
| CGLIB | 클래스를 상속해서 생성 · **스프링 부트 기본값** |

### 실무에서 반드시 물리는 함정

**자기 호출이 안 먹힘**

```java
@Service
public class OrderService {
    public void order() {
        this.save();          // 트랜잭션이 안 걸림
    }

    @Transactional
    public void save() { ... }
}
```

외부 호출은 프록시를 거치지만 `this.save()` 는 원본이 자기를 직접 부르므로 프록시를 통과하지 않음

**`final` 이 붙으면 프록시가 안 됨**<br>
CGLIB 은 상속으로 프록시를 만드는데 `final` 클래스나 메서드는 오버라이드가 불가능해<br>
`@Transactional` 이 조용히 무시됨 — 코틀린에서 `all-open` 플러그인을 쓰는 이유

**생성자와 `@PostConstruct` 에서는 프록시가 아직 없음**<br>
**JPA 프록시는 `instanceof` 와 `==` 를 깨뜨림** — `equals` 에서 `getClass` 대신 `instanceof` 를 쓰는 이유

### 데코레이터와의 최종 구분

| | 데코레이터 | 프록시 |
|---|---|---|
| 목적 | 기능을 **더함** | 접근을 **통제함** |
| 대상 | 클라이언트가 밖에서 조립 | 프록시가 스스로 관리 |
| 원본 | 반드시 호출 | **호출 안 할 수도 있음** |

마지막 줄이 실질적 구분점 — 데코레이터는 결국 원본을 부르지만<br>
프록시는 캐시에 있거나 권한이 없으면 원본을 아예 안 부름

## 6. 파사드 Facade

> 서브시스템의 여러 인터페이스에 대한 통합된 상위 인터페이스를 제공하여<br>
> 서브시스템을 더 쉽게 사용할 수 있게 하는 패턴

### 문제 및 동기

주문 완료 처리를 하려면 재고 · 결제 · 배송 · 알림 서비스를 정해진 순서로 호출해야 함<br>
컨트롤러가 이 순서와 호출 규칙을 다 알면 서브시스템 전체와 결합됨

### 해결 아이디어

앞단에 창구 하나를 세워 복잡한 호출을 감춤

```java
@Service
public class OrderFacade {

    public void completeOrder(Long orderId) {
        paymentService.approve(orderId);
        stockService.decrease(orderId);
        shippingService.prepare(orderId);
        notificationService.send(orderId);
    }
}
```

클라이언트는 `completeOrder` 하나만 호출<br>
서브시스템을 감추지만 **막지는 않음** — 필요하면 개별 서비스를 직접 써도 됨

### 적용 대상

- 복잡한 서브시스템에 단순한 진입점이 필요할 때
- 여러 서비스 호출 순서를 한곳에 모으고 싶을 때
- 레거시 시스템을 감싸 새 코드와의 접점을 하나로 줄일 때

### 구조

| 역할 | 책임 |
|---|---|
| Facade | 서브시스템 전체를 대표하는 단순한 인터페이스 |
| Subsystem | 실제 일을 하는 여러 클래스 |

어댑터와 달리 **기존 인터페이스를 변환하는 게 아니라 새 인터페이스를 만드는 것**이 차이

### 실무 위치

스프링 애플리케이션에서 여러 서비스를 조합하는 `~Facade` 클래스가 이 형태<br>
트랜잭션 경계를 하나로 잡거나 컨트롤러의 의존성을 줄이는 목적으로 자주 쓰임

## 7. 플라이웨이트 Flyweight

> 다수의 유사한 객체를 공유하여 메모리 사용을 최소화하는 패턴

### 문제 및 동기

주문 100만 건을 메모리에 올리는데 각 주문이 `Currency` 객체를 따로 가짐<br>
실제 통화 종류는 몇십 개뿐인데 내용이 똑같은 객체가 백만 개 중복됨

### 해결 아이디어

객체의 상태를 두 종류로 나눔

| 구분 | 내용 | 예 |
|---|---|---|
| 본질적 상태 intrinsic | 공유 가능 · 변하지 않음 | 통화 코드 · 기호 |
| 부가적 상태 extrinsic | 인스턴스마다 다름 | 주문 금액 |

공유 가능한 쪽만 빼서 팩토리로 캐싱해 재사용

```java
public final class Currency {
    private static final Map<String, Currency> CACHE = new ConcurrentHashMap<>();

    public static Currency of(String code) {
        return CACHE.computeIfAbsent(code, c -> new Currency(c, symbolOf(c)));
    }
}
```

### 절대 조건 — 공유 객체는 불변이어야 함

공유 객체를 누군가 수정하면 그것을 쓰는 모든 곳이 함께 오염됨<br>
필드는 전부 `final` · setter 없음 · 클래스도 `final` 이 원칙

### 자바에 이미 들어 있음

```java
Integer a = 127, b = 127;   a == b;   // true  — 캐시된 같은 객체
Integer c = 128, d = 128;   c == d;   // false — 범위를 벗어나 새 객체
```

`-128 ~ 127` 범위의 래퍼 타입은 미리 만들어두고 재사용함<br>
테스트 데이터는 ID 가 작아 통과하는데 운영에서 ID 가 커지면 조용히 실패하는 **버그 단골**

> 래퍼 타입은 무조건 `equals` 로 비교할 것

문자열 리터럴 풀과 `enum` 도 같은 원리

### 적용 대상 및 주의

- 동일한 객체가 수십만 개 이상 중복 생성될 때만 의미가 있음
- 캐시 키 종류가 무한하면 메모리 누수가 됨
- **GoF 패턴 중 실무에서 가장 안 쓰는 축** — 쓰기 위해서보다 자바 동작을 이해하려고 배움

## 🔑 최종 정리

구조 패턴은 전부 "감싼다"는 기법을 공유하므로 **목적으로 구분**해야 함

- **어댑터** — 안 맞는 것을 맞춤 · 인터페이스가 **바뀜**
- **브릿지** — 두 축을 분리해 곱셈을 덧셈으로 바꿈
- **컴포지트** — 말단과 묶음을 같은 타입으로 취급해 트리를 만듦
- **데코레이터** — 기능을 더함 · 원본을 반드시 호출
- **파사드** — 복잡한 것 앞에 단순한 창구를 세움
- **플라이웨이트** — 중복 객체를 공유해 메모리를 아낌
- **프록시** — 접근을 통제함 · 원본을 안 부를 수도 있음

특히 헷갈리는 세 쌍의 판별법

| 비교 | 결정적 차이 |
|---|---|
| 어댑터 대 데코레이터 | 받는 타입과 자기 타입이 같은가 |
| 데코레이터 대 프록시 | 원본을 반드시 부르는가 |
| 컴포지트 대 데코레이터 | 자식을 여럿 담는가 하나만 감싸는가 |

실무 체감으로는 어댑터 · 데코레이터 · 프록시를 스프링과 자바 표준 라이브러리에서 매일 소비하고<br>
컴포지트와 브릿지는 필요한 순간에 알아보는 것이 핵심이며 플라이웨이트는 원리 이해용

> **한 줄 요약:** 구조 패턴은 객체를 감싸고 조합해 더 큰 구조를 만드는 방법들이며 감싸는 모양은 비슷하되 인터페이스를 바꾸는가 · 기능을 더하는가 · 접근을 막는가 · 트리를 만드는가라는 목적으로 갈린다
