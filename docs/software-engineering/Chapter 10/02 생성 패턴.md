# 생성 패턴 Creational Patterns

> 객체를 만드는 책임을 사용하는 코드에서 떼어내는 패턴 묶음<br>
> 목적은 하나 — 코드에서 `new` 를 지워 구체 클래스와의 결합을 끊는 것<br>
> 무엇을 지렛대로 삼아 지우느냐에 따라 다섯 가지로 갈림

---

## 한눈에 보기

| 패턴 | 무엇이 결정하나 | 한 줄 정의 | 대표 비용 |
|---|---|---|---|
| 팩토리 메서드 | 자식 클래스 | 만들 객체를 서브클래스가 정함 | 제품마다 서브클래스가 생김 |
| 추상 팩토리 | 팩토리 객체 | 관련 객체 묶음을 통째로 교체 | 제품 종류 추가가 비쌈 |
| 빌더 | 조립 절차와 빌더 | 절차는 고정하고 결과물만 교체 | 빌더 클래스 증가 |
| 프로토타입 | 견본 인스턴스 | 새로 만들지 않고 복사 | 복제 구현이 어려움 |
| 싱글턴 | 클래스 자신 | 인스턴스를 하나로 강제 | 전역 상태 · 테스트 곤란 |

### 상황별 선택 기준

| 상황 | 선택 |
|---|---|
| 여러 객체가 한 세트로 움직여야 한다 | 추상 팩토리 |
| 같은 절차로 다른 형태를 만든다 | 빌더 |
| 이미 만들어둔 것과 거의 똑같다 | 프로토타입 |
| 절차는 같고 만들 타입만 다르다 | 팩토리 메서드 |
| 인스턴스가 딱 하나여야 한다 | 싱글턴 |

## 1. 팩토리 메서드 Factory Method

> 객체 생성을 위한 인터페이스를 정의하되<br>
> 어떤 클래스의 인스턴스를 만들지는 서브클래스가 결정하게 하는 패턴

### 문제 및 동기

문서 편집기의 `newDocument` 는 문서를 만들고 · 목록에 등록하고 · 열고 · 화면에 표시함<br>
문서 종류가 뭐든 뒷부분 세 단계는 완전히 동일하고 오직 `new ___` 한 줄만 다름

이 상태에서 생기는 문제

- 문서 종류를 추가할 때마다 `Application` 을 열어 수정해야 함
- `Application` 이 세상의 모든 구체 문서 클래스를 알아야 함
- 프레임워크로 배포했다면 사용자는 내부 분기문을 고칠 수 없음

### 해결 아이디어

다른 부분은 그대로 두고 `new ___` **한 줄만 메서드로 빼서 자식에게 떠넘김**

```java
abstract class Application {
    abstract Document createDocument();     // 자식이 채울 구멍

    void newDocument() {
        Document doc = createDocument();    // 뭐가 만들어지는지 모름
        docs.add(doc);
        doc.open();
        showInWindow(doc);
    }
}

class DrawingApp extends Application {
    Document createDocument() { return new DrawingDocument(); }
}
```

부모가 자식을 호출하고 · 부모가 자식이 만든 객체를 사용하는 **흐름의 뒤집힘**이 핵심<br>
프레임워크가 전체 흐름을 쥐고 사용자는 정해진 구멍만 채우는 구조 그 자체

### 적용 대상

- 어떤 클래스의 객체를 만들어야 할지 미리 알 수 없을 때
- 만들 객체를 서브클래스가 지정하게 하고 싶을 때
- 골격은 제공하되 세부 타입은 사용자에게 맡겨야 하는 프레임워크성 코드

### 구조

| 역할 | 예시 | 책임 |
|---|---|---|
| Creator | `Application` | 절차를 갖고 팩토리 메서드를 선언 |
| ConcreteCreator | `DrawingApp` | 어떤 제품을 만들지 결정 |
| Product | `Document` | 만들어질 것의 인터페이스 |
| ConcreteProduct | `DrawingDocument` | 실제 만들어지는 것 |

생성자 계층과 제품 계층 두 줄이 나란히 서서 함께 자람

### 주의할 점

- 제품 하나 바꾸려고 클래스를 하나 상속해야 하는 것이 가장 큰 비용
- 부모에 기본 구현을 두면 상속이 필수가 아닌 선택이 됨
- `Integer.valueOf` 같은 **정적 팩토리 메서드**는 이 패턴이 아님<br>
  구분 기준은 자식 클래스가 오버라이드해서 결정을 바꾸는가 여부

### 실무 위치

애플리케이션 코드에서 직접 구현할 일은 드묾 — 대부분 DI 로 해결됨<br>
대신 프레임워크를 읽을 때 계속 등장 — `Collection.iterator` · 스프링 `FactoryBean.getObject`

## 2. 추상 팩토리 Abstract Factory

> 구체적인 클래스를 지정하지 않고<br>
> 서로 연관되거나 의존적인 객체들의 묶음을 생성하는 인터페이스를 제공하는 패턴

### 문제 및 동기

여러 룩앤필을 지원해야 하는 UI 툴킷에서 두 가지 문제가 발생

**구체 클래스에 대한 결합**<br>
`new MotifScrollBar()` 처럼 직접 인스턴스화하면 룩앤필 교체 시 코드 전체를 고쳐야 함

**제품 간 일관성 붕괴**<br>
Motif 스크롤바와 Windows 버튼이 한 화면에 섞이면 안 되는데<br>
개별 생성 방식으로는 "같은 계열끼리만 조합된다"는 제약을 코드로 강제할 수 없음

### 해결 아이디어

각 제품을 만드는 연산들을 하나의 팩토리 인터페이스에 모으고 계열마다 구현체를 하나씩 둠<br>
클라이언트는 팩토리 객체 하나만 교체하면 제품군 전체가 함께 바뀜

### 적용 대상

- 시스템이 제품의 생성 · 구성 · 표현 방식과 독립적이어야 할 때
- 여러 제품군 중 하나를 선택해 구성되며 런타임이나 설정에 따라 교체될 수 있을 때
- **관련 제품 객체들이 함께 사용되도록 설계되었고 그 제약을 강제해야 할 때** ← 가장 결정적
- 제품의 구현이 아닌 인터페이스만 공개하고 싶을 때

### 구조

| 역할 | 책임 |
|---|---|
| AbstractFactory | 각 추상 제품을 생성하는 연산의 인터페이스 선언 |
| ConcreteFactory | 특정 계열에 속하는 구체 제품을 실제로 생성 |
| AbstractProduct | 제품 객체의 인터페이스 선언 |
| ConcreteProduct | 해당 팩토리가 만들 제품의 구현 |
| Client | AbstractFactory 와 AbstractProduct 인터페이스만 사용 |

### 핵심 특성 — 확장 방향의 비대칭

제품 계열과 제품 종류가 이루는 2차원 격자를 떠올리면 명확함

| | 무엇을 하는가 | 기존 코드 수정 | 비용 |
|---|---|---|---|
| 계열 추가 | 격자의 열 하나 추가 | 없음 | 낮음 |
| 제품 종류 추가 | 격자의 행 하나 추가 | 인터페이스와 모든 팩토리 | 높음 |

계열을 추가할 때는 새 클래스 파일만 쓰면 되지만<br>
제품 종류를 추가하면 인터페이스가 바뀌어 모든 구체 팩토리가 컴파일 에러를 냄

따라서 **계열이 자주 늘어날 것 같으면 적합하고 · 제품 종류가 계속 추가될 것 같으면 족쇄가 됨**

### 실무 위치

JDBC 가 교과서적 사례<br>
`Connection` 이 추상 팩토리이고 `createStatement` · `prepareStatement` 가 만드는 제품들이 모두 같은 벤더 계열로 일관됨

직접 만든다면 멀티 클라우드 지원 같은 상황 — 스토리지 · 큐 · 알림을 한 세트로 묶어 교체<br>
다만 스프링을 쓴다면 `@Profile` 이나 `@ConditionalOnProperty` 로 빈 묶음을 바꾸는 편이 간단함<br>
DI 컨테이너가 추상 팩토리 역할을 상당 부분 대신함

### 팩토리 메서드와의 차이

> 팩토리 메서드는 상속으로 객체 하나의 생성을 서브클래스에 위임하고<br>
> 추상 팩토리는 합성으로 서로 연관된 객체 묶음의 생성을 팩토리 객체에 위임함

두 축이 다름 — **상속 대 합성** · **객체 하나 대 제품군**<br>
경쟁 관계가 아니라 포함 관계 — 추상 팩토리의 각 생성 연산이 대개 팩토리 메서드로 구현됨

## 3. 빌더 Builder

> 복합 객체의 생성 과정과 표현 방법을 분리하여<br>
> 동일한 생성 절차가 서로 다른 표현 결과를 만들 수 있게 하는 패턴

### 문제 및 동기

**복합 객체**란 부품이 여러 개라서 한 번에 못 만드는 객체<br>
`new Point(3, 5)` 는 단순 객체지만 문서는 제목 · 문단 · 목록 · 이미지를 여러 단계로 쌓아 올려야 함

마크다운을 HTML 로 바꾸는 코드를 짠 뒤 평문 텍스트로도 뽑아달라는 요구가 오면 보통 복사해서 붙여넣음<br>
두 코드를 나란히 놓고 보면 `for` 문도 `if` 순서도 조건도 전부 같고 오직 만들어내는 문자열 모양만 다름

여기서 두 덩어리가 분리됨

| 구분 | 내용 | 형식에 따라 |
|---|---|---|
| 생성 과정 | 어떤 순서로 무엇을 처리하는가 | 항상 동일 |
| 표현 방법 | 그 결과를 어떤 모양으로 만드는가 | 매번 다름 |

둘이 한 클래스에 뒤엉켜 있어서 뒤엣것 하나 바꾸려고 앞엣것까지 통째로 복사한 것

### 해결 아이디어

표현 담당만 인터페이스로 뽑고 절차 담당은 한 번만 작성

```java
interface DocBuilder {
    void addTitle(String text);
    void addParagraph(String text);
    void addItem(String text);
}

class HtmlBuilder implements DocBuilder {
    private String result = "";
    public void addTitle(String t) { result += "<h1>" + t + "</h1>"; }
    public String getResult()      { return result; }
}

class MarkdownReader {                        // Director
    void read(List<Line> lines, DocBuilder builder) {
        for (Line line : lines) {
            if (line.isTitle())     builder.addTitle(line.text());
            else if (line.isPara()) builder.addParagraph(line.text());
        }
    }
}
```

```java
reader.read(lines, html);      // 같은 read 호출인데
reader.read(lines, text);      // 결과물이 다름
```

`MarkdownReader` 는 결과물이 HTML 인지 평문인지 전혀 모름<br>
"제목 나왔다" · "문단 나왔다"고 빌더에게 알려줄 뿐

비유하자면 **진행자와 서기** — 진행자는 안건 순서대로 회의를 이끌고 서기가 받아 적음<br>
서기가 한국어 서기면 한국어 회의록이 · 영어 서기면 영어 회의록이 나오지만 진행 순서는 똑같음

### 적용 대상

- 복합 객체의 생성 알고리즘이 구성 요소와 독립적이어야 할 때
- 하나의 생성 절차로 여러 표현 형식을 만들어야 할 때
- 객체가 여러 단계를 거쳐 조립되며 중간에 세밀한 제어가 필요할 때

### 구조

| 역할 | 책임 |
|---|---|
| Builder | 제품의 각 부분을 생성하는 추상 인터페이스 |
| ConcreteBuilder | 부분을 실제로 조립하고 내부 상태를 관리 · 결과 반환 |
| Director | 빌더 인터페이스를 사용해 생성 절차를 수행 |
| Product | 만들어지는 복합 객체 |

**협력 방식**<br>
클라이언트가 구체 빌더를 만들어 디렉터에게 넘김 → 디렉터가 정해진 순서로 `buildPart` 호출<br>
→ 클라이언트가 빌더에서 결과물을 회수<br>
결과는 디렉터를 거치지 않고 **빌더에서 직접 나옴**

`getResult` 가 `Builder` 인터페이스에 없는 것은 의도된 설계<br>
한 빌더는 문자열을 다른 빌더는 UI 위젯을 만들 수 있어 반환 타입 통일이 무의미한 경우가 많기 때문

### 두 종류의 빌더 — 반드시 구분할 것

| 구분 | GoF 빌더 | 점층적 생성자 해소 빌더 |
|---|---|---|
| 대표 형태 | Director + Builder | 롬복 `@Builder` · 체이닝 |
| 푸는 문제 | 같은 절차로 다른 표현 생성 | 매개변수가 많고 선택적일 때의 가독성 |
| Director | 있음 | 없음 |

```java
Pizza p = new Pizza.Builder().size(12).cheese(true).build();   // 이것은 GoF 빌더가 아님
```

실무에서 빌더라 부르는 것 대부분이 후자<br>
면접이나 시험에서는 GoF 정의로 답하되 이 구분을 아는 것을 보여주면 좋음

### 실무 위치

**압도적으로 자주 씀 — 다만 대부분 롬복 스타일**<br>
GoF 빌더가 진짜 필요한 상황은 주문 데이터를 엑셀 · CSV · PDF 세 가지로 내보내는 경우처럼<br>
순회 절차는 동일한데 출력 형태만 다를 때

## 4. 프로토타입 Prototype

> 원형이 되는 인스턴스를 사용하여 생성할 객체의 종류를 명시하고<br>
> 그 견본을 복사해서 새로운 객체를 생성하는 패턴

### 문제 및 동기

몬스터 소환기를 팩토리 메서드로 짜면 몬스터가 100종일 때 소환기 클래스도 100개가 됨<br>
그런데 진짜 문제는 **"체력 2배에 화염 스킬 달린 정예 고블린"** 같은 요구

정예 고블린은 클래스가 `Goblin` 으로 똑같고 다른 것은 설정값뿐인데<br>
팩토리 메서드로는 이것을 표현할 방법이 없어 `EliteGoblinSpawner` 를 또 만들어야 함

> 클래스만 다른 게 아니라 **설정만 다른 경우까지 전부 클래스로** 만들어야 하는 것이 한계 지점

### 해결 아이디어

"무엇을 만들지"를 서브클래스가 아니라 **이미 만들어진 견본 객체**가 정하게 함

```java
class Spawner {
    private Monster prototype;
    Spawner(Monster prototype) { this.prototype = prototype; }

    void spawn(int x, int y) {
        Monster m = prototype.copy();     // 견본을 복사
        m.setPos(x, y);
    }
}
```

```java
Goblin elite = new Goblin();
elite.setHp(500);
elite.addSkill(FIREBALL);
new Spawner(elite);                        // 새 클래스 0개
```

> 팩토리 메서드는 어떤 클래스를 상속했느냐로 결정하고<br>
> 프로토타입은 어떤 인스턴스를 들고 있느냐로 결정함

클래스는 컴파일 타임에 고정되지만 인스턴스는 런타임에 갈아끼울 수 있음

### 적용 대상

- 만들 객체의 종류가 런타임에 정해질 때
- 클래스는 같고 설정 상태만 다른 변종이 많을 때
- 객체 생성 비용이 클 때 — DB 조회나 무거운 초기화를 거친 객체라면 복사가 훨씬 쌈
- Creator 서브클래스가 제품 수만큼 늘어나는 것을 피하고 싶을 때

### 구조

Creator 계층이 통째로 사라지고 **제품 계층 하나만 남는 것**이 특징

| 역할 | 책임 |
|---|---|
| Prototype | `copy` 연산을 선언하는 인터페이스 |
| ConcretePrototype | 자기 자신을 복제해 반환 |
| Client | 견본에게 복제를 요청 |

### 반드시 걸리는 함정 — 얕은 복사

```java
c.skills = this.skills;                  // 같은 리스트를 가리키는 주소만 복사됨
c.skills = new ArrayList<>(this.skills); // 새 리스트를 만들어야 안전
```

어디까지 깊게 파고들지는 **필드가 불변인지**로 판단<br>
`String` 이나 `int` 처럼 바뀌지 않는 것은 공유해도 무해하고 리스트 · 맵 · 가변 객체는 새로 만듦

자바의 `Cloneable` · `clone` 은 권장되지 않음<br>
생성자를 거치지 않아 `final` 필드를 다룰 수 없고 기본 동작이 얕은 복사이며 규약이 어정쩡함<br>
복사 생성자나 직접 만든 `copy` 메서드가 안전

### 프로토타입 관리자

견본이 많아지면 레지스트리에 모아두고 이름으로 꺼내 씀

```java
registry.register("elite_goblin", elite);
Monster m = registry.create("elite_goblin");   // 내부에서 copy 호출
```

견본을 JSON 설정 파일에서 읽어 등록하면 **코드 수정도 재컴파일도 없이 종류를 추가**할 수 있음<br>
실무에서 이 패턴이 힘을 발휘하는 지점이 대개 여기

### 실무 위치

방어적 복사로 자주 만나고 패턴으로는 가끔 씀 — 계약서 양식 · 결재 서식 같은 템플릿 복제<br>
단점은 하나로 요약됨 — **모든 클래스가 자기 복제를 직접 구현해야 하고 그것이 생각보다 어려움**

## 5. 싱글턴 Singleton

> 클래스의 인스턴스가 오직 하나임을 보장하고<br>
> 그 인스턴스에 접근할 수 있는 전역적인 접근점을 제공하는 패턴

### 문제 및 동기

DB 커넥션 풀 · 설정 정보 · 캐시 · 로거는 애플리케이션 전체에 딱 하나만 있어야 함<br>
커넥션 풀이 두 개 생기면 커넥션 개수 제한이 무의미해지고 캐시가 두 개면 넣은 것을 못 찾음

"하나만 만들어 쓰자"는 약속일 뿐 강제가 아니므로 언어 차원에서 막아야 함

### 해결 아이디어

**생성자를 private 으로 막고 static 메서드 하나만 열어둠**

```java
public class ConnectionPool {
    private static final ConnectionPool INSTANCE = new ConnectionPool();
    private ConnectionPool() { }
    public static ConnectionPool getInstance() { return INSTANCE; }
}
```

### 구현 방식 비교

이른 초기화는 안전하지만 안 쓸 수도 있는 무거운 객체를 무조건 만듦<br>
그래서 게으른 초기화를 쓰면 **멀티 스레드 경쟁 조건**이 생김<br>
A 가 `null` 검사를 통과한 직후 아직 `new` 전에 B 가 끼어들어 똑같이 통과하면 인스턴스가 둘 생김

| 방식 | 특징 |
|---|---|
| 이른 초기화 | 안전하지만 무조건 생성 |
| `synchronized` | 확실하지만 매 호출마다 락을 잡아 느림 |
| 이중 검사 잠금 | 빠르지만 `volatile` 필수 |
| **홀더 이디엄** | 게으른 초기화가 공짜 · 락도 `volatile` 도 불필요 · 실무 권장 |
| **enum** | 리플렉션과 역직렬화 공격까지 방어 · Effective Java 권장 |

**이중 검사 잠금에서 `volatile` 이 필요한 이유**<br>
JVM 이 `new` 를 메모리 할당 → 생성자 실행 → 참조 대입 순으로 하는데<br>
최적화 과정에서 참조 대입이 생성자 실행보다 먼저 일어날 수 있어<br>
다른 스레드가 아직 초기화가 덜 된 객체를 받아갈 수 있음

```java
public class ConnectionPool {                         // 홀더 이디엄
    private ConnectionPool() { }

    private static class Holder {
        private static final ConnectionPool INSTANCE = new ConnectionPool();
    }

    public static ConnectionPool getInstance() { return Holder.INSTANCE; }
}
```

`Holder` 는 `getInstance` 가 처음 호출될 때 비로소 로딩되고<br>
클래스 초기화는 JVM 이 스레드 안전을 보장하므로 별도 동기화가 필요 없음

### 안티패턴이라 불리는 이유

| 문제 | 내용 |
|---|---|
| 전역 상태 | 어디서든 접근 가능하니 누가 언제 상태를 바꿨는지 추적 불가 |
| 테스트 곤란 | 가짜 객체로 바꿔치기 불가 · 테스트 간 상태가 새어 나감 |
| 숨은 의존성 | 생성자 시그니처만 봐서는 무엇에 의존하는지 알 수 없음 |

### 스프링과의 관계

| | GoF 싱글턴 | 스프링 싱글턴 빈 |
|---|---|---|
| 범위 | 클래스로더당 하나 | **컨테이너당** 하나 |
| 접근 | `getInstance` 직접 호출 | 생성자 주입 |
| 테스트 | 교체 불가 | 목 객체로 교체 자유 |
| 의존성 | 숨겨짐 | 생성자에 드러남 |

스프링 방식이 위 단점 세 가지를 전부 해결함<br>
인스턴스는 하나로 유지하되 접근은 주입으로 받으므로<br>
**싱글턴이라는 목표는 취하고 전역 접근점이라는 부작용은 버린 형태**

### 실무에서 진짜 사고 나는 지점

싱글턴 자체보다 이것이 훨씬 중요함 — **싱글턴 빈에 가변 상태를 두면 안 됨**

```java
@Service
public class OrderService {
    private Long currentUserId;      // 재앙

    public void process(Long userId) {
        this.currentUserId = userId;
    }
}
```

인스턴스는 하나인데 여러 요청이 동시에 들어오므로<br>
A 사용자의 처리 도중 B 사용자의 요청이 값을 덮어써 **A 가 B 의 데이터를 보게 되는 개인정보 사고**가 됨

`@Service` · `@Repository` · `@Component` 는 무상태로 유지하고 상태는 파라미터나 지역 변수로 넘길 것

## 🔑 최종 정리

다섯 패턴은 전부 **코드에서 `new` 를 지우는 방법**이고 무엇을 지렛대로 쓰는지만 다름

- **팩토리 메서드** — 만들 것을 자식에게 물어봄 · 지렛대는 **상속**
- **추상 팩토리** — 관련된 것들을 세트로 묶어 통째로 교체 · 지렛대는 **합성**
- **빌더** — 조립 순서는 고정하고 결과물만 교체 · 지렛대는 **절차 분리**
- **프로토타입** — 새로 만들지 말고 복사 · 지렛대는 **인스턴스**
- **싱글턴** — 인스턴스를 하나로 강제 · 지렛대는 **생성자 차단**

실무 체감으로 보면<br>
빌더는 매일 쓰고 · 추상 팩토리는 라이브러리 안에 이미 있으며<br>
프로토타입은 방어적 복사로 만나고 · 팩토리 메서드는 직접 구현보다 프레임워크 읽기용<br>
싱글턴은 스프링이 대신 처리해줌

생성 패턴 대부분을 스프링이 이미 처리해주고 있어 애플리케이션 개발자가 직접 손댈 일이 적은 영역

> **한 줄 요약:** 생성 패턴은 객체를 만드는 책임을 사용하는 코드에서 떼어내는 다섯 가지 방법이며 상속 · 합성 · 절차 분리 · 복사 · 생성자 차단 중 무엇을 지렛대로 쓰느냐로 갈린다
