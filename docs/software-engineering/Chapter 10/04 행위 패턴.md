# 행위 패턴 Behavioral Patterns

> 객체 사이의 책임 분배와 알고리즘 · 상호작용 방식을 다루는 패턴 묶음<br>
> 생성 패턴이 "무엇을 만드나" · 구조 패턴이 "어떻게 조합하나"였다면<br>
> 행위 패턴은 **"누가 무엇을 하고 어떻게 소통하나"** 를 다룸

---

## 한눈에 보기

| 패턴 | 한 줄 정의 | 실무 빈도 |
|---|---|---|
| 전략 | 알고리즘을 인터페이스로 통일해 밖에서 교체 | 매우 높음 |
| 템플릿 메서드 | 절차는 부모가 고정하고 일부만 자식이 채움 | 매우 높음 |
| 옵저버 | 사건을 발행하면 구독자들이 자동으로 반응 | 매우 높음 |
| 책임 연쇄 | 처리기를 줄로 세워 넘기거나 중단 | 높음 |
| 반복자 | 순회 방법을 컬렉션에서 떼어냄 | 높음 · 소비 위주 |
| 상태 | 상태를 객체로 만들어 분기를 위임 | 중간 |
| 커맨드 | 실행할 동작 자체를 객체로 만듦 | 중간 |
| 중재자 | 얽힌 소통을 한 지점으로 모음 | 중간 |
| 메멘토 | 상태를 봉인해 저장하고 복원 | 낮음 |
| 방문자 | 연산을 노드 계층 밖으로 뺌 | 낮음 |
| 인터프리터 | 문법 요소를 클래스로 만들어 문장을 실행 | 매우 낮음 |

## 1. 전략 Strategy

> 동일 계열의 알고리즘군을 정의하고 각각을 캡슐화하여<br>
> 알고리즘을 사용하는 클라이언트와 독립적으로 교체할 수 있게 하는 패턴

### 문제 및 동기

회원 등급별 할인을 `if / else if` 로 계산하다 보면 요구사항이 붙을 때마다 분기가 늘어남<br>
몇 달 뒤 이 메서드는 수백 줄이 됨

| 문제 | 내용 |
|---|---|
| 수정 위험 | 정책 하나 추가할 때마다 이 메서드를 열어야 함 |
| 테스트 곤란 | VIP 로직만 테스트하려 해도 전체 분기를 타야 함 |
| 교체 불가 | 런타임이나 설정에 따라 바꿀 수 없음 |

### 해결 아이디어

**각 `if` 블록을 독립된 클래스로 꺼냄**

```java
public interface DiscountPolicy {
    long discount(Order order);
}

public class VipDiscountPolicy implements DiscountPolicy {
    public long discount(Order order) { return (long)(order.getAmount() * 0.2); }
}

public class OrderService {
    private final DiscountPolicy policy;      // 밖에서 주입받음

    public long finalPrice(Order order) {
        return order.getAmount() - policy.discount(order);   // if 가 없음
    }
}
```

`if` 가 사라진 게 아니라 **객체 선택으로 바뀐 것**<br>
새 정책이 필요하면 클래스를 하나 추가할 뿐 기존 코드는 열지 않음

### 적용 대상

- 분기가 계속 늘어날 것이 예상될 때
- 각 분기 로직이 여러 줄이고 독립적으로 테스트하고 싶을 때
- 런타임이나 설정에 따라 알고리즘을 바꿔야 할 때

**쓰지 말아야 할 때**<br>
분기가 두세 개고 각각 한 줄이면 그냥 `if` 가 나음 — 클래스만 늘고 흐름이 더 안 보임

### 구조

| 역할 | 책임 |
|---|---|
| Strategy | 알고리즘 공통 인터페이스 |
| ConcreteStrategy | 알고리즘 각각의 구현 |
| Context | 전략을 보유하고 위임하는 사용자 |

### 실무에서 진짜 유용해지는 지점

스프링은 **같은 인터페이스를 구현한 빈들을 자동으로 모아 주입**해줌

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final Map<String, DiscountPolicy> policies;   // 스프링이 채워줌

    public long finalPrice(Order order) {
        DiscountPolicy policy = policies.getOrDefault(order.getGrade().name(), NONE);
        return order.getAmount() - policy.discount(order);
    }
}
```

조건이 복잡하면 `List` 주입에 판별 메서드를 다는 방식이 더 나음

```java
public interface DiscountPolicy {
    boolean supports(Order order);      // 자기가 처리할지 스스로 판단
    long discount(Order order);
}

policies.stream()
        .filter(p -> p.supports(order))
        .findFirst()
        .map(p -> p.discount(order))
        .orElse(0L);
```

우선순위가 필요하면 `@Order` 를 붙임<br>
**결제 수단 · 배송비 계산 · 파일 스토리지 · 알림 채널** — 이 형태를 실무에서 계속 만남

### 다른 표현 방식

**람다** — 전략이 단순하면 클래스를 만들지 말 것<br>
`Comparator` · `Runnable` · `Predicate` · `Function` 이 전부 전략임

```java
list.sort(Comparator.comparing(Order::getAmount));
```

**enum** — 정책이 등급에 고정되고 개수가 확정이면 가장 깔끔함<br>
빠뜨린 등급이 있으면 컴파일이 안 되는 것이 장점<br>
다만 런타임 교체가 불가하고 스프링 빈 주입도 못 받음

### 헷갈리는 이웃

| 비교 | 결정적 차이 |
|---|---|
| 브릿지 | 구조는 같지만 두 계층의 독립적 확장이 목적 · 전략은 한쪽만 교체 |
| 상태 | 전략은 외부에서 주입 · 상태는 객체가 스스로 다음 상태로 전이 |
| 커맨드 | 전략은 어떻게 할지 · 커맨드는 무엇을 할지 |

## 2. 템플릿 메서드 Template Method

> 알고리즘의 골격을 정의하고 일부 단계를 서브클래스로 미루어<br>
> 알고리즘 구조는 그대로 둔 채 특정 단계만 재정의할 수 있게 하는 패턴

### 문제 및 동기

일별 리포트와 월별 리포트를 만드는데 절차는 인증 확인 → 데이터 조회 → 집계 → 파일 생성 → 감사 로그<br>
두 메서드를 나란히 놓고 보면 **인증 · 파일 생성 · 감사 로그는 완전히 같고 조회와 집계만 다름**

주간 리포트가 추가되면 또 복사하고 상품별 리포트가 추가되면 또 복사함

문제의 정체는 **전체 절차는 정해져 있는데 몇 단계만 상황마다 다른 것**<br>
게다가 절차의 순서가 뒤바뀌면 안 됨 — 인증을 마지막에 하거나 로그를 먼저 남기면 곤란함

### 해결 아이디어

부모가 전체 흐름을 확정된 순서로 갖고 달라지는 단계만 추상 메서드로 남김

```java
public abstract class ReportGenerator<T> {

    public final byte[] generate(T param) {              // final — 자식이 못 바꿈
        checkPermission();
        List<Order> orders = fetchData(param);           // 자식이 채움
        Map<String, Long> aggregated = aggregate(orders); // 자식이 채움
        byte[] file = createExcel(aggregated);
        recordAuditLog(param);
        return file;
    }

    protected abstract List<Order> fetchData(T param);
    protected abstract Map<String, Long> aggregate(List<Order> orders);
}
```

새 리포트는 두 메서드만 구현하면 되고 인증 · 엑셀 생성 · 감사 로그는 자동으로 붙음

### 흐름의 뒤집힘

`generate` 는 부모 메서드인데 그 안에서 호출되는 `fetchData` 는 자식 메서드<br>
**부모가 자식을 호출함** — Hollywood Principle 이라 부르는 그것

이 덕분에 **자식이 절차를 뒤엎을 수 없음**<br>
인증을 건너뛰거나 순서를 바꾸는 것이 원천 봉쇄됨 — `final` 을 붙이는 이유

### 훅 메서드

절차 중 필요할 수도 아닐 수도 있는 단계는 기본 구현을 빈 껍데기로 둠

```java
protected void applyFilter(Map<String, Long> data) { }   // 훅
```

| 구분 | 의미 |
|---|---|
| 추상 메서드 | 반드시 채워야 할 필수 구멍 |
| 훅 메서드 | 선택적으로 개입할 수 있는 구멍 |

### 적용 대상

- 여러 구현이 알고리즘 골격을 공유하고 일부 단계만 다를 때
- 리소스 관리 · 트랜잭션 · 예외 처리처럼 틀리기 쉬운 절차를 강제하고 싶을 때
- 프레임워크성 코드에서 확장점을 명시적으로 제공하고 싶을 때

### 구조

| 역할 | 책임 |
|---|---|
| AbstractClass | 템플릿 메서드로 절차를 확정하고 추상 메서드와 훅을 선언 |
| ConcreteClass | 추상 메서드를 구현하고 필요하면 훅을 재정의 |

### 전략과의 결정적 차이

| | 전략 | 템플릿 메서드 |
|---|---|---|
| 수단 | **합성** — 인터페이스 주입 | **상속** — 자식이 오버라이드 |
| 결정 시점 | 런타임 | 컴파일 타임 |
| 흐름 방향 | 클라이언트 → 전략 | 부모 → 자식 |
| 바꾸는 것 | 알고리즘 하나를 통째로 | 절차의 여러 구멍 각각 |

**바꿀 게 많고 절차가 확실하면 템플릿 · 바꿀 게 하나뿐이고 통째로 바꾸면 전략**

### 팩토리 메서드와의 관계

팩토리 메서드는 템플릿 메서드의 특수한 경우<br>
자식이 채우는 게 **아무 로직**이면 템플릿 메서드이고 **객체 생성**이면 팩토리 메서드

### 실무 위치 — 가장 많이 살아 있는 곳

스프링의 `~Template` 계열이 전부 이것

**`JdbcTemplate.query`** 가 하는 일<br>
커넥션 획득 → `PreparedStatement` 생성 → 파라미터 바인딩 → 실행 → `ResultSet` 순회 →<br>
**당신의 매핑 로직** → 리소스 해제 → 예외 변환<br>
이 중 매핑 한 단계만 개발자가 채움 — 리소스 누수를 원천 봉쇄한 결과

`RestTemplate` · `TransactionTemplate` · `RedisTemplate` · `OncePerRequestFilter`<br>
Spring Batch 의 `Job` 과 `ItemReader/Processor/Writer` · JUnit 의 `@BeforeEach`

### 주의할 점

- 부모 메서드는 반드시 `final` — 안 그러면 자식이 절차를 뒤엎어 패턴의 존재 이유가 사라짐
- 추상 메서드가 너무 많으면 부모가 하는 일이 없다는 신호 — 전략이나 합성이 더 맞을 수 있음
- 자바는 다중 상속이 안 되므로 여러 절차가 얽히면 인터페이스 조합이 유연함

## 3. 옵저버 Observer

> 객체 사이에 일대다 의존을 정의하여<br>
> 한 객체의 상태가 변하면 그에 의존하는 객체들이 자동으로 통보받게 하는 패턴

### 문제 및 동기

주문이 완료되면 재고 감소 · 포인트 적립 · 이메일 발송 · 배송 준비가 필요함<br>
`OrderService` 가 이들을 직접 호출하면

| 문제 | 내용 |
|---|---|
| 결합 | 주문 서비스가 후속 처리 서비스를 전부 알아야 함 |
| 실패 전파 | 이메일 발송 실패로 예외가 튀어 **주문이 롤백됨** |
| 확장 부담 | 후속 작업이 늘 때마다 주문 코드를 수정 |

핵심은 **주문 완료라는 사건이 "누구에게 알려야 할지"까지 결정하고 있다는 것**

### 해결 아이디어

사건 자체만 알리고 누가 받을지는 각자 알아서 하게 함

```java
public class OrderService {
    private final List<OrderEventListener> listeners;   // 누가 있는지 관심 없음

    public void order(Long orderId) {
        Order order = save(orderId);
        OrderCreatedEvent event = new OrderCreatedEvent(orderId);
        for (OrderEventListener listener : listeners) {
            listener.onOrderCreated(event);
        }
    }
}
```

리스너가 추가되어도 `OrderService` 는 한 줄도 바뀌지 않음

### 적용 대상

- 한 사건에 후속 작업이 여러 개 붙고 앞으로 늘어날 것으로 예상될 때
- 발행자가 구독자의 존재를 몰라야 할 때
- 후속 작업 실패가 원 작업에 영향을 주면 안 될 때

**쓰지 말아야 할 때**<br>
후속 작업이 하나뿐이거나 · 성공까지 확인하고 응답해야 하거나 · 실행 순서가 결정적일 때

### 구조

| 역할 | 책임 |
|---|---|
| Subject | 구독자 목록을 관리하고 사건을 통보 |
| Observer | 통보를 받는 인터페이스 |
| ConcreteObserver | 통보를 받아 자기 일을 수행 |

GoF 원형은 주체가 구독자 목록을 직접 관리하지만<br>
지금은 그 관리를 이벤트 버스로 완전히 떼어낸 형태가 주류

### 스프링에서

```java
publisher.publishEvent(new OrderCreatedEvent(orderId));
```

```java
@EventListener
public void handle(OrderCreatedEvent event) { ... }
```

### 반드시 알아야 할 함정 — 동기 실행

**`@EventListener` 는 기본이 동기 실행**이라 발행자가 리스너 종료까지 기다림<br>
따라서 처음 문제로 짚었던 것들이 그대로 남음

| 도구 | 효과 |
|---|---|
| `@Async` | 비동기 실행 — 발행자가 즉시 반환 |
| `@TransactionalEventListener(AFTER_COMMIT)` | 커밋된 뒤에만 리스너 실행 |

> 옵저버 자체는 결합만 낮춤<br>
> 실행 시점과 실패 전파 제어는 `@Async` + `AFTER_COMMIT` 조합이 사실상 표준

### 실무 위치

스프링 이벤트 · 메시지 큐 · 리액티브 스트림의 `Publisher` 와 `Subscriber`<br>
JDK 의 `java.util.Observer` 는 Java 9 에서 deprecated 되어 지금은 안 씀

### 주의할 점

- `publishEvent` 한 줄이 무슨 일을 일으키는지 코드로 안 보여 **흐름 추적이 어려움**<br>
  분산 추적이 사실상 필수가 됨
- 리스너 순서에 의존하지 말 것 — 순서가 필요해졌다는 것 자체가 이벤트로 풀 문제가 아니라는 신호
- 이벤트에 데이터를 많이 담으면 결합되고 적게 담으면 리스너가 DB 를 다시 침<br>
  **ID 만 담고 필요하면 다시 조회**하는 것이 실무의 절충점
- 실패한 이벤트의 재처리 정책을 반드시 정할 것

## 4. 책임 연쇄 Chain of Responsibility

> 요청을 처리할 수 있는 객체들을 사슬로 연결하고<br>
> 요청을 사슬을 따라 전달하며 처리 담당자를 찾는 패턴

### 문제 및 동기

API 요청 전에 인증 · 권한 · 요청수 제한 · 입력 검증을 확인해야 함<br>
한 메서드에 `if` 로 나열하면

- 검증 하나 추가할 때마다 이 메서드를 수정
- 순서를 바꾸려면 코드를 옮겨야 함
- 일부 API 에만 적용하려면 또 분기가 붙음

전략 패턴과 비슷해 보이지만 다름<br>
전략은 **여럿 중 하나를 고르는 것**이고 여기는 **여럿을 순서대로 다 거치되 중간에 끊을 수 있어야 함**

### 해결 아이디어

각 검사를 독립 객체로 만들고 자기 다음 차례를 알게 함

```java
public abstract class Handler {

    private Handler next;

    public Handler setNext(Handler next) {
        this.next = next;
        return next;                                  // 체이닝을 위해 반환
    }

    protected Response passToNext(Request req) {
        return (next != null) ? next.handle(req) : Response.ok();
    }
}

public class AuthHandler extends Handler {
    public Response handle(Request req) {
        if (!isAuthenticated(req)) return Response.unauthorized();  // 여기서 끊음
        return passToNext(req);                                     // 다음으로 넘김
    }
}
```

각 핸들러는 **두 가지 선택만** 함 — 여기서 끝내거나 다음에게 넘기거나<br>
순서를 바꾸려면 조립 코드의 줄 순서만 바꾸면 됨

### 적용 대상

- 여러 검사나 처리 단계를 순서대로 통과시켜야 할 때
- 단계 추가와 순서 변경이 잦을 때
- 조건에 따라 처리를 중단해야 할 때

### 구조

| 역할 | 책임 |
|---|---|
| Handler | 요청 처리 인터페이스와 다음 핸들러 참조 |
| ConcreteHandler | 처리하거나 다음에게 전달 |
| Client | 사슬을 조립하고 첫 핸들러에 요청 |

### GoF 원형과 실무 변형

| 구분 | 동작 |
|---|---|
| GoF 원형 | 누군가 하나가 처리하면 끝 — 결재 승인 같은 것 |
| 실무 필터 체인 | 전부 통과하는 것이 정상이고 문제가 있을 때만 중단 |

실무에서 만나는 것은 대부분 후자

### 실무 위치 — 서블릿 필터가 바로 이것

```java
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
    if (!isAuthenticated(req)) {
        ((HttpServletResponse) res).sendError(401);
        return;                          // 체인 중단
    }
    chain.doFilter(req, res);            // 다음 필터로
}
```

`chain.doFilter` 가 `passToNext` 와 정확히 같은 역할<br>
스프링 시큐리티는 이 필터를 15개 넘게 순서대로 엮어놓은 체인

스프링 MVC 인터셉터 · OkHttp 와 Feign 의 Interceptor · AOP 의 `MethodInterceptor`

### 주의할 점

**다음으로 넘기는 호출을 빠뜨리는 실수가 압도적으로 많음**<br>
에러도 예외도 안 나고 요청이 조용히 사라져 응답이 안 옴 — 원인 찾기가 매우 어려움

순서 의존성이 있고 스택 트레이스가 깊어지며 아무도 처리하지 않는 경우도 대비해야 함

### 데코레이터와의 구분

| | 데코레이터 | 책임 연쇄 |
|---|---|---|
| 원본 도달 | 반드시 도달 | 중간에 끊는 것이 정상 |
| 목적 | 기능 추가 | 처리 담당자 찾기 · 통과 여부 판단 |
| 최종 처리자 | 반드시 존재 | 없을 수도 있음 |

## 5. 반복자 Iterator

> 내부 표현을 노출하지 않고 집합 객체의 원소들에 순차적으로 접근하는 방법을 제공하는 패턴

### 문제 및 동기

컬렉션이 내부 배열을 그대로 반환하면

- 내부 구조가 새어 나가 나중에 자료구조를 바꾸면 클라이언트가 전부 깨짐
- null 체크와 유효 범위를 클라이언트가 신경 써야 함
- 컬렉션에 현재 위치를 두면 두 곳에서 동시에 순회할 수 없음

### 해결 아이디어

순회 상태를 별도 객체로 뺌

```java
public Iterator<Book> iterator() {
    return new Iterator<>() {
        private int index = 0;                    // 순회 상태는 여기

        public boolean hasNext() { return index < count; }
        public Book next()       { return books[index++]; }
    };
}
```

클라이언트는 내부가 배열인지 리스트인지 모르고<br>
`iterator` 를 두 번 부르면 각자 자기 위치를 가진 독립된 반복자가 나옴

### 구조

| 역할 | 책임 |
|---|---|
| Iterator | `hasNext` · `next` 를 선언 |
| ConcreteIterator | 현재 위치를 관리하며 순회 |
| Aggregate | 반복자를 생성하는 인터페이스 |
| ConcreteAggregate | 자기에게 맞는 반복자를 반환 |

### Iterable 과 Iterator 의 구분

| | 의미 | 재사용 |
|---|---|---|
| `Iterable` | 나는 순회 가능하다 | 가능 |
| `Iterator` | 나는 지금 순회 중이다 | **한 번 쓰고 버림** |

`Iterable` 을 구현하는 것이 곧 향상된 for 문을 쓸 수 있게 만드는 것<br>
스트림도 이터레이터의 사촌이라 한 번만 씀 — 두 번 쓰면 `IllegalStateException`

### 순회 중 컬렉션 수정 — 실무 단골 예외

```java
for (User u : users) {
    if (u.isExpired()) users.remove(u);       // ConcurrentModificationException
}
```

반복자가 생성 시점의 컬렉션 상태를 기억해두고 매 `next` 마다 변경 여부를 확인함<br>
조용히 잘못 도는 것보다 즉시 터뜨리는 것이 낫다는 판단 — **fail-fast**

| 해결 | 방법 |
|---|---|
| 권장 | `it.remove()` 사용 |
| 간결 | `users.removeIf(User::isExpired)` |
| 함수형 | 스트림으로 필터링해 새 컬렉션 생성 |

### 외부 반복자와 내부 반복자

| 구분 | 진행 제어 | 예 |
|---|---|---|
| 외부 | 클라이언트가 `hasNext` · `next` 호출 | 자바 기본 |
| 내부 | 컬렉션이 순회하고 클라이언트는 할 일만 넘김 | `forEach` · 스트림 |

### 실무 위치

**JPA 페이지네이션** — 수백만 건을 못 올리니 잘라 가져오고 오프셋 관리는 뒤에 숨김<br>
**Kafka Consumer 의 `poll`** — 오프셋이 곧 현재 위치<br>
**Spring Batch 의 `ItemReader`** — `read` 가 다음 아이템을 반환하고 없으면 `null`<br>
**JDBC `ResultSet`** · MyBatis `Cursor`

직접 만들 일은 트리나 그래프 같은 커스텀 컬렉션을 제공할 때<br>
같은 트리에 대해 깊이 우선 · 너비 우선 등 여러 반복자를 제공하는 것이 이 패턴의 힘

## 6. 상태 State

> 객체의 내부 상태에 따라 행동을 변경할 수 있게 하여<br>
> 마치 객체의 클래스가 바뀐 것처럼 보이게 하는 패턴

### 문제 및 동기

주문 상태는 결제대기 → 결제완료 → 배송중 → 배송완료로 흐르고 상태마다 할 수 있는 일이 다름<br>
`pay` · `ship` · `cancel` · `refund` 모든 메서드에 상태별 분기가 반복됨

| 문제 | 내용 |
|---|---|
| 분기 중복 | 상태 하나 추가되면 **모든 메서드에 분기 하나씩** 추가 |
| 규칙 산재 | 전이 규칙이 코드 전체에 흩어져 전체를 한눈에 볼 수 없음 |

"이 주문은 지금 뭘 할 수 있지"를 알려면 모든 메서드를 다 읽어야 함

### 해결 아이디어

`if` 분기 대신 상태 자체를 클래스로 만들고 다음 상태를 반환하게 함

```java
public interface OrderState {
    OrderState pay(Order order);
    OrderState ship(Order order);
    OrderState cancel(Order order);
}

public class PendingState implements OrderState {
    public OrderState pay(Order o)    { return new PaidState(); }
    public OrderState ship(Order o)   { throw new IllegalStateException("결제 안 됨"); }
    public OrderState cancel(Order o) { return new CancelledState(); }
}

public class Order {
    private OrderState state = new PendingState();

    public void pay()  { this.state = state.pay(this); }
    public void ship() { this.state = state.ship(this); }
}
```

각 클래스가 자기 상태의 규칙만 안고 `Order` 는 위임만 함<br>
`PaidState` 파일 하나만 열면 결제완료 상태에서 할 수 있는 일을 완전히 파악할 수 있음

**상태 전이도에 화살표가 없다는 것 자체가 규칙**이 되어 코드와 그림이 1:1 로 대응함

### 적용 대상

- 상태에 따라 동작이 크게 달라지고 상태 수가 많을 때
- 전이 규칙이 도메인의 핵심일 때 — 결제 · 배송 · 예약 워크플로우
- 상태별로 필드나 의존성이 다를 때

### 구조

| 역할 | 책임 |
|---|---|
| Context | 현재 상태를 보유하고 위임 |
| State | 상태별 행동 인터페이스 |
| ConcreteState | 자기 상태의 규칙과 **다음 상태 결정** |

### 전략과의 결정적 차이

| | 전략 | 상태 |
|---|---|---|
| 누가 선택 | 외부에서 주입 | 객체가 **스스로 전이** |
| 언제 바뀜 | 보통 안 바뀜 | 실행 도중 계속 바뀜 |
| 서로 인식 | 서로 모름 | 다음 상태를 알아야 함 |

각 상태 메서드가 **다음 상태를 반환**하는 것이 이 패턴의 핵심 — 전략에는 이런 게 없음

### 실무 판단 — enum 형태가 대개 더 낫다

상태가 5개 정도이고 규칙이 단순하면 `enum` 에 담는 것이 훨씬 깔끔함

```java
public enum OrderStatus {
    PENDING {
        public OrderStatus pay()    { return PAID; }
        public OrderStatus cancel() { return CANCELLED; }
    },
    PAID {
        public OrderStatus ship()   { return SHIPPING; }
    };

    public OrderStatus pay()  { throw new IllegalStateException(); }
    public OrderStatus ship() { throw new IllegalStateException(); }
}
```

부모에 기본 동작으로 예외를 두고 각 상태가 허용된 전이만 오버라이드<br>
클래스 폭발이 없고 컴파일러가 누락을 잡아줌 — **실무에서 상태 패턴이라 하면 대부분 이 형태**

풀 클래스 구조가 정당해지는 경우

- 상태별로 필드가 다름 — 결제ID · 송장번호
- 상태별로 의존성이 다름 — 배송 상태만 배송 API 필요
- 상태별 로직이 각각 수십 줄

### 저장의 실무 문제

JPA 와 상태 패턴은 궁합이 나쁨 — `OrderState` 인터페이스를 어떻게 저장할 것인가<br>
실무에서는 **저장은 enum 으로 · 로직은 상태 객체로** 분리하거나 enum 에 로직을 함께 담음

### 실무 위치

Spring Statemachine · JPA 엔티티의 생명주기 · Spring Security 인증 흐름 · PG 결제 상태 머신

### 주의할 점

- 하이브리드 상태가 늘면 클래스가 폭증 — 상태를 두 축으로 나누는 것을 고려
- 전이 시 부작용의 위치를 정할 것 — 공통 부작용은 이벤트로 발행하는 것이 나음

## 7. 커맨드 Command

> 요청을 객체로 캡슐화하여<br>
> 요청의 매개변수화 · 큐잉 · 로깅 · 취소를 가능하게 하는 패턴

### 문제 및 동기

리모컨의 버튼마다 다른 기기를 다뤄야 하는데 버튼과 동작이 코드에 박혀 있으면

- 버튼 기능을 바꾸려면 코드를 고쳐야 함
- 리모컨이 세상 모든 기기의 인터페이스를 알아야 함
- 되돌리기를 붙일 수 없고 작업을 예약하거나 큐에 넣을 수도 없음

핵심 문제는 **"어떤 동작을 수행한다"는 사실이 코드에만 있고 데이터로는 존재하지 않는 것**

### 해결 아이디어

동작 하나를 클래스 하나로 만듦

```java
public interface Command { void execute(); }

public class AcSetTempCommand implements Command {
    private final AirConditioner ac;
    private final int temp;                       // 파라미터도 같이 담음

    public void execute() { ac.setTemp(temp); }
}

public class Remote {
    private Command[] buttons = new Command[10];
    public void press(int i) { buttons[i].execute(); }
}
```

리모컨은 이제 TV 도 에어컨도 모르고 `execute` 만 앎

### 진짜 힘 — 동작이 데이터가 됨

| 가능해진 것 | 방법 |
|---|---|
| 저장 | 히스토리 리스트에 담음 |
| 되돌리기 | `undo` 메서드와 이전 값 기억 |
| 큐잉 | 큐에 넣고 워커가 꺼내 실행 |
| 예약 | 스케줄러에 등록 |
| 직렬화 | DB 에 저장했다가 꺼내 실행 |

원천은 하나 — **"뭘 할지"가 코드가 아니라 객체이기 때문에 다른 객체처럼 취급할 수 있게 된 것**

### 적용 대상

- 실행 취소와 재실행이 필요할 때
- 작업을 나중에 하거나 다른 곳에서 해야 할 때 — 스케줄러 · 메시지 큐
- 여러 명령을 하나로 묶어 실행하는 매크로가 필요할 때
- 누가 언제 무엇을 했는지 감사 로그가 필요할 때

**오버킬인 경우**<br>
그냥 함수 호출로 충분하거나 · 취소도 큐도 로그도 필요 없거나 · 종류가 두세 개일 때

### 구조

| 역할 | 책임 |
|---|---|
| Command | `execute` 인터페이스 |
| ConcreteCommand | 수신자와 파라미터를 담고 실제 호출 |
| Invoker | 커맨드를 실행시키는 호출자 |
| Receiver | 실제 일을 하는 대상 |

호출자와 수신자 사이에 커맨드 객체가 **완충층**으로 들어간 것이 골격

### 실무 위치

**`Runnable` 과 `Callable` 이 커맨드**<br>
`ExecutorService` 가 하는 일이 정확히 이 패턴 — 동작을 객체로 만들어 큐에 넣고 워커가 꺼내 실행

**메시지 큐의 메시지도 본질적으로 커맨드**<br>
"실행할 일을 데이터로 표현해 저장 · 전송한다"는 정의 그대로<br>
커맨드가 프로세스를 넘어 시스템 경계까지 확장된 형태

**이벤트 소싱** — 현재 상태 대신 상태를 만든 커맨드들을 순서대로 저장하는 아키텍처<br>
Git 이 파일의 최종 형태 대신 커밋 히스토리를 저장하는 것과 같은 발상

### 실무 감각

요즘은 커맨드 클래스를 직접 만드는 일이 많이 줄었음 — 람다와 `@Async` · 이벤트 · 큐로 대체됨<br>
그래서 **"동작을 데이터로 다뤄야 하는 상황을 알아보는 관점"** 으로 익히는 것이 나음

### 전략과의 구분

| | 전략 | 커맨드 |
|---|---|---|
| 목적 | 같은 일을 다른 방식으로 | 실행할 일 자체를 캡슐화 |
| 파라미터 | 실행 시점에 받음 | 생성 시점에 담아둠 |

전략은 정렬을 오름차순으로 할까 내림차순으로 할까 — **어떻게**<br>
커맨드는 1번 주문을 처리해라 — **무엇을**

## 8. 중재자 Mediator

> 객체들이 서로 직접 참조하지 않도록 상호작용을 캡슐화하는 객체를 정의하여<br>
> 결합도를 낮추고 상호작용을 독립적으로 변경할 수 있게 하는 패턴

### 문제 및 동기

회원가입 폼에서 필드들이 서로 영향을 줌<br>
이메일이 입력되면 버튼 활성화 · 비밀번호가 다르면 비활성화 · 회원 유형에 따라 필드가 나타남

각 컴포넌트가 서로를 직접 알면 참여자 n 개일 때 참조가 **n(n−1) 개**까지 생김<br>
6개면 30개 · 10개면 90개이고 이 얽힘 하나하나가 변경 시 부담이 됨

### 해결 아이디어

컴포넌트끼리 직접 얘기하지 못하게 하고 **오직 중재자를 통해서만** 소통시킴

```java
public class SignupFormMediator implements FormMediator {

    public void notify(Component sender, String event) {
        if (sender == email || sender == password) {
            submit.setEnabled(email.isValid() && password.matches(passwordConfirm));
        }
        if (sender == userType) {
            businessNumber.setVisible(userType.getValue().equals("법인"));
        }
    }
}
```

협력 로직이 한 파일에 모이므로 폼 전체의 동작을 파악하려면 이 클래스만 읽으면 됨<br>
컴포넌트는 자기 상태만 알고 다른 필드의 존재를 신경 쓰지 않음

그물망이 **별 모양**으로 바뀌는 것이 이 패턴의 그림

### 적용 대상

- 여러 객체가 서로 참조하며 협력 규칙이 복잡하게 얽혀 있을 때
- 한 객체의 변화가 다른 여러 객체에 조건부 영향을 줄 때
- 서비스 간 결합을 낮춰 독립 배포하고 싶을 때

**쓰지 말아야 할 때** — 참여자가 두세 개고 관계가 단순할 때

### 구조

| 역할 | 책임 |
|---|---|
| Mediator | 협력 규칙 전체를 보유하고 통보를 받아 조정 |
| Colleague | 중재자만 알고 자기 사건을 알림 |

### 옵저버와의 관계

둘은 반대 관계가 아니라 **다른 관점**이며 스프링 이벤트는 양쪽으로 다 설명됨

| 관점 | 초점 | 협력 규칙 위치 |
|---|---|---|
| 옵저버 | 한 객체의 변화를 여러 객체가 구독 | **각 구독자에 분산** |
| 중재자 | 여러 객체의 협력을 한 지점에 집중 | **가운데 객체에 집중** |

폼처럼 규칙이 얽혀 있으면 중재자 · 발행자와 구독자가 독립적이면 옵저버<br>
스프링 이벤트는 규칙이 각 리스너에 분산되어 옵저버 쪽에 가까움

### 실무 위치

`ApplicationEventPublisher` · 메시지 큐 · `DispatcherServlet`<br>
MSA 에서 이벤트 기반 통신은 중재자의 발상이 시스템 규모로 커진 것

### 주의할 점

- **중재자가 신이 됨** — 규칙을 다 안고 있어 자연스럽게 비대해짐<br>
  도메인 단위로 쪼개거나 규칙을 별도 전략 객체로 뽑을 것
- 전체 흐름 추적이 어려움 — 특히 이벤트 기반일 때 심각함
- 순환 통보를 조심할 것 — 상태 변경 중 이벤트 발행을 막는 장치가 필요

## 9. 메멘토 Memento

> 캡슐화를 위반하지 않으면서 객체의 내부 상태를 붙잡아 외부에 저장하여<br>
> 나중에 그 상태로 복원할 수 있게 하는 패턴

### 문제 및 동기

편집기에 되돌리기를 붙이려면 이전 상태를 저장해야 하는데

- 상태가 여러 필드에 걸쳐 있어 필드마다 히스토리를 두면 관리가 지옥이 됨
- 되돌리기 로직이 편집기 본연의 일에 끼어듦
- 필드가 `private` 이라 히스토리를 밖으로 옮길 수도 없음

핵심 딜레마는 **되돌리려면 내부 상태에 접근해야 하는데 캡슐화는 유지하고 싶다는 것**

### 해결 아이디어

상태를 통째로 담은 **불투명한 객체**를 밖으로 내보내되 안은 못 보게 함

```java
public class Editor {

    public static class Snapshot {
        private final String content;
        private final int cursorPos;
        private Snapshot(String content, int cursorPos) { ... }   // private 생성자
    }

    public Snapshot save() { return new Snapshot(content, cursorPos); }

    public void restore(Snapshot s) {
        this.content = s.content;                                 // 같은 클래스라 접근 가능
        this.cursorPos = s.cursorPos;
    }
}
```

`History` 는 스냅샷을 스택에 쌓고 꺼낼 뿐 안에 뭐가 들었는지 모름<br>
편집기에 필드가 추가되어도 `save` 와 `restore` 만 고치면 되고 히스토리는 그대로

### 구조

| 역할 | 예 | 책임 |
|---|---|---|
| Originator 원조자 | `Editor` | 자기 상태를 봉인하고 복원 |
| Memento 기념품 | `Snapshot` | 봉인된 상태 · 원조자만 안을 봄 |
| Caretaker 관리자 | `History` | 스냅샷을 보관 · 안을 절대 안 봄 |

핵심은 **양방향 접근 제어** — 원조자는 자유롭게 읽고 관리자는 참조로만 다룸

### 커맨드와의 관계

커맨드의 `undo` 에서 이전 값을 필드로 들고 있는 것이 스냅샷의 아주 작은 형태<br>
상태가 커지면 **커맨드는 "무엇을 했는가" · 메멘토는 "그 시점의 상태 전체"** 로 역할을 나눔<br>
실무에서는 커맨드가 실행 전 메멘토를 만들어 들고 있는 형태로 조합됨

### 실무 위치

**JPA 더티 체킹** — 하이버네이트가 조회 시점의 상태를 저장해두고 커밋 시 비교해 변경 필드만 UPDATE<br>
**Spring Batch 재시작** — 실행 컨텍스트를 저장해 마지막 성공 지점부터 이어감<br>
**트랜잭션 롤백** — 언두 로그가 곧 메멘토 저장소

### 주의할 점

- 매 스냅샷마다 전체를 복사하면 메모리 부담 — 증분 저장이나 불변 자료구조 활용
- 가변 컬렉션을 참조로 저장하면 원본 변경 시 스냅샷이 오염됨 — 프로토타입의 얕은 복사 문제와 동일
- 히스토리 최대 개수를 제한할 것

## 10. 방문자 Visitor

> 객체 구조의 원소에 수행할 연산을 별도 객체로 분리하여<br>
> 원소 클래스를 변경하지 않고 새로운 연산을 추가할 수 있게 하는 패턴

### 문제 및 동기

조직도 트리에 인원수 세기 · JSON 직렬화 · CSV 내보내기가 계속 추가됨<br>
컴포지트 방식으로는 새 기능마다 인터페이스에 메서드가 추가되고 모든 노드가 구현을 강요받음<br>
게다가 JSON 변환이 정말 `Employee` 의 책임인지 의문이고 라이브러리 의존성이 도메인에 침투함

### 표현 문제 Expression Problem

| 축 | 컴포지트 | 방문자 |
|---|---|---|
| 노드 타입 추가 | **쉬움** | 모든 방문자 수정 |
| 연산 추가 | 모든 노드 수정 | **쉬움** |

**노드 종류가 안정적이고 연산이 계속 늘어난다면** 방문자가 유리함

### 해결 아이디어

연산을 하나의 객체로 뽑고 노드는 방문자를 받아들이기만 함

```java
public interface OrgVisitor<R> {
    R visitEmployee(Employee e);
    R visitDepartment(Department d);
}

public class Employee implements OrgUnit {
    public <R> R accept(OrgVisitor<R> visitor) {
        return visitor.visitEmployee(this);       // 자신이 어느 타입인지 알림
    }
}
```

```java
long totalSalary = root.accept(new SalarySumVisitor());
int  memberCount = root.accept(new MemberCountVisitor());
```

새 연산은 방문자 클래스 하나로 끝나고 노드 클래스는 열지 않음

### 왜 이중 위임인가 — 더블 디스패치

자바는 **단일 디스패치** 언어라 정적 타입만 보고 오버로딩을 고름<br>
그래서 노드에게 `accept` 를 부르면 노드가 자기 타입을 알고 정확한 `visitXxx` 를 골라주는 트릭이 필요함

`node.accept(visitor)` 로 노드 타입이 결정되고 `visitor.visitXxx(this)` 로 방문자 타입이 결정되어<br>
노드 타입 × 방문자 타입 조합마다 정확한 메서드가 호출됨

Kotlin 이나 Scala 처럼 패턴 매칭이 있으면 이 트릭이 필요 없어 방문자의 중요도가 낮음

### 결정적 약점

새 노드 타입이 추가되면 인터페이스가 바뀌어 **기존 방문자 전부가 컴파일 에러**<br>
방문자가 10개면 10개를 다 손봐야 함 — **노드가 자주 늘어나는 도메인엔 쓰면 안 됨**

### 적용 대상

**맞는 예** — 컴파일러 AST · 문법 트리 순회 · 파일 시스템 순회<br>
**틀린 예** — 도메인 모델이 성장 중이거나 연산이 두세 개뿐일 때

### 데코레이터와의 구분

| | 데코레이터 | 방문자 |
|---|---|---|
| 대상 | 한 인터페이스의 기존 메서드 | 여러 타입의 계층 전체 |
| 추가하는 것 | 기존 동작의 부가 요소 | 없던 새 연산 |
| 원본 호출 | 반드시 함 | 안 함 · 자기가 처리 |
| 확장 방향 | 세로 — 실행 파이프라인을 늘림 | 가로 — 타입들에 걸쳐 연산을 붙임 |

데코레이터는 커피에 시럽을 얹는 것이고 방문자는 도서관에 감정사와 사서가 방문하는 것

### 실무 위치

ANTLR 파서의 AST 순회 · JPA Criteria 의 쿼리 트리 · 자바의 `FileVisitor`<br>
웹 백엔드에서 직접 구현할 일은 사실상 없고 프레임워크 안에서 소비함

## 11. 인터프리터 Interpreter

> 언어의 문법을 클래스로 표현하고 그 표현을 사용해 문장을 해석하는 패턴

### 문제 및 동기

관리자가 `"price < 10000 AND (category = 'shirt' OR category = 'pants')"` 같은 문자열로<br>
조건을 넣을 수 있게 해야 함 — 무한히 중첩되고 조합도 그때그때 다름

### 해결 아이디어

**문법의 각 요소마다 클래스 하나**를 대응시킴

```java
public interface Expression { boolean interpret(Product product); }

public class LessThan implements Expression { ... }    // price < 10000
public class Equals   implements Expression { ... }    // category = 'shirt'

public class And implements Expression {
    private final Expression left, right;
    public boolean interpret(Product p) {
        return left.interpret(p) && right.interpret(p);
    }
}
```

문자열을 이 트리로 바꾸는 파서는 엄밀히는 패턴의 범위 밖이지만 실무에서는 함께 다루게 됨

### 컴포지트와의 차이

구조는 같지만 관점이 다름

| | 컴포지트 | 인터프리터 |
|---|---|---|
| 트리의 의미 | 일반적인 트리 구조 | **문법의 문장** |
| 연산의 의미 | 자식 결과 합산 | 그 언어의 의미를 실행 |

### 실무 위치와 판단

SpEL · QueryDSL `BooleanExpression` · 정규표현식 엔진 · Drools · 엘라스틱서치 쿼리 DSL

**직접 구현할 일은 사실상 없음**

- 진짜 파서는 연산자 우선순위 · 괄호 · 에러 복구까지 필요해 손으로 짜면 버그 온상이 됨
- 필요하면 ANTLR 같은 파서 생성기나 SpEL 을 갖다 씀
- 표현식 평가 수준이면 컴포지트로 충분함 — 조건 트리를 JSON 으로 저장하는 방식이 훨씬 흔함

GoF 스스로도 문법이 단순하고 변경 빈도가 낮을 때만 쓰라고 명시함<br>
**만들려고가 아니라 알아보려고 배우는 패턴**

## 🔑 최종 정리

행위 패턴은 "누가 무엇을 하고 어떻게 소통하나"를 다루며 크게 세 갈래로 묶임

**알고리즘과 절차를 다루는 것**

- **전략** — 알고리즘을 통째로 교체 · 합성 기반
- **템플릿 메서드** — 절차는 고정하고 구멍만 채움 · 상속 기반
- **상태** — 상태에 따른 분기를 상태 객체에 위임 · 스스로 전이

**요청과 흐름을 다루는 것**

- **커맨드** — 실행할 동작 자체를 객체로 만듦
- **책임 연쇄** — 처리기를 줄로 세워 넘기거나 중단
- **인터프리터** — 문법 요소를 클래스로 만들어 문장을 실행

**객체 사이 소통을 다루는 것**

- **옵저버** — 사건을 발행하면 구독자들이 자동 반응
- **중재자** — 얽힌 소통을 한 지점으로 모아 그물망을 별 모양으로
- **반복자** — 순회 방법을 컬렉션에서 떼어냄
- **메멘토** — 상태를 봉인해 저장하고 복원
- **방문자** — 연산을 노드 계층 밖으로 뺌

특히 헷갈리는 조합의 판별법

| 비교 | 결정적 차이 |
|---|---|
| 전략 대 상태 | 외부가 선택하는가 · 객체가 스스로 전이하는가 |
| 전략 대 템플릿 메서드 | 합성인가 상속인가 · 통째로 바꾸는가 일부만 바꾸는가 |
| 전략 대 커맨드 | 어떻게 할지인가 · 무엇을 할지인가 |
| 옵저버 대 중재자 | 협력 규칙이 구독자에 분산인가 중앙에 집중인가 |
| 데코레이터 대 책임 연쇄 | 원본에 반드시 도달하는가 · 중간에 끊는 것이 정상인가 |

실무 체감으로는 전략 · 템플릿 메서드 · 옵저버 · 책임 연쇄 · 반복자를 스프링에서 매일 소비하고<br>
상태와 커맨드는 도메인이 요구할 때 꺼내며 나머지는 알아보는 눈을 갖는 것으로 충분함

> **한 줄 요약:** 행위 패턴은 객체 사이의 책임과 소통 방식을 다루는 열한 가지 방법이며 알고리즘 교체 · 절차 고정 · 요청 전달 · 사건 통보 중 무엇이 문제인지에 따라 선택이 갈린다
