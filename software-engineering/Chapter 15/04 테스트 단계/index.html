    테스트 단계¶

    단위 테스트¶

    모듈이 정확히 동작하는지를 테스트

    • 화이트박스 테스트 가능
    • 함수, 모듈, 태스크, 화면 단위가 테스트 대상

    고려 사항

    • 어떻게 예상 결과를 작성할 것인가
    • 드라이버와 스텁을 개발해야 한다
    단위 테스트에서 화이트박스 테스트가 가능한 이유는? 테스트 대상이 작아 내부 코드 구조를 전부 파악할 수 있음
    분기와 경로가 한정되어 있어 커버리지 기준을 적용하기 쉬움
    통합 이후 단계는 대상이 커져 내부 구조를 다 보기 어려우므로 블랙박스 위주가 됨
    예상 결과 작성이 왜 고려 사항이 되는가? 모듈 단위는 명세가 요구사항 수준으로 자세히 적혀 있지 않은 경우가 많음
    그래서 어떤 입력에 어떤 값이 나와야 하는지를 테스터가 직접 판단해야 함
    판단 근거가 모호하면 결과가 틀렸는지조차 알 수 없으므로 오라클 문제와 직결됨

    통합 테스트¶

    단위 테스트를 통과한 모듈들이 통합되어 실행될 때 발생할 수 있는 문제를 검사하기 위한 활동

    모듈 간의 상호작용, 인터페이스 일관성에 관심

    통합 시 발견되는 문제

    • 인터페이스가 잘못 사용된 경우
    • 모듈 기능 구현에 대한 잘못된 가정이 존재하는 경우
    • 테스트 드라이버와 스텁에 오류가 존재하는 경우
    단위 테스트를 다 통과했는데 왜 통합에서 문제가 생기는가? 각 모듈이 상대 모듈의 동작을 나름대로 가정한 채 만들어졌기 때문임
    단위 테스트에서는 그 가정대로 동작하는 스텁을 쓰므로 가정이 틀려도 드러나지 않음
    매개변수의 단위나 순서, null 허용 여부, 예외 처리 책임이 어긋나는 경우가 대표적임
    그래서 통합 테스트의 관심은 모듈 내부가 아니라 인터페이스임

    비점증적 통합¶

    모든 모듈을 한 번에 통합해 테스트하는 방식

    • 테스트 실행을 한 번에 할 수 있다
    • 결함의 원인이 무엇인지 식별하기 어렵다

    점증적 통합¶

    단위 모듈을 한 번에 하나만 통합해 테스트하는 방식

    • 단위 모듈이 추가될 때마다 테스트 수행
    • 오류 검출이 매우 쉬움
    • 통합되지 않은 모듈에 대한 스텁을 개발해야 함
    구분 비점증적 통합 점증적 통합
    통합 방식 한 번에 전부 하나씩 추가
    테스트 횟수 적음 많음
    결함 원인 파악 어려움 쉬움
    드라이버·스텁 적게 필요 많이 필요
    적용 대상 소규모 시스템 대부분의 실제 프로젝트
    점증적 통합이 결함 원인을 찾기 쉬운 이유는? 모듈 하나를 추가한 직후에 오류가 나면 방금 추가한 모듈이나 그 인터페이스가 원인임
    용의자가 한정되므로 추적 범위가 좁아짐
    반면 비점증적 통합은 전부 붙인 뒤 오류가 나므로 어느 연결에서 터졌는지 알 수 없음

    모듈 통합 방식¶

    방식 통합 순서 필요한 임시 모듈 특징
    하향식 통합 상위 모듈에서 하위 모듈로 스텁 주요 제어 구조를 조기에 검증, 하위 모듈 결함은 늦게 발견
    상향식 통합 하위 모듈에서 상위 모듈로 드라이버 하위 모듈을 충실히 검증, 전체 구조는 늦게 확인
    스레드 기반 통합 하나의 기능을 구성하는 모듈들을 묶어서 드라이버·스텁 기능 단위로 동작을 조기에 확인 가능
    샌드위치 통합 상위와 하위에서 동시에 시작해 중간에서 만남 드라이버·스텁 모두 두 방식의 장점을 결합, 관리 복잡
    핵심 모듈 기반 통합 중요도·위험도가 높은 모듈부터 드라이버·스텁 위험이 큰 부분을 먼저 검증
    하향식 통합에서 스텁이 필요한 이유는? 상위 모듈부터 통합하므로 그 상위 모듈이 호출할 하위 모듈이 아직 없음
    호출 대상이 없으면 실행 자체가 되지 않으므로 미리 정한 값을 돌려주는 스텁으로 대신함
    반대로 상향식은 하위 모듈부터 만들어 호출해 줄 상위 모듈이 없으므로 드라이버가 필요함
    스레드 기반 통합의 장점은? 계층 순서가 아니라 하나의 기능이 지나가는 모듈들을 묶어 통합함
    로그인이면 화면부터 인증 로직, 데이터 접근까지 한 줄로 붙여 검증함
    전체가 완성되기 전에도 실제로 동작하는 기능을 확인할 수 있어 조기 피드백에 유리함

    시스템 테스트¶

    시스템이 사용될 하드웨어 플랫폼에 설치된 뒤 수행하는 테스트

    기능뿐만 아니라 성능 등의 품질에도 관심

    유형 확인 내용
    기능 테스트 요구사항의 기능이 모두 동작하는가
    성능 테스트 응답 시간과 처리량이 기준을 만족하는가
    부하·스트레스 테스트 한계를 넘는 부하에서 어떻게 동작하는가
    보안 테스트 비인가 접근과 데이터 유출을 막는가
    호환성 테스트 지정된 환경과 브라우저에서 동작하는가
    복구 테스트 장애 발생 후 정상 상태로 돌아오는가
    설치 테스트 실제 환경에 설치와 제거가 정상 수행되는가
    단위·통합 테스트 환경과 무엇이 다른가? 개발 환경이 아니라 실제 운영될 하드웨어와 네트워크 위에서 수행함
    개발 환경에서는 드러나지 않던 자원 부족, 설정 차이, 외부 시스템 연동 문제가 여기서 나타남
    그래서 기능 확인을 넘어 성능과 안정성 같은 비기능 요구사항이 주요 대상이 됨

    인수 테스트¶

    시스템을 사용자에게 전달하기 전에 수행하는 테스트

    종류 수행 주체 장소·방식
    알파 테스트 전문적 지식이 있는 사용자 일부를 테스터로 선정 개발자가 관찰하는 통제된 환경
    베타 테스트 실제 사용자 사용자 환경에서 일정 기간 시범적으로 운영
    감마 테스트 사용자 성능, 사용 편의성 같은 품질 항목을 확인
    알파 테스트와 베타 테스트의 결정적 차이는? 알파 테스트는 개발자가 함께 있는 통제된 환경에서 수행함
    문제가 발생하면 개발자가 즉시 관찰하고 기록할 수 있음
    베타 테스트는 개발자가 없는 실제 사용 환경에서 진행되므로 사용자가 문제를 보고해야 함
    대신 예상하지 못한 사용 방식과 환경에서 나오는 결함을 발견할 수 있음

    회귀 테스트¶

    소프트웨어에 대해 기능을 추가하거나 결함을 제거한 후 수행하는 테스트

    새로운 결함이 없는지 확인

    방식 내용 특징
    전수 회귀 테스트 기존 테스트 케이스를 전부 재실행 가장 안전하지만 비용이 큼
    선택적 회귀 테스트 변경의 영향을 받는 케이스만 골라 실행 영향 범위 분석이 정확해야 함
    우선순위 기반 회귀 테스트 중요도가 높은 케이스부터 순서대로 실행 시간이 부족해도 핵심은 검증됨
    회귀 테스트에 자동화가 필수인 이유는? 같은 케이스를 변경이 있을 때마다 반복 실행해야 함
    수동으로 하면 실행 비용이 커서 결국 생략하게 되고, 생략하는 순간 의미가 사라짐
    자동화하면 실행 비용이 거의 0에 가까워져 전수 회귀 테스트도 현실적으로 가능해짐

    테스트 단계 정리¶

    단계 대상 주 관심사 주 기법
    단위 테스트 함수·모듈 모듈 내부 로직 화이트박스
    통합 테스트 모듈 묶음 인터페이스 일관성 블랙박스 + 일부 화이트박스
    시스템 테스트 시스템 전체 기능과 품질 속성 블랙박스
    인수 테스트 사용자 관점의 시스템 요구사항 충족 여부 블랙박스
    회귀 테스트 변경 영향 범위 기존 기능의 보존 기존 케이스 재사용

    🔑 최종 정리¶

    한 줄 요약: 테스트 단계는 모듈 내부에서 인터페이스, 시스템 품질, 사용자 수용으로 관심사를 넓혀 가는 순서이며, 변경이 생길 때마다 회귀 테스트로 그동안 확보한 품질을 지킨다.
