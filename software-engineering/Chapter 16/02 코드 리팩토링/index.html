    코드 리팩토링¶

    코드 기능은 그대로 두고, 내부 구조를 개선하는 것

    • 가독성과 이해도 향상
    • 유지보수성 향상
    • 결함 발견이 쉬워지고 확장에 유리해짐

    마틴 파울러 코드 리팩토링 기법¶

    1. 메서드 구성¶

    No. 기법 설명
    R1 메서드 추출 묶을 수 있는 코드 조각을 의도가 드러나는 이름의 메서드로 분리
    R2 인라인 메서드 본문이 이름만큼 명확하면 호출부에 본문을 넣고 메서드 제거
    R3 인라인 임시 변수 단순 대입만 받는 임시 변수를 원래 식으로 대체
    R4 임시 변수를 질의로 대체 임시 변수를 메서드로 추출해 다른 곳에서도 재사용
    R5 설명 변수 도입 복잡한 식의 일부를 의미 있는 이름의 변수에 담기
    R6 임시 변수 분리 여러 용도로 재사용되는 임시 변수를 용도별로 분리
    R7 매개변수 할당 제거 매개변수에 값을 대입하지 말고 별도 지역 변수 사용
    R8 메서드를 메서드 객체로 대체 지역 변수가 많아 추출이 어려운 긴 메서드를 하나의 클래스로 변환
    R9 알고리즘 대체 알고리즘을 더 명확한 것으로 통째로 교체

    2. 객체 간 특성 이동¶

    No. 기법 설명
    R10 메서드 이동 다른 클래스의 기능을 더 많이 쓰는 메서드를 그 클래스로 옮김
    R11 필드 이동 필드를 더 자주 사용하는 클래스로 옮김
    R12 클래스 추출 두 가지 책임을 가진 클래스를 나눠 새 클래스 생성
    R13 인라인 클래스 하는 일이 거의 없는 클래스를 다른 클래스에 흡수
    R14 위임 감추기 위임 객체를 직접 노출하지 않고 감싸는 메서드 제공
    R15 중간자 제거 단순 위임만 하는 메서드가 지나치게 많으면 클라이언트가 직접 호출
    R16 외부 메서드 도입 수정할 수 없는 클래스의 기능이 필요하면 클라이언트 쪽에 메서드 작성
    R17 지역 확장 도입 수정 불가 클래스에 기능이 여러 개 필요하면 서브클래스나 래퍼로 확장

    3. 데이터 구조화¶

    No. 기법 설명
    R18 자체 캡슐화 필드 자기 클래스 안에서도 필드를 접근자로 사용
    R19 데이터 값을 객체로 대체 의미와 동작이 붙는 데이터 항목을 별도 객체로 승격
    R20 값을 참조로 대체 같은 실체를 공유해야 하면 참조 객체로 변경
    R21 참조를 값으로 대체 작고 불변이며 관리 부담이 크면 값 객체로 변경
    R22 배열을 객체로 대체 요소마다 의미가 다른 배열을 필드를 가진 객체로 변경
    R23 관찰 데이터 복제 GUI에 있는 도메인 데이터를 도메인 객체로 분리하고 옵저버로 동기화
    R24 단방향 관계의 양방향 변경 반대편에서도 참조가 필요하면 양방향으로
    R25 양방향 관계의 단방향 변경 쓰이지 않는 역참조를 제거해 결합도 낮춤
    R26 매직 넘버의 기호 상수화 의미 없는 숫자 리터럴을 이름 있는 상수로
    R27 필드 캡슐화 public 필드를 private로 바꾸고 접근자 제공
    R28 집합 캡슐화 컬렉션은 읽기 전용으로 반환하고 추가/삭제 메서드를 따로 제공
    R29 레코드를 데이터 클래스로 대체 외부 인터페이스용 레코드 구조를 클래스로 감쌈
    R30 타입 코드를 클래스로 대체 동작에 영향을 주지 않는 타입 코드를 클래스로
    R31 타입 코드를 서브 클래스로 대체 타입에 따라 동작이 다르고 타입이 변하지 않을 때
    R32 타입 코드를 상태로 대체 타입이 도중에 바뀔 수 있을 때 상태/전략 패턴 적용
    R33 서브 클래스를 필드로 대체 상수만 다르게 반환하는 서브 클래스를 필드로 통합

    4. 조건절 단순화¶

    No. 기법 설명
    R34 조건 분리 복잡한 조건식과 각 분기를 의미 있는 메서드로 추출
    R35 조건절 통합 결과가 같은 여러 조건을 하나로 합쳐 메서드로 추출
    R36 중복 조건의 통합 모든 분기에 공통으로 있는 코드를 조건문 밖으로 이동
    R37 제어 플래그 제거 반복 제어용 boolean 플래그를 break/return으로 대체
    R38 중첩 조건을 가드절로 대체 특이 케이스는 앞에서 즉시 반환해 중첩 제거
    R39 조건을 다형성으로 대체 타입 검사 조건문을 서브 클래스의 오버라이딩으로 대체
    R40 널 객체 도입 반복되는 null 검사를 "아무것도 안 하는 객체"로 대체
    R41 단언문 도입 반드시 참이어야 하는 가정을 assert로 코드에 명시

    5. 메서드 호출 단순화¶

    No. 기법 설명
    R42 메서드 재명명 하는 일이 드러나도록 이름 변경
    R43 매개변수 추가 필요한 정보를 얻기 위해 매개변수 추가
    R44 매개변수 제거 더 이상 쓰이지 않는 매개변수 제거
    R45 수정자에서 질의 분리 값 반환과 상태 변경을 하나의 메서드에서 동시에 하지 않도록 분리
    R46 매개변수화된 메서드 값만 다른 비슷한 메서드들을 매개변수 하나로 통합
    R47 매개변수를 기존 메서드로 대체 매개변수 값에 따라 동작이 완전히 갈리면 별도 메서드로 분리
    R48 전체 객체 보존 객체에서 값을 여러 개 꺼내 넘기지 말고 객체 자체를 전달
    R49 매개변수를 메서드로 대체 수신 객체가 스스로 구할 수 있는 값은 매개변수에서 제거
    R50 매개변수 객체 도입 항상 함께 다니는 매개변수 묶음을 하나의 객체로
    R51 설정 메서드 제거 생성 후 변경되면 안 되는 필드의 setter 제거
    R52 메서드 감추기 외부에서 쓰이지 않는 메서드의 가시성을 private로 낮춤
    R53 생성자를 팩토리 메서드로 대체 생성 시 조건 판단이나 타입 선택이 필요하면 팩토리 메서드 사용
    R54 다운캐스트 캡슐화 캐스팅을 호출자에게 떠넘기지 말고 메서드 안에서 처리해 반환
    R55 에러 코드를 예외 처리로 대체 반환값으로 오류를 알리지 말고 예외를 던짐
    R56 예외 처리를 테스트로 대체 사전 조건 검사로 피할 수 있는 예외는 조건문으로 대체

    6. 일반화하기¶

    No. 기법 설명
    R57 필드 올리기 서브 클래스들의 동일한 필드를 슈퍼 클래스로 이동
    R58 메서드 올리기 서브 클래스들의 동일한 메서드를 슈퍼 클래스로 이동
    R59 생성자 몸체 올리기 서브 클래스 생성자의 공통 부분을 슈퍼 클래스 생성자로 이동
    R60 메서드 내리기 일부 서브 클래스에만 해당하는 메서드를 아래로 이동
    R61 필드 내리기 일부 서브 클래스에만 쓰이는 필드를 아래로 이동
    R62 서브 클래스 추출 일부 인스턴스에만 쓰이는 특성을 서브 클래스로 분리
    R63 슈퍼 클래스 추출 비슷한 두 클래스의 공통 부분을 슈퍼 클래스로 추출
    R64 인터페이스 추출 클라이언트가 사용하는 부분집합을 인터페이스로 추출
    R65 계층 구조 해체 슈퍼 클래스와 서브 클래스가 거의 같으면 하나로 합침
    R66 템플릿 메서드 구성 순서는 같고 세부만 다른 메서드를 상위에 골격, 하위에 구현으로 분리
    R67 상속을 위임으로 대체 슈퍼 클래스 기능의 일부만 쓴다면 상속 대신 위임
    R68 위임을 상속으로 대체 위임 메서드가 지나치게 많고 전부 사용한다면 상속으로 전환

    실제 적용 사례¶

    사례 1. 메서드 추출 + 조건 분리 + 매직 넘버 상수화 - R26 + R34¶

    Before

    public boolean hasValidChoices() {
    if (choices.size() != 4 ) {
        return false;
    }
    if (choices.stream().anyMatch(choice -> choice == null || choice.isBlank())) {
        return false;
    }
    if (choices.stream().distinct().count() != choices.size()) {
        return false;
    }
    return choices.stream().filter(choice -> choice.equals(answer)).count() == 1;
}

    After

    public static final int CHOICES_NUMBER = 4;          // R26

public boolean hasValidChoices() {                    // R34
    return hasRequiredChoiceCount()
            && hasNoBlankChoice()
            && hasNoDuplicateChoice()
            && containsAnswer();
}

private boolean hasRequiredChoiceCount() { return choices.size() == CHOICES_NUMBER; }
private boolean hasNoBlankChoice()       { return choices.stream().noneMatch(String::isBlank); }
private boolean hasNoDuplicateChoice()   { return choices.stream().distinct().count() == choices.size(); }
private boolean containsAnswer()         { return answer != null && choices.contains(answer); }

    사례 2. 매개변수를 기존 메서드로 대체 - R47¶

    boolean / null 시그널 파라미터로 분기하던 메서드를 동사별 메서드로 분리.

    Before — 하나의 update가 파라미터 유무에 따라 여러 일을 함

    public QuizFolder update(String memberId, String folderId, String name, Boolean active) {
    if (name == null && active == null) {
        throw new IllegalArgumentException("name과 active 중 최소 하나는 포함해야 합니다.");
    }
    QuizFolder folder = loadOwnedFolder(memberId, folderId);
    if (name != null)   { folder.rename(name); }
    if (active != null) { if (active) folder.activate(); else folder.deactivate(); }
    folderRepository.save(folder);
    return folder;
}

    After — 인자로 분기하지 않고, 메서드를 분리

    public QuizFolder rename(String memberId, String folderId, String name) { ... }
public QuizFolder activate(String memberId, String folderId)   { ... folder.activate();   ... }
public QuizFolder deactivate(String memberId, String folderId) { ... folder.deactivate(); ... }

    사례 3. 메서드 이동 + 메서드 재명명 + 메서드 감추기 - R10 + R42 + R52¶

    // Before — QuizFolder에 있던 public static 메서드
public static Quiz draftToQuiz(QuizCommand command, String folderId, Instant now) {
    int answerNumber = command.choices().indexOf(command.answer());
    return new Quiz(UUID.randomUUID().toString(), folderId,
            command.question(), command.choices(), answerNumber, true, ...);
}

// After — Quiz로 이동(R10) + 이름 변경(R42) + 가시성 축소(R52)
private static Quiz from(QuizCommand command, String folderId, Instant now) {

    R38. 중첩 조건을 가드절로 대체¶

    정상 경로를 들여쓰기 깊이에서 꺼내는 기법
    예외·특이 케이스는 위에서 먼저 처리하고 반환

    // Before — 진짜 하려는 일(주문 취소)이 3단계 안쪽에 숨어 있음
public void cancelOrder(Order order) {
    if (order != null) {
        if (order.getStatus() == OrderStatus.PAID) {
            if (!order.isShipped()) {
                order.cancel();
                refundService.refund(order);
            } else {
                throw new AlreadyShippedException();
            }
        } else {
            throw new NotCancelableException();
        }
    } else {
        throw new OrderNotFoundException();
    }
}

// After — 못 하는 경우를 먼저 걸러내고, 정상 흐름은 맨 아래 한 덩어리
public void cancelOrder(Order order) {
    if (order == null) throw new OrderNotFoundException();
    if (order.getStatus() != OrderStatus.PAID) throw new NotCancelableException();
    if (order.isShipped()) throw new AlreadyShippedException();

    order.cancel();
    refundService.refund(order);
}

    R39. 조건을 다형성으로 대체¶

    타입에 따라 갈리는 switch/if를 서브타입의 오버라이딩으로 옮긴다

    새 타입이 추가될 때 조건문을 찾아다니며 고치지 않아도 된다

    // Before — 결제 수단이 추가될 때마다 이 switch를 찾아 고쳐야 함
public int calculateFee(PaymentType type, int amount) {
    switch (type) {
        case CARD:     return (int) (amount * 0.025);
        case TRANSFER: return 300;
        case POINT:    return 0;
    }
    throw new IllegalArgumentException("지원하지 않는 결제 수단입니다.");
}

// After — 각 결제 수단이 자기 수수료 계산을 책임짐
public interface PaymentMethod {
    int calculateFee(int amount);
}

public class CardPayment implements PaymentMethod {
    public int calculateFee(int amount) { return (int) (amount * 0.025); }
}

public class TransferPayment implements PaymentMethod {
    public int calculateFee(int amount) { return 300; }
}

public class PointPayment implements PaymentMethod {
    public int calculateFee(int amount) { return 0; }
}

// 호출부는 분기 없이 한 줄
int fee = paymentMethod.calculateFee(amount);

    R12. 클래스 추출¶

    한 클래스가 두 가지 이상의 책임을 지고 있을 때 나눈다

    // Before — 주문 처리 서비스가 알림 문구 조립까지 담당
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;
    private final SmsSender smsSender;

    public void placeOrder(Order order) {
        orderRepository.save(order);
        String message = "[주문완료] " + order.getItemName()
                + " " + order.getQuantity() + "개, 총 " + order.getTotalPrice() + "원";
        smsSender.send(order.getPhoneNumber(), message);
    }
}

// After — 문구 조립은 별도 클래스로 분리, 서비스는 흐름만 담당
@Component
public class OrderMessageFormatter {
    public String orderCompleted(Order order) {
        return "[주문완료] " + order.getItemName()
                + " " + order.getQuantity() + "개, 총 " + order.getTotalPrice() + "원";
    }
}

@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;
    private final OrderMessageFormatter messageFormatter;
    private final SmsSender smsSender;

    public void placeOrder(Order order) {
        orderRepository.save(order);
        smsSender.send(order.getPhoneNumber(), messageFormatter.orderCompleted(order));
    }
}

    R28. 집합 캡슐화¶

    컬렉션 getter가 내부 리스트를 그대로 넘기면 외부에서 마음대로 추가·삭제할 수 있어 캡슐화가 깨진다

    읽기 전용으로 노출하고, 변경은 도메인 메서드로만 열어 준다

    // Before — 외부에서 항목을 직접 넣으면 총액이 갱신되지 않아 상태가 깨짐
public class Order {
    private final List<OrderItem> items = new ArrayList<>();
    private int totalPrice;

    public List<OrderItem> getItems() { return items; }
}
// 호출부: order.getItems().add(newItem);   ← totalPrice는 그대로

// After — 변경은 도메인 메서드로만, 그 안에서 총액도 함께 갱신
public class Order {
    private final List<OrderItem> items = new ArrayList<>();
    private int totalPrice;

    public List<OrderItem> getItems() { return List.copyOf(items); }

    public void addItem(OrderItem item) {
        items.add(item);
        recalculateTotalPrice();
    }

    public void removeItem(String itemId) {
        items.removeIf(item -> item.getId().equals(itemId));
        recalculateTotalPrice();
    }

    private void recalculateTotalPrice() {
        totalPrice = items.stream().mapToInt(OrderItem::getPrice).sum();
    }
}
